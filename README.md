## День 7: как работает сервис

### Что это

Простой AI-агент — веб-чат с LLM через OpenAI-совместимый API GPustack. Ключ API берётся из файла `.env` (переменная `GPUSTACK_API_KEY`).

### Компоненты

- **`agent.py`** — класс `SimpleAgent`: системный промпт, хранение диалогов, сборка контекста из скользящего окна + LLM-сводка старых сообщений (см. «День 9»), включение рассуждений через `chat_template_kwargs`, учёт usage-токенов (вход/рассуждения/всего), сохранение последнего API-запроса.
- **`main.py`** — HTTP-сервер на `http.server` + REST-эндпоинты:

  | Метод | Маршрут | Назначение |
  | ----- | ------- | ---------- |
  | GET | `/` | чат-страница (index.html) |
  | GET / POST | `/agent/config` | текущие настройки / изменение (system prompt, модель, temperature, max_tokens, reasoning; с дня 9 — window_size, summary_gap, compression_enabled) |
  | POST | `/agent/ask` | отправить сообщение, получить ответ |
  | GET / DELETE | `/agent/history` | история запросов / очистка |
  | GET | `/agent/tokens` | токен-статистика: история диалога, ответ модели, сводка (summary_tokens) |
  | GET | `/agent/models` | список доступных моделей |
  | GET | `/agent/last-request` | JSON последнего API-запроса |
  | GET / POST | `/agent/dialogues` | список диалогов / новый диалог |
  | GET | `/agent/dialogues/{id}` | сообщения диалога |
  | POST | `/agent/dialogues/{id}/activate` | сделать диалог активным |

- **`index.html`** — TRON-HUD интерфейс: показ токенов и лимита контекста, чекбокс рассуждений, выбор модели, модалки — системный промпт и JSON последнего запроса, список диалогов с бейджами непрочитанных, история запросов.

### Запуск

1. Создать `.env` с переменной `GPUSTACK_API_KEY`.
2. `python main.py`
3. Открыть http://127.0.0.1:8000

### Данные

- `dialogues.json` — все диалоги + отметка активного; файл в `.gitignore`, в git не попадает.
- `history.json` — legacy-формат, автоматически мигрируется в `dialogues.json`.

### Возможности дня 7

- Персистентность: после перезапуска сервиса чат продолжает «как будто не заканчивался».
- TRON-HUD: токены (вход/рассуждения/всего), лимит контекста, toggle рассуждений, выбор модели.
- Новый диалог: текущий уходит в архив.
- Продолжение диалога из архива: клик по диалогу делает его активным, предыдущий закрывается.
- Бейдж непрочитанных диалогов в списке.
- JSON последнего API-запроса в модалке (что именно ушло в API).

### Рабочие модели

`qwen3.8-27b`, `deepseek-v4-flash`, `glm-5.3-flash`

### Безопасность

В репозиторий не попадают секреты и данные диалогов: в `.gitignore` — `.env`, `history.json`, `dialogues.json`, `*.log`.

## День 8: подсчёт токенов

### Задание

- Поправить реализованный алгоритм подсчёта токенов: для текущего запроса,
  для всей истории диалога, для ответа модели.
- Указать лимит токенов выбранной модели.
- Модалка JSON-запроса: кнопка «Скопировать» последнего JSON + возможность
  изменить размеры модального окна.

### Как считается

Токенайзера в stdlib нет, поэтому подсчёт эвристический, но **каллиброванный
по реальному API**: норму «токенов на символ» для каждой модели измерили
пробными запросами (`max_tokens=1`): `rate = (prompt_tokens(текст) −
prompt_tokens("")) / len(текст)`.

| модель | other (кириллица/латиница) | CJK |
| ------ | -------------------------- | --- |
| qwen3.8-27b | 0.4366 | 0.588 |
| deepseek-v4-flash | 0.3803 | 0.588 |
| glm-5.3-flash | 0.4085 | 0.588 |

Алгоритм (`agent.count_tokens`, зеркало `countTokens` в index.html — при
изменении менять оба места): символы делятся на CJK (Han/Kana/Hangul) и
остальное, каждая часть умножается на норму модели и округляется вверх.
Нормы идут в ответе `GET /agent/models` (`token_rate`) — клиент живьём
пересчитывает «текущий запрос» по норме выбранной модели.

Подсчёт — токены ТЕКСТА сообщений (без служебных токенов chat-шаблона, ~2–4
на сообщение), точность ±10% по замерам.

| Ячейка HUD | Что считается | Где |
| ---------- | ------------- | --- |
| Лимит токенов | `context_limit` выбранной модели | `/agent/models` |
| Текущий запрос | текст поля ввода, live при каждом нажатии клавиши | клиент (JS, `token_rate` модели) |
| История диалога | вся история активного диалога (каллиброванный подсчёт) | сервер (`get_token_stats`) |
| Ответ модели | **точные** `completion_tokens` из usage последнего API-ответа (после рестарта — оценка по тексту) | сервер (`get_token_stats`) |

Новый эндпоинт: `GET /agent/tokens` → `{"history_tokens": N, "reply_tokens": N}`.

### Модалка JSON-запроса

- Кнопка «Скопировать» — pretty-JSON последнего запроса в буфер обмена
  (clipboard API, фолбэк `execCommand`); disabled, пока запросов не было.
- Размер окна меняется перетаскиванием маркера в правом нижнем углу
  (pointer events; min 320×200, max — окно браузера минус отступы).

## День 9: управление контекстом

### Что добавлено

Вместо «последние 20 сообщений целиком» контекст для LLM собирается из
**скользящего окна** и **сводки**:

- В LLM уходит последние `window_size` (по умолчанию **6**) сообщений
  активного диалога.
- Сообщения старше окна суммируются LLM-сводкой: когда за окном скапливается
  `summary_gap` (по умолчанию **4**) новых сообщений, сводка пересчитывается.
  Сводка хранится **по диалогу** и вставляется в system-промт префиксом
  `Резюме диалога: ...`.
- Если запрос сводки упал (ошибка API), агент деградирует в обычное окно,
  а `HISTORY_CAP = 20` остаётся жёстким потолком числа сообщений.
- Настройки меняются через `POST /agent/config`: `window_size`, `summary_gap`,
  `compression_enabled` (bool, по умолчанию true). Хранятся в памяти сервера,
  в `.env` не попадают.

Токен-статистика (`GET /agent/tokens`) дополнена полем `summary_tokens`
— размер текущей сводки.

### Бенчмарк расхода токенов

`benchmark.py` прогоняет один и тот же N-ходовый диалог дважды на
изолированном экземпляре агента (tmp-каталог, свой dialogues.json) и
сравнивает usage:

- **Режим A** — сжатие выключено (`compression_enabled: false`),
- **Режим B** — сжатие включено.

На каждый ход печатает prompt/completion/total, в конце — итоги обоих режимов
и разницу.

```bash
# офлайн-прогон (mock-API, без ключа, без сети)
python benchmark.py --mock

# реальный прогон: 22 хода, рассуждения выключены
python benchmark.py --turns 22 --reasoning off
```

Полный список флагов: `--turns N`, `--model M`, `--reasoning on|off`,
`--mock`, `--out DIR` (транскрипты режимов A и B в JSON).

### Запуск и тесты

```bash
python main.py              # сервер: http://127.0.0.1:8000
python -m pytest -q         # тесты
```

## День 10: стратегии управления контекстом

### Что добавлено

`strategies.py` — ABC `ContextStrategy` и 4 реализации. Стратегия привязана
к **диалогу** (ключ `strategy` в `dialogues.json`); новые диалоги получают
стратегию по умолчанию из `/agent/config` (дефолт — `legacy`, день 9):

| Стратегия | Как собирается контекст |
| --------- | ----------------------- |
| `sliding_window` | последние `N` (N=4) сообщения + текущий вопрос, без сводки |
| `sticky_facts` | окно N=4 + актуальные факты (цель/стек/ограничения/дедлайн/решения) в system-промпте; факты извлекает отдельный LLM-вызов (temp 0, без `last-request`) после каждого сообщения |
| `branching` | чекпоинт + две ветки A/B: payload = история до чекпоинта + активная ветка; ответ дописывается в основную историю и в активную ветку |
| `legacy` | день 9: вся история (окно тримом сжатия) + LLM-сводка старых сообщений |

Все стратегии не-деструктивны к истории на диске (кроме `legacy`, где
сжатие — движок дня 9).

### Эндпоинты

| Метод | Маршрут | Назначение |
| ----- | ------- | ---------- |
| GET | `/agent/strategy` | `strategy` / `strategy_state` / `facts` активного диалога |
| POST | `/agent/strategy/switch` | `{"strategy": "sliding_window"}` — переключение (свежий `default_state`) |
| POST | `/agent/strategy/checkpoint` | чекпоинт (только `branching`) |
| POST | `/agent/strategy/branch` | `{"branch": "A" \| "B"}` — переключение ветки |
| GET | `/agent/strategy/state` | только `strategy_state` активного диалога |

### Web UI

- селект «Стратегия» + кнопка «Применить стратегию» (`#cfg-strategy`,
  `#cfg-strategy-apply`);
- `sticky_facts`: панель фактов — 5 ключей, обновляется после каждого
  сообщения;
- `branching`: метка «Активная ветка» + кнопки «Чекпоинт» / «Ветка A» /
  «Ветка B» (панель опрашивает `/agent/strategy` каждые 2,5 с).

### Данные

`dialogues.json`: аддитивные ключи `strategy` + `strategy_state` на каждый
диалог; файлы дня 9 читаются как `legacy`. Деструктивных миграций нет.

### Бенчмарк стратегий

`benchmark_day10.py` прогоняет детерминированный 12-ходовой сценарий сбора
ТЗ (`scenario_day10.py`) на трёх стратегиях в изолированном агенте
(tmp-каталог). Метрики без LLM-judge:

```bash
python benchmark_day10.py --mock          # офлайн, mock-API, без ключа
python benchmark_day10.py --real          # реальный GPustack
python benchmark_day10.py --out FILE.json # отчёт в JSON
```

| Стратегия | stability | recall | total tokens | LLM-вызовы |
| --------- | --------- | ------ | ------------ | ---------- |
| sliding_window | 0.8333 | 0.5833 | 4211 | 12 |
| sticky_facts | 1.0000 | 1.0000 | 8681 | 24 |
| branching | 1.0000 | 1.0000 | 10374 | 13 |

stability — доля KEY_DETAILS в payload финального хода; recall — средняя
доля по ходам 7-12. Значения mock-прогона (qwen3.8-27b).

### E2E-прогон

```bash
python scripts/e2e_day10.py
```

Поднимает сервер (порт 8000 — зашардкожен в main.py) и проходит поток
стратегий: switch ×3, checkpoint, ветка B, `strategy/state`, UI
(`cfg-strategy` на странице). При достижимом GPustack дополнительно 3
реальных ask и проверка границы скользящего окна в `/agent/last-request`
(1 system + 4 + 1 user). Без API ask-зависимые проверки SKIP'ятся,
не-LLM поверхность проверяется. exit 0 = PASS/SKIP, 1 = FAIL.
