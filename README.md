## День 7: как работает сервис

### Что это

Простой AI-агент — веб-чат с LLM через OpenAI-совместимый API (по умолчанию). Ключ API берётся из файла `.env` (переменная `GPUSTACK_API_KEY`).

### Компоненты

- **`agent.py`** — класс `SimpleAgent`: системный промпт, хранение диалогов, сборка контекста из скользящего окна + LLM-сводка старых сообщений (см. «День 9»), включение рассуждений через `chat_template_kwargs`, учёт usage-токенов (вход/рассуждения/всего), сохранение последнего API-запроса.
- **`main.py`** — HTTP-сервер на `http.server` + REST-эндпоинты:

  | Метод | Маршрут | Назначение |
  | ----- | ------- | ---------- |
  | GET | `/` | чат-страница (index.html) |
  | GET / POST | `/agent/config` | текущие настройки / изменение (system prompt, модель, temperature, max_tokens, reasoning; с дня 9 — window_size, summary_gap, compression_enabled) |
  | POST | `/agent/ask` | отправить сообщение, получить ответ |
  | GET / DELETE | `/agent/history` | история запросов / очистка |
  | GET | `/agent/tokens` | токен-статистика: история диалога, ответ модели, сводка (summary_tokens) |
  | GET | `/agent/models` | список доступных моделей |
  | GET | `/agent/last-request` | JSON последнего API-запроса |
  | GET / POST | `/agent/dialogues` | список диалогов / новый диалог |
  | GET | `/agent/dialogues/{id}` | сообщения диалога |
  | POST | `/agent/dialogues/{id}/activate` | сделать диалог активным |

- **`index.html`** — TRON-HUD интерфейс: показ токенов и лимита контекста, чекбокс рассуждений, выбор модели, модалки — системный промпт и JSON последнего запроса, список диалогов с бейджами непрочитанных, история запросов.

### Запуск

1. Создать `.env` с переменной `GPUSTACK_API_KEY`.
2. `python main.py`
3. Открыть http://127.0.0.1:8000

### Данные

- `dialogues.json` — все диалоги + отметка активного; файл в `.gitignore`, в git не попадает.
- `history.json` — legacy-формат, автоматически мигрируется в `dialogues.json`.

### Возможности дня 7

- Персистентность: после перезапуска сервиса чат продолжает «как будто не заканчивался».
- TRON-HUD: токены (вход/рассуждения/всего), лимит контекста, toggle рассуждений, выбор модели.
- Новый диалог: текущий уходит в архив.
- Продолжение диалога из архива: клик по диалогу делает его активным, предыдущий закрывается.
- Бейдж непрочитанных диалогов в списке.
- JSON последнего API-запроса в модалке (что именно ушло в API).

## День 8: подсчёт токенов

### Задание

  для всей истории диалога, для ответа модели.

- Модалка JSON-запроса: кнопка «Скопировать» последнего JSON + возможность

### Как считается

Токенайзера в stdlib нет, поэтому подсчёт эвристический, но **каллиброванный
по реальному API**: норму «токенов на символ» для каждой модели измерили
пробными запросами (`max_tokens=1`): `rate = (prompt_tokens(текст) −
prompt_tokens("")) / len(текст)`.

| модель | other (кириллица/латиница) | CJK |
| ------ | -------------------------- | --- |
| qwen3.8-27b | 0.4366 | 0.588 |
| deepseek-v4-flash | 0.3803 | 0.588 |
| glm-5.3-flash | 0.4085 | 0.588 |

Алгоритм (`agent.count_tokens`, зеркало `countTokens` в index.html — при
изменении менять оба места): символы делятся на CJK (Han/Kana/Hangul) и
остальное, каждая часть умножается на норму модели и округляется вверх.
Нормы идут в ответе `GET /agent/models` (`token_rate`) — клиент живьём
пересчитывает «текущий запрос» по норме выбранной модели.

Подсчёт — токены ТЕКСТА сообщений (без служебных токенов chat-шаблона, ~2–4
на сообщение), точность ±10% по замерам.

| Ячейка HUD | Что считается | Где |
| ---------- | ------------- | --- |
| Лимит токенов | `context_limit` выбранной модели | `/agent/models` |
| Текущий запрос | текст поля ввода, live при каждом нажатии клавиши | клиент (JS, `token_rate` модели) |
| История диалога | вся история активного диалога (каллиброванный подсчёт) | сервер (`get_token_stats`) |
| Ответ модели | **точные** `completion_tokens` из usage последнего API-ответа (после рестарта — оценка по тексту) | сервер (`get_token_stats`) |

Новый эндпоинт: `GET /agent/tokens` → `{"history_tokens": N, "reply_tokens": N}`.

## День 9: управление контекстом

### Что добавлено

Вместо «последние 20 сообщений целиком» контекст для LLM собирается из
**скользящего окна** и **сводки**:

- В LLM уходит последние `window_size` (по умолчанию **6**) сообщений
  активного диалога.
- Сообщения старше окна суммируются LLM-сводкой: когда за окном скапливается
  `summary_gap` (по умолчанию **4**) новых сообщений, сводка пересчитывается.
  Сводка хранится **по диалогу** и вставляется в system-промт префиксом
  `Резюме диалога: ...`.
- Если запрос сводки упал (ошибка API), агент деградирует в обычное окно,
  а `HISTORY_CAP = 20` остаётся жёстким потолком числа сообщений.
- Настройки меняются через `POST /agent/config`: `window_size`, `summary_gap`,
  `compression_enabled` (bool, по умолчанию true). Хранятся в памяти сервера,
  в `.env` не попадают.

Токен-статистика (`GET /agent/tokens`) дополнена полем `summary_tokens`
— размер текущей сводки.

### Бенчмарк расхода токенов

`benchmark.py` прогоняет один и тот же N-ходовый диалог дважды на
изолированном экземпляре агента (tmp-каталог, свой dialogues.json) и
сравнивает usage:

- **Режим A** — сжатие выключено (`compression_enabled: false`),
- **Режим B** — сжатие включено.

На каждый ход печатает prompt/completion/total, в конце — итоги обоих режимов
и разницу.

```bash
# офлайн-прогон (mock-API, без ключа, без сети)
python benchmark.py --mock

# реальный прогон: 22 хода, рассуждения выключены
python benchmark.py --turns 22 --reasoning off
```

Полный список флагов: `--turns N`, `--model M`, `--reasoning on|off`,
`--mock`, `--out DIR` (транскрипты режимов A и B в JSON).

### Память (3 слоя)

| Слой | Ключ | Область | Что хранит |
| --- | --- | --- | --- |
| Диалог (ST) | `dialogues.json` | на диалог | сообщения чата (история) |
| Рабочая (WM) | `working.json` | на диалог | ключ-значения «текущей задачи» |
| Долговременная (LT) | `longterm.json` | глобально | ключ-значения знаний |

WM активного диалога и LT инжектятся в system-промт блоками `- key: value`
(пустой слой → блок не добавляется). Сообщения диалога (ST) идут в `messages`
тела запроса, не в system-промт.

**Тумблеры слоёв.** Каждый слой (ст/wm/lt) можно включить/отключить в любой
последовательности (свитчи в вкладке «Память», состояние — `toggles.json`,
в ответе `GET /api/memory` и `GET /api/memory/toggles`). Выключенный слой не
уходит в LLM: ст off — в запросе только текущее сообщение (сообщения при этом
хранятся и видны в UI), wm/lt off — их блоки не добавляются в system-промт,
правило конфликтов и server-side гард смотрят только включённые слои.
Данные слоя при выключении не удаляются — включил, всё на месте. В UI
выключенный слой задиммится и редактирование в нём блокируется.

**Важно:** выключенный непустой слой — в system-промт добавляется явная
заметка «слой отключён, не ссылайся на его пункты, даже если они
упоминались ранее в диалоге». Без неё модель «отрабатывает» память из
истории диалога: прошлые ответы, сказавшие «по памяти …», удерживают её —
и запрос, противоречащий выключенной памяти, модель всё равно отклоняла.

**Правило конфликтов.** Когда память непустая, к system-промту добавляется
правило: пункты памяти — устойчивые ограничения **с приоритетом над любыми
запросами диалога** (включая последние); перед ответом запрос сверяется с
каждым пунктом, и при противоречии агент не подчиняется молча — **вежливо
отказывает**, добавляет **лёгкий юмор**, ссылается на конкретный пункт и
**сообщает, что принято решение действовать по памяти**. В правиле есть
few-shot пример (мелкие модели без явного примера подчиняются свежему
запросу). Сам пункт памяти не изменяет и не удаляет — памятью управляет
только пользователь.

**Server-side гард конфликта.** Мелкие модели (glm/deepseek/qwen flash) при
истории диалога всё равно подчиняются противоречащему запросу, несмотря на
правило в system-промте. Поэтому бэкенд детектирует конфликт до запроса:
ключ пункта памяти (WM+LT) встречается в сообщении, значение пункта НЕ
встречается, и в сообщении есть глагол действия («напиши», «измени», …).
При срабатывании в конец `messages` (самое «свежее» место) добавляется
явное system-напоминание «запрос противоречит пункту X — откажись».
Вопросы про память («какой источник?») гард не трогает; ключ короче 4
символов слишком неоднозначен — пропускается.

## День 12: Персонализация (профиль пользователя)

### Что это

Персонализация поверх модели памяти дня 11: у каждого диалога — свой профиль
пользователя (4 текстовых поля: имя, профессиональная роль и сфера, тон и
стиль общения, стоп-слова/табу) + статус (`pending` → `active` | `declined`).
Профиль хранится в записи диалога (`dialogues.json`), переживает перезапуск
сервера и переключается вместе с диалогом.

### Инициализация

При первом сообщении в новом диалоге запрос НЕ уходит в LLM: агент
предлагает инициализировать профиль тремя способами:

1. **Заполнить вручную** — вкладка «Профили» в панели «Контекст»: 4 поля +
   «Сохранить» (`POST /api/profile`), статус становится `active`.
2. **Провести интервью** — агент задаёт 4 вопроса одним сообщением; из ответа
   non-stream LLM-вызовом (best-effort JSON, тот же паттерн, что у
   авто-заголовка дня 11) извлекаются 4 поля. Сбой экстракции не ломает чат:
   интервью остаётся активным, агент просит повторить.
3. **Отказаться** — запросы выполняются как обычно, без учёта предпочтений
   (статус `declined`).

Служебные тексты приглашения, интервью и отказа — детерминированные
константы: LLM в них не участвует. Выбор варианта — по маркерам в сообщении
пользователя («интерв…», «вручную», «отказ…»).

### Инъекция

`active`-профиль добавляется в system-промт каждого запроса блоком
«Профиль пользователя» (`agent.build_profile_block`): пустые поля
пропускаются, при заполненных стоп-словах — дополнительная строка
«Избегай: …». Порядок сборки system-промпта: базовый промпт → профиль →
блоки памяти → правило конфликтов.

**Два действия стоп-слов/табу.** Поле «стоп-слова/табу» работает в двух
направлениях:

1. **Избежание** (инъекция): строка «Избегай: …» в system-промпте — агент
   не использует перечисленные слова/темы в собственных ответах.
2. **Гард на упоминание** (server-side, `agent._detect_taboo`, день 12 D8):
   при `active`-профиле система детерминированно (без LLM) режет табу-поле
   на слова по `,`/`;` (токены короче 2 символов — шум, пропускаются) и
   сверяет с сообщением пользователя без учёта регистра. Если табу-слово
   в запросе есть — в конец списка сообщений добавляется system-напоминание
   (тот же паттерн, что server-side гард конфликтов памяти дня 11): агент
   вежливо отказывает в части запроса, задействующей табу-слово (лёгкая
   интонация, ссылка на конкретное слово), сообщая, что решение принято по
   профилю. Статус профиля гардом не меняется; для `pending`/`declined` и
   при пустых табу гард неактивен. Профиль остаётся вне гарда WM/LT:
   предпочтения, а не факты.

## День 13b: Задача как запрос пользователя (Task Redesign)

### Что это

Задача = запрос пользователя в режиме «задача»: тумблер чат/задача у поля
ввода (глобальный, состояние в `localStorage`) — в режиме «задача»
отправленное сообщение становится задачей, в режиме «чат» — обычным
сообщением. Задача пер-диалог: пайплайн
`planning → execution (N work-шагов) → validation → done`, unified FSM из
6 значений — `planning | execution | validation | done | paused | failed`
(`paused`/`failed` — значения стадии, не флаги). Stage-агенты (Планировщик
/ Исполнитель / Валидатор / Оркестратор) — один и тот же LLM из конфига с
разными system-промптами; пайплайн ведёт детерминированный код
(`agent.task_run`) — LLM не управляет FSM. Вкладки «Задача» больше нет:
всё — в карточке процесса прямо в ленте чата.

### Пошаговое исполнение

- **Планировщик** (1 LLM-вызов) — JSON-план: 1–5 work-шагов (best-effort
  парсинг; сбой/не-JSON — фолбэк в один шаг «Выполнить запрос»).
- **Исполнитель** — по LLM-вызову на work-шаг, стримингом (события
  `step_updated`/`step_delta` — карточка показывает живой вывод шага).
- **Валидатор** — сверка результатов с планом, вердикт
  `<verdict>pass|fail</verdict>` (best-effort, отсутствие метки = pass);
  fail → ретрай execution (максимум 1) с замечаниями валидатора в
  промпте.
- **Оркестратор** — финальный синтез. Итого N+3 LLM-вызова (до 2N+3 с
  ретраем); stage/work-вызовы не пишутся в журнал `requests.json`.
- **Пауза** вступает на границе work-шага: текущий LLM-вызов
  доигрывается, следующий шаг не начинается; фиксируется
  `context_snapshot`. **Инструкция на паузе** инжектится в промпт
  следующего шага/стадии и используется один раз. **Продолжение** — с
  сохранённого состояния: выполненные шаги/стадии не повторяются.
  **Ошибка LLM-вызова** — стадия `failed` + событие `task_failed`;
  повтор — через «Продолжить»/новый run (auto-resume к первой
  невыполненной стадии).

### Карточка процесса в чате

Пользовательский запрос задачи — якорь карточки в ленте (user-сообщение с
`task_id`). Карточка живая: спавн stage-агентов (иконка, «спавн N с
назад»), чек-лист work-шагов [✓]/[⏳]/[○], живой бокс вывода текущего
шага, секции стадий сворачиваются (DONE — всё свёрнуто, FAILED — секция
ошибки развёрнута); кнопки Пауза/Продолжить/Повтор прямо в карточке.
История задачи после перезагрузки восстанавливается из маркеров
сообщений (`task_id`/`task_stage`/`task_step`) — выводы стадий/шагов
хранятся как assistant-сообщения с метками и не рендерятся отдельными
bubble (показаны в секциях карточки), финальный синтез — обычное
assistant-сообщение с `task_id` без `task_stage`.

### Контекст

Task-промпты собираются ТОЛЬКО из состояния задачи (`description`,
`plan`, `work_steps`, `instruction`); история сообщений чата в
task-промпты не уходит (чат — лишь представление задачи).

### API

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/task/start` | Создать задачу `{dialogue_id, description}` → 200 `task` (новый `task_id`, `stage: planning`, `plan` из 4 записей) + user-сообщение-маркер; 400 — незавершённая активная задача / пустое описание; 404 — диалог; после done/failed — новая задача (новый `task_id`) |

### Гард чата

Активная непаузанная незавершённая задача: `POST /api/chat` → SSE
`error` «Задача выполняется…», сообщение пользователя не сохраняется.
На паузе/после done/failed чат работает как обычно (в том числе режим
«чат» не создаёт задачи).

### Проверка задания

E2E: старт → user-маркер → run до `task_done` (структура событий,
пошаговый пайплайн) → done-состояние (plan + work_steps) → маркеры
сообщений → 400-гарды на done → новая задача (другой `task_id`) → гард
чата → reset; live: пауза на границе work-шага → `task_paused` +
`context_snapshot` → instruction → resume → `task_done`; чат-режим —
без task-маркеров.

### Исправления после релиза

- **Resume, пока стримится чужой run — не теряется.** Run-слот глобальный:
  если стримится run другого диалога (`taskRunning`), клик «Продолжить» ждёт
  освобождения слота (wait-loop `sleep(400)`), затем `POST /api/task/resume` +
  `reloadTask` + `runTask`. Раньше resume отправлялся, пока слот занят, и
  состояние бэкенда рассинхронизировалось с фронтендом. `resumeInFlight`
  защищает от двойного клика (двойной «Продолжить»/«Повтор»). Ошибка
  (задача уже не resumable, 400-гард) → перечитывается авторитетная задача.
- **Карточка: кнопка «Продолжить» в зависшем состоянии.** Если задача в
  `execution`/`planning`, но run не идёт (`!running`) — показывается кнопка
  «Продолжить», запускающая пайплайн через `POST /api/task/run`
  (восстановление из маркеров при перезагрузке).
- **Бренд сайдбара — «◆ День 13»** (было «День 11»), соответствует номеру
  текущего дня.

## День 14: Инварианты

### Что это

Инварианты — жёсткие ограничения ассистента, которые он **не имеет права
нарушать**. Хранятся отдельно от диалога, всегда активны, инжектятся в
system-промпт, и при противоречии с запросом ассистент отказывается, а
server-side гард добавляет system-напоминание. Примеры: выбранная
архитектура, принятые технические решения, ограничения по стеку,
бизнес-правила.

### Модель данных

Инвариант = `{id, title, description, forbidden[], is_active}`; `id` = `"inv_" + 4 hex`.
Глобальный слой (`invariants.json` рядом с `longterm.json`), **не** на диалог.
`forbidden` — список строк-паттернов (подстрока, без учёта регистра): если
паттерн встречается в сообщении пользователя (попытка переопределить) или в
ответе модели — срабатывает гард. `is_active` — тумблер пользователя: `false`
⇒ инвариант не инжектится и не проверяется, но НЕ удаляется (виден в UI,
задиммлен). В UI — интерфейс редактирования с полями title/description/forbidden
и свитч is_active.

### Инъекция и правило конфликтов

Сборка system-промпта: базовый промпт → профиль → **инварианты** → блоки
памяти (WM→LT) → правило конфликтов. Непустой слой **активных** инвариантов
добавляет блок `- title: description`, затем правило `INVARIANTS_RULE` —
**жёстче** правила конфликтов памяти: инварианты имеют **высший приоритет** над
любым запросом диалога и памятью; при противоречии ассистент **отказывается**,
называет конкретный инвариант, объясняет причину и предлагает альтернативу.
Сам инвариант не изменяет и не удаляет. В `INVARIANTS_RULE` — требование
явно сверять запрос/ответ с инвариантами в шаге рассуждения.

### Server-side гард (двухуровневый)

- **Pre-guard** (до LLM): если в сообщении пользователя есть `forbidden`-паттерн
  (попытка переопределить, например "забудь… используем Python"), в конец
  `messages` добавляется system-напоминание «запрос противоречит инварианту —
  откажись». Гард активен только на активных инвариантах.
- **Post-guard** (после ответа): детерминированная проверка ответа `answer` на
  `forbidden`-паттерны (`_postcheck_invariants`); при срабатывании ответ
  заменяется отказом (называет нарушающий паттерн), а в SSE-потоке перед `done`
  отдаётся событие `{"type": "invariant_violation", "patterns": [...]}`.
  Семантический L2-чек (вторичный LLM) — задел на будущее, код структурно
  к этому готов.

### API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/invariants` | Список инвариантов |
| POST | `/api/invariants` | Создать `{title, description, forbidden?, is_active?}`; 400 — пустой title/description, forbidden не список строк, is_active не bool |
| POST | `/api/invariants/{id}/toggle` | Переключить `is_active`; 404 — не найден |
| DELETE | `/api/invariants/{id}` | Удалить; 404 — не найден |
| GET | `/api/rules` | Добавлено поле `invariants_block` (готовый блок для system-промпта) |

post-guard заменяет его отказом + SSE `invariant_violation`. Бэкенд-тесты:
конкурс — при противоречии запроса и инварианта ассистент отказывается и
называет инвариант; объяснение отказа; post-guard на ответе.<br>**Старое
представление `{key, value}`** автоматически мигрирует на чтении
(`title=key`, `description=value`, `forbidden=[]`, `is_active=true`).

### Исправления после релиза

- **Спящие инварианты полностью игнорируются.** Раньше `is_active=false` всё ещё
  учитывался из-за обработки булевых значений как строк: в `longterm.json` /
  `invariants.json` значение могло быть `"false"`/`"0"` (строка), и проверка
  `if value is True` его не отсекала. Добавлен `memory._parse_active`,
  нормализующий `bool`/строки `"1"/"true"/"yes"` → `True`, остальное → `False`;
  `_read_invariants` использует его. Неактивный инвариант не инжектится в
  system-промпт и не проверяется гардами, но НЕ удаляется (виден в UI, задиммлен).
- **`pending → declined` продолжает выполнение.** При отказе от инициализации
  профиля сообщение с содержательным остатком («отказ, теперь объясни лямбды»)
  раньше проглатывалось: `_decline_remainder` возвращал только маркер отказа, а
  остаток не отправлялся в LLM. Теперь остаток после маркера идёт в чат как
  обычный запрос — LLM-стрим вызывается; чистое «отказ» (без текста) по-прежнему
  закрывает тему без вызова.
- **Тип frontend `invariant_violation`.** В `TaskEvent`-union (`api.ts`) не было
  этого события, хотя бэкенд его шлёт, — `tsc` выдавал ошибку и блокировал сборку.
  Добавлен тип `{ type: 'invariant_violation'; patterns: string[] }`.
- **Бренд — «AI Studio».** В сайдбаре и `<title>` вкладки название сменено с
  «День 13» / «Студия — день 13» на универсальное «AI Studio».

## День 15: Проверка плана и согласованный контекст

### Что это

Надстройка над пайплайном задач дня 13b/14: между `planning` и `execution`
появляется **человеческая стадия `plan_review`** — гейт одобрения плана,
плюс фикс done-пост-гарда, чтобы объяснение согласованной альтернативы не
рубилось отказом. Полный FLOW теперь
`planning → plan_review → execution → validation → done` (5 стадий вместо 4).

### Plan review (человеческий гейт)

- После `planning` (планировщик отработал) задача не идёт сразу в
  `execution`: стадия `plan_review`, `expected_action = human_input`. Run на
  этой стадии не запускает агентов — отдаётся SSE `plan_review` и ожидается
  решение пользователя.
- **Ограничения плана** (`_task_plan_constraints`, детерминированно, без
  LLM): план сверяется с активными инвариантами, памятью (WM/LT) и табу
  профиля. Найденные — фиксируются в `constraints` + предлагается
  `alternative` («переработаю план в рамках ограничений»). Показываются в
  карточке на `plan_review`.
- **Кнопки «Одобрить»/«Отклонить»** в карточке:
  - `POST /api/task/approve` → `plan_approved=true`, стадия `execution`,
    запускается исполнение.
  - `POST /api/task/reject {note?}` → запись planning сбрасывается в
    `pending`, стадия `planning`, `plan_approved=false`; note уходит как
    `instruction` — планировщик переиграет план с учётом замечания.
- Ввод новой задачи на `plan_review` исключён — решение только кнопками.

### Фикс done-пост-гарда (согласованный контекст)

Проблема: если план одобрен (`plan_approved`), исполнитель/оркестратор
легитимно объясняют отказ от запрета словами из `forbidden` (например
«Python запрещён, поэтому TypeScript»). Наивный пост-гард дня 14 считал
это нарушением и рубил финальный синтез отказом.

Фикс: на done-ветке при `plan_approved` из `hits` исключаются
`forbidden`-паттерны, уже встретившиеся в **согласованном контексте задачи**
— `description` + `plan['output']` + выводы всех `work_steps`. Реальное
нарушение (паттерн вне контекста задачи) по-прежнему режется.

### Пауза во время LLM-вызова

`/api/task/run` обёрнут в `try/except` в `gen()`: непойманное исключение

## День 16: Подключение MCP

### Что это

Подключение внешних **Model Context Protocol (MCP)** серверов к Студии:
реестр стартует с фиксированным набором (Firecrawl — web-поиск, Git —
репозиторий; stdio-процессы на `npx`, поддерживается и удалённый
streamable-http), пользователь нажимает «Подключить» — и видит инструменты
сервера в отдельной панели «MCP» (своя кнопка «🧩» в шапке чата рядом с
«⚙», панель выезжает справа). День 16 — **подключение, отключение, просмотр и вызов**: инструмент
подключённого сервера вызывается командой `/имя-сервера имя-тула` прямо в
чате (автодополнение, форма аргументов по `input_schema`); результат
сохраняется в диалог и виден LLM в следующих запросах (tool-loop).

### Архитектура

- **`mcp.py`** — клиент MCP-протокола (2024-11-05, JSON-RPC 2.0):
  - `_StdioSession` — локальный процесс: pipes (stdin/stdout), по одной
    JSON-строке в кадр; env-плейсхолдеры `{VAR}` расширяются из окружения
    на запуске (в файле хранятся плейсхолдеры, не значения);
  - `_HttpSession` — streamable-http: `POST {url}` с заголовками
    `MCP-Protocol-Version`/`MCP-Session-Id` (из ответа `initialize`),
    `Accept: application/json, text/event-stream`; SSE-ответ разбирается
    по кадрам `data: {json}`;
  - `MCPClient` — facade: `connect()` = `initialize` + `tools/list`,
    `tools()`, `call_tool()` (tools/call), `close()`;
  - `MCPRegistry` — реестр: держит клиенты, runtime-статусы
    (`idle`/`connected`/`error` + `tools_count`), `add`/`remove`/
    `connect`/`disconnect`/`tools`/`call_tool`/`close_all`. Сбой подключения —
    `status: error` + текст ошибки, агент не падает; повторный connect
    разрешён (self-heal).
- **`memory.py`** — CRUD реестра: `mcp_servers.json` рядом с
  `longterm.json`; при первом обращении создаются дефолты **Firecrawl**
  (`npx -y firecrawl-mcp`) и **Git**
  (`npx -y @cyanheads/git-mcp-server@latest`).
- **`agent.py`** — принимает опциональный `mcp` (DI для тестов) или
  строит `MCPRegistry` сам; `MCPRegistry.close_all()` — shutdown-хук.
- **Таймауты** — из `.env`: `MCP_CONNECT_TIMEOUT` (дефолт 30 c).

### API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/mcp/servers` | Реестр MCP-серверов с runtime-статусом (idle/connected/error, tools_count) |
| POST | `/api/mcp/servers` | Добавить сервер `{name, type, command?, url?, env?, enabled?}` → 201 `{server}`; 400 — RU-detail |
| DELETE | `/api/mcp/servers/{id}` | Удалить сервер (404 — не найден) |
| POST | `/api/mcp/servers/{id}/connect` | Подключить (initialize + tools/list) → `{server}`; сбой = status error, 404 — не найден |
| POST | `/api/mcp/servers/{id}/disconnect` | Отключить (закрыть сессию, status → idle, сервер остаётся в реестре) → `{server}`; 404 — не найден |
| GET | `/api/mcp/tools` | Инструменты подключённых серверов `[{server, name, description, input_schema}]` |
| POST | `/api/mcp/servers/{id}/tools/{tool}` | Вызвать инструмент (tool-loop) `{dialogue_id, arguments}` → `{"ok": true}`; результат — system-сообщение с маркером `mcp_tool` в диалоге (видно LLM); 400 — сервер не подключён / arguments не объект, 404 — сервер или диалог не найден |

### UI

Отдельная панель «MCP» — **не** вкладка настроек: своя кнопка «🧩» в шапке
чата (рядом с «⚙ Настройки») открывает overlay `McpOverlay`, выезжающий
справа (те же классы, что у `SettingsOverlay`); контент — `McpTab`.
Настройки «⚙» (Память / Профили / Инварианты) MCP больше не содержат:

- строка сервера — имя / чип типа (`stdio`/`http`) / статус-чип
  (не подключён / подключён / ошибка, при ошибке — текст) / число
  инструментов / кнопка «Подключить» (подключён — «Отключить») / «×» (удалить);
- секция «Инструменты подключённых серверов» — name + description
  каждого инструмента;
- тумблер: не подключён → «Подключить» (блокируется, пока не enabled); подключён → «Отключить» (закрывает сессию, status → idle, сервер **остаётся в реестре** — в отличие от «×», которое удаляет запись);
- добавления в UI нет — реестр фиксирован (дефолты); API `POST
  /api/mcp/servers` остаётся (на нём держится детерминированный e2e).

**Вызов инструмента из чата (tool-loop).** В режиме «Чат» ввод `/`
открывает автодополнение: сначала серверы, после выбора — инструменты
подключённого сервера (↑/↓/Enter/Tab — выбор, Esc — закрыть; Enter при
открытом списке не шлёт сообщение). Выбранный инструмент открывает форму
аргументов, сгенерированную из его `input_schema` (string/number/boolean/
JSON-поля, `required` помечены); «Вызвать» шлёт
`POST /api/mcp/servers/{id}/tools/{tool}`. Результат появляется в ленте как
карточка «MCP {сервер}/{тул}» и сохраняется в диалог — в следующих
LLM-запросах модель видит результат (tool-loop).

### Безопасность

Секреты — только в `.env` (корень репозитория). В `mcp_servers.json`
для переменных окружения хранятся плейсхолдеры `{VAR}` — расширение
происходит в памяти при запуске процесса, значения в файл не пишутся.

## День 17: MCP Tool-Loop (LLM-driven)

### Что это

LLM-driven tool-calling поверх подключения MCP дня 16: инструменты
подключённых MCP-серверов уходят в тело LLM-запроса (`tools`, формат
OpenAI), модель **сама** решает вызвать инструмент (`tool_calls`), агент
вызывает его на MCP-сервере, результат возвращается модели сообщением
`role: "tool"` в цикле до финального текстового ответа (кап 5 итераций).
День 16 вызывал инструменты только по команде пользователя
(`/сервер тул`); день 17 — модель сама. Пути дня 16 не меняются —
tool-loop добавлен поверх. Новый MCP-сервер — **Mock Task Manager**
(`studio/mcp_servers/task_manager.py`): stdio JSON-RPC (2024-11-05),
только stdlib, без npx; in-memory задачи (TASK-42: `in_progress`,
исполнитель migor; TASK-7: `done`), инструменты `get_task_details`
(required `task_id`) и `create_task` (required `title`).

### Архитектура

- **`task_manager.py`** — stdio MCP-сервер (newline-delimited JSON-RPC
  2.0): `initialize` (protocolVersion 2024-11-05), `tools/list`,
  `tools/call`; notification (без id) — без ответа; неизвестный метод —
  JSON-RPC -32601; ошибка «не найдено» — `{"error": "Задача не найдена:
  <id>"}` с `isError: true`.
- **`mcp.py`** — Task Manager добавлен как третий дефолт реестра
  (`command = [sys.executable, <repo>/studio/mcp_servers/task_manager.py]`,
  без npx); `connect()` на успех логирует `[MCP Init] {name}: {n}
  инструментов: {список}` (stdout, flush).
- **`agent.py`** — tool-loop в `ask_stream` (максимум 5 итераций):
  `_llm_tools()` превращает инструменты подключённых серверов в
  OpenAI-`tools`-массив (коллизии имён — префикс `{server_id}__`);
  `delta.tool_calls` агрегируются по `index`; assistant-сообщение
  сохраняется в диалог с `tool_calls`, каждый вызов — через
  `MCPRegistry.call_tool`, результат — `role: "tool"`-сообщение с
  `tool_call_id` и `name`; цикл повторяется (guards памяти/табу/
  инвариантов — повторно); финальный текст — `done`. Превышение капа —
  SSE `error` «Tool-loop: превышен лимит итераций (5)». Ошибка
  инструмента (MCPError, битые JSON-аргументы) — текст ошибки в
  tool-сообщении, цикл продолжается, агент не падает. Без подключённых
  серверов `tools` в payload нет (поведение дня 16, регресс
  `test_chat_payload_has_no_mcp_tools` остаётся зелёным). Журнал
  LLM-запросов — запись на каждую итерацию (тело с `tools`), usage
  суммируется.
- **Фронтенд** (`state.tsx`, `ChatPanel.tsx`) — сообщения
  `role: "tool"` — служебные записи: хранятся в памяти диалога (видно
  LLM), но не рендерятся чат-пузырями (паттерн day-16 mcp_tool-карточек).

### Логирование (консоль)

| Тег | Момент |
| --- | --- |
| `[MCP Init] {сервер}: N инструментов: a, b` | успешный `connect` (`mcp.py`) |
| `[LLM Decision] {тул} {args}` | модель решила вызвать инструмент |
| `[MCP Response] {тул}: {результат}` | сырой результат MCP-сервера |
| `[Final Response] {ответ}` | финальный текстовый ответ |

## День 18: Планировщик и фоновые задачи (MCP-дайджест 24/7)

### Что это

Агент, который **работает 24/7 и периодически выдаёт сводку**. Суть
задания дня 18 — MCP-инструмент с периодическим выполнением, который
**сохраняет данные (JSON)**, **выполняется по расписанию** и
**возвращает агрегированный результат**. Реализовано как связка из трёх
частей:

1. **Общий stdlib-коллектор** (`studio/collector.py`) — собирает
   агрегированный дайджест: погода (Open-Meteo, город по умолчанию
   Самара, `current` + `daily.2d`) и новости трёх RU-tech RSS-источников
   (vc.ru, habr, tproger) — top-5 на источник, дедуп по нормализованному
   заголовку. Чистый stdlib (`urllib`/`xml`/`json`), без зависимостей.
2. **Свой stdio MCP-сервер** (`studio/mcp_servers/news_weather.py`) —
   четвёртый дефолт реестра MCP дня 16, только stdlib (newline JSON-RPC
   2.0, паттерн `task_manager.py` дня 17), 4 инструмента:
   `get_weather(city?)`, `get_news(source?)`, `make_digest(city?)`
   (собирает + **сохраняет в JSON**) и `get_latest_digest()`
   (читает локальный файл, фолбэк — GitHub API репозитория).
3. **Расписание — GitHub Actions cron** (`.github/workflows/digest.yml`)
   — `0 */6 * * *` (UTC) + ручной `workflow_dispatch`: собирает
   `python studio/collector.py --out <repo>/data/digests`, коммитит
   `data/digests/` (push с retry). Дайджест лежит в git — «message bus»
   между расписанием и агентом.

Итого: расписание **пишет** дайджест в `data/digests/` (JSON), агент
**читает** его через tool-loop дня 17 — «покажи последнюю сводку» →
модель сама вызывает `get_latest_digest` → ответ со свежей сводкой.

## День 19: Композиция MCP-инструментов (pipeline: search → summarize → saveToFile)

Композиция MCP-инструментов: несколько MCP-инструментов, которые
**комбинируются в пайплайн** — первый получает данные, второй обрабатывает,
третий сохраняет результат. Ключевое архитектурное решение: **LLM-driven
композиция** — оркестратора в коде нет. Модель через tool-loop дня 17 (лимит
5 итераций) сама решает, какие из 3 инструментов вызвать, в каком порядке и
сколько. Пайплайн **динамический** и меняется от запроса пользователя:

- «Какая погода сейчас?» → 1 `search`.
- «Суммаризируй записи про Самара» → `search` → `summarize`.
- «…и сохрани в PDF» → `search` → `summarize` → `saveToFile(format=pdf)`.

Пути дней 16–18 (реестр, tool-loop, UI, `data/digests`) не меняются —
новый сервер `pipeline_tools`, PDF-модуль `pdf_writer` и e2e добавлены
поверх; `agent.py`/фронтенд/роуты не трогаются (tool-loop сам отдаст
3 инструмента модели через `_llm_tools`).

### MCP-сервер `pipeline_tools` (stdio, только stdlib)

Стандартный stdio MCP-сервер (2024-11-05, newline JSON-RPC 2.0, паттерн
`news_weather.py`/`task_manager.py`). 3 компонуемых инструмента:

| Инструмент | Аргументы | Результат |
| --- | --- | --- |
| `search` | `query` | локальный поиск по `data/digests/*.json` (день 18), case-insensitive, топ-20 по `generated_at` desc |
| `summarize` | `text`, `max_points=8` | **детерминированная** экстрактивная сводка (частотная оценка предложений), **без LLM** — сервер офлайн |
| `saveToFile` | `filename`, `content`, `format=md\|txt\|json\|pdf` | атомарная запись (tmp + `os.replace`) в `data/pipeline/`; basename-санитизация, traversal-safe |

- **`summarize` без LLM** — сервер офлайн (как `news_weather`);
  детерминизм критичен для офлайн-тестов и для e2e Part A, который
  ассертит на передачу данных. «Интеллектуальность» композиции — на модели,
  «обработка» на сервере — воспроизводимый алгоритм.
- **`saveToFile`** — только basename (`../` не проходит за каталог вывода),
  каталог `PIPELINE_OUT_DIR` (дефолт `<repo>/data/pipeline`) создаётся
  при отсутствии; `format=pdf` → `content` (строка) → `pdf_writer` → байты.
- **Env** (читаются на время вызова): `PIPELINE_SEARCH_DIR` (дефолт
  `<repo>/data/digests`), `PIPELINE_OUT_DIR`, `PIPELINE_FONT_PATH`.
- Ошибка любого инструмента — `{"error": ...}` + `isError: true`, процесс не
  падает. **Pipeline Tools** — **пятый дефолт** `MCPRegistry`
  (`[sys.executable, .../pipeline_tools.py]`, stdio, без npx).

### PDF-движок `pdf_writer` (stdlib, кириллица)

Полный PDF на чистом stdlib (не картинка/заглушка). `struct`-парсинг TTF:
`head` (unitsPerEm), `hhea` (ascent/descent, numHMetrics), `maxp`
(numGlyphs), `hmtx` (advance; short-run), `cmap` (форматы 4 + 12), `name`
(family → `/BaseFont`). **`glyf` не парсится** — контуры не нужны.

- Шрифт встраивается **целиком** как `/FontFile2` (сырые байты TTF) в
  Type0/CIDFontType2 с `/CIDToGIDMap /Identity`. Кириллица «из коробки»
  (GID↔code через Identity + `/ToUnicode` CMap `begincidrange` для
  поиска/копирования текста).
- Cвёртка: A4 595×842, поля 72pt, 11pt body / 14pt title, межстрочный 1.45,
  перенос по hmtx-ширинам (hard-break длинных слов), мультистраничность.
- **Детерминизм** — в PDF нет дат/UUID: повторный вызов на том же входе →
  **идентичные байты** (закреплено тестом).
- Шрифт ищется `find_default_font()` (env `PIPELINE_FONT_PATH` → первый из
  `arial.ttf`/`segoeui.ttf`/`tahoma.ttf` в `C:\Windows\Fonts` → `None`
  → `PdfError`). Без кириллического шрифта `text_to_pdf` бросает `PdfError`.

### LLM-driven цепочка (композиция на модели)

Tool-loop дня 17 отдаёт 3 инструмента в LLM-payload (`_llm_tools`); модель
сама вызывает их в нужном порядке/числе. **Факт live** (GPustack:
qwen3.8-27b, deepseek-v4-flash, glm-5.3-flash): модели автономно вызывают
`search` и используют результат, но **не** надёжно доводят цепочку до
`saveToFile` (суммаризируют в тексте ответа). Это ограничение моделей, а не
баг пайплайна. Поэтому **корректность передачи данных** доказана
**детерминированно** в e2e Part A (fake-LLM со скриптованной цепочкой из 3
tool-вызовов + assert: выход этапа N ⊂ вход N+1), а Part B — best-effort
live (PASS/PDF на диске или SKIP, не FAIL). Отдельно прогнана авто-цепочка
через реальный MCP-сервер (subprocess, не mock) →
`data/pipeline/demo_samara_report.pdf` (валидный `%PDF-1.4`, кириллица).

## День 20: Orchestration MCP

### Что это

Оркестрация MCP-инструментов: разбивка мультитул-серверов дней 17–19
(`task_manager`, `news_weather`, `pipeline_tools` — 3 файла, 9 тулов) на
**10 едицельных локальных MCP-серверов** (1 сервер = 1 тул, без дублей —
старые файлы удалены, общий каркас `_mcp_base.py`), плюс агентская
маршрутизация по серверам: **always-префикс** `{server}__{tool}` в именах
тулов (без логики коллизий) + **каталог подключённых серверов** в
system-промпте, лимит tool-loop поднят с 5 до **15** (хватает на длинный
флоу), бейджи «server · tool» в UI. Проверка задания — 10-шаговый
кросс-серверный флоу в e2e: модель сама маршрутизирует запрос через 10
разных серверов и передаёт данные между ними.

### Архитектура

- **`studio/mcp_servers/_mcp_base.py`** — общий каркас едицельных
  stdio-серверов (stdio JSON-RPC 2.0, protocolVersion 2024-11-05, только
  stdlib, паттерн `task_manager.py` дня 17): `run_server(server_name,
  tool, call)` — сервер описывается константой `TOOL` и функцией
  **`call(args) -> (payload: dict, is_error: bool)`**. `initialize`
  (serverInfo `{name, version: "1.0"}`), `tools/list` (ровно 1 тул),
  `tools/call` (чужое имя тула — `isError` «Инструмент не найден»),
  notification без ответа, неизвестный метод — `-32601`, битая JSON-строка
  — `-32700`. Исключение в `call` — `{"error": ...}` + `isError: true`,
  процесс не падает. При старте `sys.stdout`/`sys.stderr` реconfigure'ятся
  с `errors="replace"`: пайп на Windows cp1251, а JSON-RPC
  (`ensure_ascii=False`) может содержать символы вне cp1251 (U+2011,
  эмодзи из реального контента) — без фикса `UnicodeEncodeError` убивал
  MCP-процесс («MCP-сервер закрыл соединение»); тот же паттерн фикса
  дня 18 из `agent.py`.
- **10 едицельных серверов** (все stdio, `[sys.executable, .../<name>.py]`,
  без npx, только stdlib; live-источники деградируют в `isError`, процесс
  не падает):

  | Сервер | Тул | Назначение |
  | --- | --- | --- |
  | `weather` | `get_weather` | Погода Open-Meteo, `city?` (дефолт Самара) |
  | `news` | `get_news` | Новости vc.ru/habr/tproger, `sources?`, top-5, дедуп (collector дня 18) |
  | `digest_make` | `make_digest` | Сбор + сохранение дайджеста (`data/digests/last-digest.json` + `history.json`, кап 96) |
  | `digest_read` | `get_latest_digest` | Чтение последнего дайджеста (локальный файл → фолбэк GitHub API → `isError`) |
  | `task_create` | `create_task` | Создать задачу (file-backed `data/tasks.json`), `title` required |
  | `task_get` | `get_task_details` | Прочитать задачу, `task_id` required |
  | `digest_search` | `search` | Локальный поиск по `data/digests/*.json`, case-insensitive, топ-20, поле `text` для передачи в `summarize` |
  | `digest_summarize` | `summarize` | Детерминированная экстрактивная сводка, `text`, `max_points=8`, **без LLM** |
  | `file_save` | `saveToFile` | Атомарная запись в `data/pipeline/`, `md\|txt\|json\|pdf` (PDF — `pdf_writer` дня 19), basename/traversal-safe |
  | `habr_news` | `get_habr_news` | Новости Habr по темам `testing`/`ai` (word-boundary-фильтр по заголовку: `\bтест\w*\|\bqa\b` / `\b(ai\|ии\|llm\|gpt\|ml)\b\|нейросет\w*` — «акции», «студии», «maintain» не проходят), `topics?`, `limit` (дефолт 10, макс 50), sort по `published` desc |

- **File-backed задачи** (`_tasks_store.py`, `data/tasks.json`, в
  `.gitignore`): задачи `task_create`/`task_get` живут в файле, а не в
  памяти — два разных процесса не видят память друг друга. Сид — задачи
  дня 17: `TASK-42` (`in_progress`) / `TASK-7` (`done`); новая задача —
  `TASK-<max+1>` (первая созданная — `TASK-43`). Атомарная запись
  (tmp + `os.replace`); env `TASKS_FILE` — путь файла (тесты/e2e — tmp).
- **`agent.py`** — маршрутизация:
  - **always-префикс**: имена тулов в LLM-payload ВСЕГДА
    `{slug}__{tool}` (`_llm_tools`), `slug = re.sub(r"[^a-z0-9]+", "_",
    name.lower()).strip("_")` (`_mcp_slug`); логики коллизий нет —
    префикс снимает проблему по построению; `tool_map: llm_name ->
    (server_id, real_tool)` — обратный маршрут;
  - **каталог в system-промпте**: при подключённых серверах за
    `MCP_TOOLS_RULE` идёт `_mcp_catalog_block()` — строки `- {server}
    ({slug}): {tool} — описание (до 120 симв.)`;
  - **кап 15**: `_tool_loop_cap()` читает env `TOOL_LOOP_CAP` на каждый

  - **имена LLM = имена в истории**: assistant-`tool_calls` и
    `role:"tool"`-сообщения хранятся с префиксированными именами —
    следующая итерация цикла и история диалога видят одно и то же имя
    (routing proof: из payload журнала видно, что модель вызывает
    `server__tool`, а не голый `tool`).
- **Реестр: 12 дефолтов + миграция** (`mcp.py`): Firecrawl, Git (npx,

  `Pipeline Tools` удаляются **по имени** (открытые сессии закрываются),

  `GET /api/mcp/tools` — каждая запись дополнена полем
  `server_name` (имя сервера, не только id).
- **UI** (`ChatPanel.tsx`): бейджи MCP-тулов в шапке блока «🧩 Шаги
  агента» рендерят `server · tool` — имя режется по **первому** `__`

## День 21: База знаний (индексация документов + RAG)

### Что это

База знаний Студии поверх дня 20: пайплайн индексации документов —
корпус (доки репозитория + код бэкенда + файлы пользователя),
2 стратегии chunking, 2 эмбеддера, локальный SQLite-индекс с метаданными
и сравнением стратегий, **гибридный поиск** (векторный + лексический
BM25, фузия Reciprocal Rank Fusion) с опциональным **2-м этапом —
реранкером** (cross-encoder `qwen3-reranker-4b`: гибридный recall
top-`rag_recall` → пересчёт пар (query, doc) → top-`rag_top_k`) — и
RAG-инъект в агентский чат: на каждое сообщение пользователя в
system-промпт добавляется блок «База знаний» с top-k релевантными
выдержками (`agent.build_kb_block`, окно выдержки центрируется на
характерном токене запроса), RAG-контекст ответа сохраняется в
assistant-сообщении (инспектор в чате). Управление индексом:
загрузка/удаление файлов, полная очистка (wipe). Тумблеры: RAG
вкл/выкл, реранкер off/api и цикл-агента (MCP-тулы tool-loop дня 17)
вкл/выкл.

Корпус — документы самого репозитория: `README.md`, `RELEASE.md`,

### Архитектура

- **`studio/backend/kb.py`** (новый, stdlib + httpx для API-эмбеддера
  и API-реранкера) — RAG-ядро: `KBError`, `CorpusDoc`, `Chunk`,
  `FixedChunker`, `StructuredChunker`, `HashEmbedder`, `APIEmbedder`,
  `APIReranker`, `search_rag`, `cosine`, `GOLD_QUERIES`,
  `KnowledgeBase`.
- **Сборка корпуса** — 3 источника: `docs` (README.md, RELEASE.md,
  `docs/superpowers/**/*.md`, `openspec/**/*.md`), `code`
  (`studio/backend/*.py`), `upload` (`data/kb/uploads/*`, только
  `UPLOAD_EXTS`).
- **Две стратегии chunking**:
  - **FixedChunker** — фиксированный размер **1200** символов,
    перекрытие **200** (хвост предыдущего чанка = голова следующего);
  - **StructuredChunker** — markdown: секции по заголовкам `#..######`
    (заголовок — в метаданных `section`; текст до первого заголовка —
    «(без заголовка)»); секция длиннее **2400** символов — суб-чанки
    через FixedChunker; не-markdown (код) — целый файл одним чанком,
    длиннее 2400 → суб-чанки.
- **Метаданные чанка** — `{chunk_id, source, file, section, chars,
  text, vector, terms}`; `terms` — dict терм → tf (для BM25-ноги
  поиска; пересчитывается при инкрементальной сборке — апгрейд
  старых индексов без переэмбеддинга); `chunk_id =
  "<stem>-<strategy>-NNNN"` (индекс в пределах файла).
- **Два эмбеддера**:
  - **HashEmbedder** (дефолт) — stdlib: char 3-граммы → `md5` → 256
    бакетов, L2-нормировка; детерминированный (только hashlib —
    встроенный `hash()` salted per-process), офлайн/CI;
  - **APIEmbedder** — GPustack OpenAI-совместимый `POST /embeddings`,
    модель `qwen3-vl-embedding-8b`, dim **4096**, батчи по **16**;
    ключ — новая переменная `.env` `GPUSTACK_KEY_EMBED` (400, если не
    настроен; сбой API при сборке — 502).
- **Индекс-хранилище** — `data/kb/index.db` (SQLite, stdlib sqlite3;
  в `.gitignore`): таблица `meta` (key/value — version, strategy,
  embedder, model, dim, built_at + stats/comparison как JSON) и
  `chunks` (chunk_id, source, file, section, chars, text, vector —
  BLOB float32 little-endian, terms — JSON); одна транзакция на
  полную сборку/миграцию, инкрементальная сборка — INSERT новых
  чанков + UPDATE meta (старые строки не переписываются), удаление —
  DELETE по файлу; авто-миграция из legacy `index.json` при первой
  сборке; активная стратегия — одна (`strategy` в метаданных
  индекса); в
  индексе встроен **сравнительный отчёт** по обеим стратегиям: число
  чанков, среднее/максимальное число символов, hit@3, precision@3, MRR
  по 8 встроенным gold-запросам (`GOLD_QUERIES`, ожидаемый файл — из
  реального корпуса).
- **Поиск — гибридный (вектор + BM25, RRF)**: две ноги, фузия
  Reciprocal Rank Fusion (`score = Σ 1/(60+rank)`):
  - **векторная нога** — косинусная близость top-N (чистый stdlib,
    `cosine`); эмбеддер запроса берётся из индекса (hash — офлайн,
    api — из env);
  - **BM25-нога** — Okapi BM25 (k1=1.5, b=0.75) по `terms` чанков;
    запрос токенизуется (`[a-zа-я0-9]+`, «ё»→«е»), **stopwords
    отбрасываются** (~100 RU/EN служебных слов — иначе частые
    «была/какая» суммой tf обгоняют редкие токены), матчинг — точный
    + substring (короче ≥ 5 симв.) для инфлексий («телефона» ↔
    «телефон»);
  - сбой векторной ноги (например, api-эмбеддер без ключа) —
    деградация на лексический, не ошибка;
  - зачем: скрытый факт в длинном чанке (строка 66 симв. в чанке
    1200) вектором «размывается» до rank 1500+, BM25 с редким токеном
    (idf ~7.6) поднимает его в top-1.
- **2-й этап — реранкер (`APIReranker`)** — опциональный (тумблер
  `reranker: off|api`, дефолт `off`), модель `qwen3-reranker-4b`
  (GPustack, Jina-совместимый `POST /v1/rerank`), ключ
  `GPUSTACK_KEY_RERANK`; **нет ключа или API-сбой — деградация на
  этап 1** (`reranked=false`, лог, не ошибка). Пайплайн
  (`search_rag`): этап 1 — гибридный recall top-`rag_recall`
  (дефолт **50**, 1..200) → cross-encoder считает пары (query, doc):
  документ срезается до **1024** символов, батчи по **16** →
  сортировка по `rerank_score` → top-`top_k`. Ответ
  `/api/kb/search` при `reranked=true`: у результата дополнительно
  `rerank_score` и `stage1_rank` (позиция на этапе 1), наверху —
  `recall_total` и `reranked`. **Live-факт дня 21**: иголка в
  длинном чанке cross-encoder'ом не всегда поднимается (пасхалка
  66 симв. в чанке 1200: этап 1 №2 → после реранкера №10; слово
  «модель» в запросе буквально матчит спека «модель вызывает
  инструмент») — этап 1 находит редкий токен, реранкер —
  precision-слой для общих запросов.
- **RAG** (`agent.py`) — `StudioAgent(..., kb=None)`; поиск —
  2-этапный (`search_rag`, тумблеры `reranker`/`rag_recall` из
  settings), top-k (настройка `rag_top_k`, дефолт **3**) выдержек,
  `build_kb_block` — блок в system-промпт на каждый пользовательский
  запрос (с указанием источника `file · section`); **RAG-контекст
  ответа** (`rag_context`: `query`, `reranked`, `recall_total`,
  `chunks`) сохраняется в assistant-сообщении (в LLM-пейлоад не
  уходит — в пейлоад только блок в system-промпте), фронтенд
  рендерит его инспектором под сообщением; нет индекса / сбой
  поиска / нет результатов — блок пуст, **чат не ломается** (только
  лог `[KB]`).
- **Окно выдержки** (`agent._focus_snippet`) — чанк может быть
  длиннее 300 символов, и слепой срез `text[:300]` «утоняет» факт в
  середине чанка (пасхалка 66 симв. на 1200 — LLM «не видела» и
  отвечала, что телефона не было). Окно 300 символов центрируется на
  первом вхождении самого дискриминативного (длинейшего)
  некратного токена запроса, инфлексия срезается (до 2 симв. —
  «телефона» → «телефон»); токен не найден — первые 300, как раньше.
- **Тумблеры** — `data/kb/settings.json` (в `.gitignore`), дефолты
  `{agent_loop: true, rag: true, rag_top_k: 3, strategy: "structural",
  embedder: "hash", reranker: "off", rag_recall: 50}`; читаются
  **на каждый запрос**. `rag=false` — без RAG-блока;
  `agent_loop=false` — в LLM-payload нет `tools` и нет tool-loop
  (один LLM-вызов, паттерн дня 16 «без MCP-серверов»), MCP-каталог
  дня 20 не инжектится; `reranker=api` — 2-й этап поиска
  (cross-encoder), `rag_recall` — глубина recall на этапе 1
  (1..200).
- **`main.py`** — `create_app(agent, kb)` (DI для тестов) + 8
  маршрутов `/api/kb/*` (400/404/409/502 с RU-detail, паттерн дня 11).
- **Фронтенд** — KB-хелперы в `api.ts` (+`KbReranker`, `RagContext`,
  `reranker`/`rag_recall` в `KbSettings`), `KbTab.tsx` (select
  реранкера + recall, поиск с чипами score/`stage1_rank`), вкладка
  «База знаний» в `ContextPanel` (состояние — `'kb'`),
  `RagContextInspector` в `ChatPanel.tsx` (RAG-контекст под
  assistant-сообщением), стили.
- **Зависимости** — `requirements.txt`: + `python-multipart`
  (multipart-upload).

### API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/kb/stats` | Статистика индекса: strategy, embedder, dim, built_at, stats (docs/files/chunks/chars/corpus_words/build_ms), comparison, files, `reranker_key_configured` (настроен ли `GPUSTACK_KEY_RERANK`); 404 — «Индекс не построен» |
| GET | `/api/kb/uploads` | Список загруженных файлов (data/kb/uploads) — работает без индекса: {uploads: [{name, size}]} |
| POST | `/api/kb/index` | Построить индекс `{strategy: fixed\|structural, embedder: hash\|api}` → `{stats, comparison, strategy}`; 400 — некорректные значения / нет ключа `GPUSTACK_KEY_EMBED`, 502 — сбой эмбеддинг-API |
| POST | `/api/kb/upload` | Загрузить файл в `data/kb/uploads/` (multipart, поле `file`): whitelist `UPLOAD_EXTS`, имя — только basename (traversal-safe) → `{ok, file, size}`; 400 — неподдерживаемый формат |
| GET | `/api/kb/search?q=&k=5` | 2-этапный top-k: этап 1 — гибридный (вектор + BM25, RRF) top-`rag_recall`, этап 2 — cross-encoder (если `reranker=api`) → `{results: [{chunk_id, source, file, section, score, text, + rerank_score, stage1_rank}], recall_total, reranked}`; 400 — пустой q / сбой БЗ, 404 — индекс не построен |
| DELETE | `/api/kb/uploads/{name}` | Удалить загруженный файл: с диска + его чанки из индекса + stats (incremental); 400 — basename-гард, 404 — файла нет в uploads, 409 — идёт сборка |
| DELETE | `/api/kb` | Очистить базу: все uploads + `index.db` (settings сохраняются); 409 — идёт сборка |
| GET / POST | `/api/kb/settings` | Настройки БЗ `{agent_loop, rag, rag_top_k, strategy, embedder, reranker, rag_recall}` / частичное обновление с валидацией (лишние ключи игнорируются); 400 — RU-detail (`rag_top_k` 1..10, bool-тумблеры, `strategy: fixed\|structural`, `embedder: hash\|api`, `reranker: off\|api`, `rag_recall` 1..200) |

  среднее/макс. символов, hit@3, precision@3, MRR; активная стратегия
  подсвечена;
- **«Поиск по базе»**: поле запроса → top-5 результатов (чип score
  с цветом 🟢 ≥0.8 / 🟡 0.5–0.8 / 🔴 <0.5 + `file · section` +

  «из #N» (позиция на этапе 1) с 🚨 при `stage1_rank > 20`);
- **RAG-контекст в чате** (`RagContextInspector`): под
  assistant-сообщением с непустыми `rag_context.chunks` — блок с
  чанками (`file · section` + отрывок), score (та же цветовая шкала),
  «(Reranked из #N)» + 🚨 при `stage1_rank > 20`; служебное поле
  сообщения — в LLM-пейлоад не уходит.

- **Сравнение двух стратегий** — отчёт в индексе (чанки, avg/max

  0.25** — structural-чанки больше и их меньше (целостность секции),
  на этом gold-наборе по метрикам поиска впереди fixed; сравнительная
  таблица — то, что видит пользователь после индексации.
- **Гибридный поиск** — векторная нога (косинус) + BM25-нога
  (stopwords, substring-инфлексии) с фузией RRF; live-доказательство:

- **RAG в агентском чате** — top-k выдержек (окно ≤ 300 символов,

## День 22: Первый RAG-запрос

### Что это

Первый RAG-запрос поверх базы знаний дня 21: студия отвечает на вопрос
**двумя способами (без RAG и с RAG) в одном HTTP-вызове**
(`POST /api/rag/compare`) и показывает оба ответа рядом в UI (секция
«Сравнение RAG» во вкладке «База знаний»). Эндпоинт делает оба
LLM-вызова сам: **T=0, max_tokens=1024 (пин, не из конфига)**,
симметричный голый system-промпт (`config.system_prompt` как есть —
без памяти, профиля и инвариантов); у RAG-руки к промпту
добавляется блок «База знаний» из `kb.search_rag` (recall top-50 →
cross-encoder top-3). Тумблер `rag` из settings **не consulted** —
сравнение явное, обе руки всегда. Сбой одной руки не роняет вторую:
ответ сбойной руки — строка «Ошибка: …» (статус остаётся 200).
Корпус — 5-книжный каталог (`scripts/fetch_books.py`, stdlib):
Пушкин «Евгений Онегин», Чехов «Вишнёвый сад», Толстой «Война и мир»
(том 1), Гоголь «Мёртвые души», Чехов «Дама с собачкой» (seed-копия
34KB) — primary-источник → fallback → committed seed-корпус при
полном провале сети.

```
вопрос

  детерминированный O(len)) — «телфон» ↔ «телефон» матчит в обе
  стороны. Точное совпадение, substring-инфлексии (`_SUBSTR_MIN`,
  «телефона» ↔ «телефон»), короткие термы (< 5 симв.) и max-tf
  семантика (несколько матчей — максимум tf) не изменены.

      этап 1: гибридный recall top-rag_recall (вектор + BM25, RRF)
      [этап 2: cross-encoder, если reranker=api]
      → отсечение по min_score (только при > 0): после оценки, до [:top_k]
          reranked:     rerank_score >= min_score
          без реранка:  score >= min_score * best   (относительное)
      → срез top_k
  → agent.rag_compare(question, min_score?)
      5 non-stream LLM-вызовов (T=0, _task_llm_call, requests.json не пишется):
          plain(0) → rag(1) → rag+filter(2) → rewrite(3, mt=200)
          → rag+rewrite(4, mt=1024, отвечает на ОРИГИНАЛЬНЫЙ вопрос)
  → ответ: 13 полей (5 дня 22 + 8 аддитивных)
```

- **Позиция отсечения** (`kb.search_rag`, одна точка): после stage1
  (и после сортировки реранка, если он сработал) и до среза `[:top_k]`.
  До реранка отсекать нельзя (реранкер пересматривает оценки, порог по
  устаревшим счётам уберёт то, что cross-encoder признал бы
  релевантным); после top_k-среза тоже нельзя: задание «топ-K до и
  после фильтрации» требует, чтобы top_k выбирался из прошедших порог.
- **Семантика `min_score`**:
  - `0.0` (дефолт) = off: поведение байт-в-байт как до дня 23 (полю
    `filtered`/`dropped` вообще не добавляются, регрессия закреплена
    снимком-сравнением списков);
  - `reranker=api` → `rerank_score >= min_score` (шкала cross-encoder
    0..1, абсолютная);
  - `reranker=off` (или реранк деградировал на stage1) →
    `score >= min_score * best` (best = максимум RRF-счёта stage1;
    сырой RRF = Σ 1/(60+rank) ≈ 0.003..0.033 несовместим с абсолютной
    шкалой 0..1, поэтому относительная нормализация); guard:
    `best == 0` → пустой список, деления нет;
  - семантика `>=`: `min_score = 1.0` оставляет результат с
    максимальной оценкой.
- **Консистентность**: фильтр действует на всех 3 потребителя
  `search_rag` (live-чат `_rag_retrieve`, `GET /api/kb/search`,
  `rag_compare`) из одних и тех же settings.
- **4 армы** (`agent.rag_compare`): plain (голый system-промпт) и rag
  (промпт + блок «База знаний») НИКОГДА не фильтруют, даже при
  заданном `min_score` (контрольные руки); rag+filter — retrieval с
  `min_score` (body-override, иначе settings); rag+rewrite — retrieval
  на перефразе, ANSWER-LLM отвечает на **оригинальный** вопрос
  (kb_block рендерится с оригинальным вопросом, окно выдержки под него).
  Порядок LLM-вызовов: plain → rag → filter → rewrite (T=0,
  max_tokens=200) → rewrite-arm (T=0, max_tokens=1024); rewrite-вызов
  поставлен после первой тройки рук, чтобы captured[0..1] остались
  plain/rag (контракт захвата e2e).
- **`rewrite_query`** (`agent.py`): один non-stream вызов, T=0,
  max_tokens=200, RU-system-промпт «одним предложением, ключевыми
  словами, без приветствий»; `(rewritten, True)` только при непустом и
  не-идентичном (case-insensitive) ответе; пустой/идентичный/исключение
  → `(question, False)` + log warning, наружу не «Ошибка:». Вызывается
  только из rewrite-армы; из `ask_stream` никогда (guardrail-тест).
- **Деградация**: сбой rewrite → rewrite-арма отвечает на оригинале
  (`rewrite_applied=false`, `rewritten_query` = оригинал, рука не
  «Ошибка:»); реранкер down при `min_score > 0` → фильтр не отключается,
  переходит в relative-режим на stage1-счётах; всё отфильтровано (напр.
  0.999) → 200, `chunks_rag_filter == []`, пустой kb_block, непустой
  ответ без контекста («не знаю по базе» — честный ответ, не ошибка).
- **Валидация** (settings и compare-body, одна логика): bool ПЕРВЫМ
  (Python-ловушка `isinstance(True, int)`), затем `int/float` и
  диапазон 0..1, строк-чисел нет → 400 RU «min_score должен быть
  числом от 0 до 1».

## День 25: Мини-чат с RAG + памятью задачи (production-like)

### Что это

Мини-чат (production-like) поверх Студии: чат хранит историю диалога
(ST, день 11), при каждом новом вопросе ищет контекст в базе через
RAG (дни 21–23: гибридный поиск + реранкер + `min_score`), отвечает с
учётом найденной информации (блок «База знаний» + CITE_RULE, день 24)
и **всегда выводит источники** (`rag_context` + панель «📖 Источники
и цитаты», dont-know при 0 чанков). Усиление — **память задачи
(task state)**: что пользователь уже уточнил, какие ограничения/термины
зафиксированы, какова цель диалога. Проверка задания — 2 длинных
сценария по 10–15 сообщений (e2e Part C): ассистент не теряет цель и
продолжает выдавать ответы с источниками.

### Архитектура

- **Хранение** (`memory.py`) — `task_state` в записи диалога
  (`dialogues.json`): `{goal: str, clarifications: [str],
  constraints: [str]}`; `get_task_state` / `update_task_state`
  (целое состояние, валидация 400-формы) + `_task_state_of`
  (бэкворд-совместимость: старой записи без поля — пустое состояние);
  новое поле у `new_dialogue`, отдаётся `GET /api/dialogues` и
  `GET /api/dialogues/{id}`.
- **Инъекция** (`agent.build_task_memory_block`) — блок «Память задачи
  (день 25)» в system-промпт на каждый запрос: `Цель диалога: …` +
  «Уточнения пользователя» + «Зафиксированные ограничения и термины» +
  инструкция «Не теряй цель диалога: учитывай её и ограничения в
  каждом ответе»; пустое состояние — блок не добавляется. (Не
  коллидирует с методом дня 13 `build_task_state_block(t, stage, ...)`
  — блок task-машины для stage-агентов, другое имя.)
- **Авто-обновление** (`agent._update_task_state`) — после хода один
  non-stream LLM-вызов (T=0, max_tokens=600,
  `enable_thinking: false`, паттерн авто-заголовка дня 11; НЕ в журнал
  `requests.json`): по хвосту диалога (последние 12 user/assistant,
  без task-/tool-маркеров; < 2 сообщений — skip) извлекает
  goal/clarifications/constraints с учётом предыдущей памяти (best-effort
  JSON; лимит 10 пунктов на список). Любой сбой — состояние не
  меняется, чат не затрагивается. Текущая память возвращается в SSE
  `done` (`done["task_state"]`) — фронтенд синхронизирует вкладку без
  перечитывания.
- **UI** — `TaskStateTab.tsx` (новый): 5-я вкладка «Задача» в панели
  «Контекст» (`ContextPanel.tsx`) — цель (textarea) + два списка
  (уточнения / ограничения), ручное сохранение
  (`POST .../task-state`) + автосинхронизация по `done.task_state`;
  `api.ts` — тип `TaskMemoryState` + хелперы.
- **RAG-часть** — не меняется (дни 21–24): retrieval → блок «База
  знаний» + `CITE_RULE` → ответ → `rag_context` с источниками и

2. **Retrieval** — эмбеддинг запроса **локально**: `nomic-embed-text:v1.5`
   (768 dim) через OpenAI-совместимый `POST {OLLAMA_BASE_URL}/embeddings`.
3. **Генерация** — **локальная** LLM (Ollama), как в дне 26.

Разрыв был ровно в эмбеддере: `hash` локален, но 256-мерный char-3-gram
md5 не различает смысл; `api` семантичен, но требует GPustack и ключ.
День 28 добавляет третий эмбеддер `ollama` — **не замену**, а соседа
существующих.

### Архитектура

| `embedder` | Модель | Где считает | Нужен ключ |
|---|---|---|---|
| `hash` | — (char 3-gram md5, 256 dim) | локально, детерминированно | нет |
| `api` | `qwen3-vl-embedding-8b` | GPustack (сеть) | `GPUSTACK_KEY_EMBED` |
| `ollama` | `nomic-embed-text:v1.5` (768 dim) | локально (Ollama) | нет |

Два решения, которые стоит отметить:

- **Модель для поиска берётся ИЗ ИНДЕКСА, а не из env.**
  `_embedder_from_index` строит эмбеддер на `idx["model"]`: векторная
  нога считает `cosine(qv, chunk_vector)`, и если запрос посчитать
  другой моделью, косинус бессмыслен — поиск деградирует молча.
  `OLLAMA_EMBED_MODEL` описывает модель для **новой сборки**; поиск по
  уже собранному индексу следует индексу.
- **Недоступная Ollama — 502, а не тихий фолбэк на `hash`.** Подмена
  эмбеддера дала бы индекс с несравнимыми векторами и расхождение
  `embedder`/`dim` в meta с реальностью. Молчаливо сломанный RAG хуже
  явной ошибки.

Смена эмбеддера — другой индекс: существующее правило дня 21
(`mode: "auto"` → инкремент только при совпадении strategy+embedder)
пересобирает индекс полностью.

### 1. Параметры

* **`temperature` 0.7 → 0.2.** Рекомендация — выбор из списка, а не
  свободное творчество: нужна воспроизводимость и верность каталогу.
* **`max_tokens` 2048 → 512.** Ответ — 3–5 коротких JSON-объектов;
  2048 только добавляют латентность (4495 → 3887 токенов на 20 кейсов).
* **`num_ctx` — 8192 явно.** До дня 29 context window не задавался
  вообще: Ollama брала авто-размер по видеопамяти (**32768** на этой
  машине) и выделяла KV-кэш под всё окно сразу.
* **`seed=29`** — воспроизводимость замеров.

**Context window требует нативного API.** Проверено на Ollama 0.34.4:
OpenAI-совместимый `/v1/chat/completions` **игнорирует `num_ctx`** — и в
корне тела, и внутри `options`. Поэтому профиль с окном идёт нативным
`/api/chat` (`options.num_ctx`), а профиль без окна — прежним путём
(регрессия дней 11–28). Проверка:

```bash
python scripts/e2e_day29.py    # B1: CONTEXT == num_ctx профиля
ollama ps                      # колонка CONTEXT: было 32768, стало 8192
```

Модели **неравны по цене контекста в 8 раз** — формула
`KV = 2 × слои × KV-голов × head_dim × токены × байты` даёт на
`num_ctx=8192`: `qwen3-coder:30b` — **0.75 ГиБ** (4 KV-головы),
`gemma3:27b` — 3.88 ГиБ (16), `glm-4.7-flash` — 7.34 ГиБ (20). Это и
есть главный аргумент выбрать `qwen3-coder` основной моделью кейса.

### 2. Квантование

Квантование измерено двумя способами.

**Сравнение семейств на одном кванте (`Q4_K_M`)** — одинаковый профиль,
один промпт, одни кандидаты, один seed:

| Модель | Квант | Формат | Ограничения | Латентность p50 | Токены/с |
|---|---|---|---|---|---|
| `qwen3-coder:30b` (MoE) | Q4_K_M | 100 % | 99 % | **3.38 с** | **65.7** |
| `glm-4.7-flash` (MoE+reasoning) | Q4_K_M | 100 % | 100 % | 5.95 с | 41.2 |
| `gemma3:27b` (плотная) | Q4_K_M | 100 % | 98 % | 18.45 с | 12.6 |

Вывод: `qwen3-coder` выигрывает по скорости в **5.5 раза** у `gemma3:27b`
при том же качестве — MoE-архитектура (3B активных параметров) и в 8 раз
более дешёвый KV-кэш. «Больше параметров» ≠ «лучше для задачи».

**A/B одной модели по кванту** — профили `series_q4` (`gemma3:4b`,
Q4_K_M) и `series_q8` (`gemma3:4b-it-q8_0`), отличаются **только**
квантом:

```bash
ollama pull gemma3:4b-it-q8_0     # ~5 ГБ
python scripts/series_eval.py --profiles series_q4,series_q8
```

Ожидание из литературы: Q4_K_M ≈ +0.9 % перплексии к F16 при ~29 %
размера, Q8_0 ≈ +0.2 %, но **медленнее** (bandwidth-bound: 50.9 против
71.9 т/с в бенчмарке llama.cpp) — то есть на задаче рекомендаций
выигрыш Q8_0 может лежать в пределах шума, а цена — вдвое больше
памяти. ⚠️ В этом окружении скачать Q8_0 не удалось (реестр Ollama
отдавал 503, загрузка 29-ГБ модели оборвалась на 28.7 ГБ из-за
нестабильного DNS) — A/B-пара заведена и протестирована, но цифры по
ней не сняты; это отмечено честно, а не подменено оценкой.

### 3. Prompt-шаблон

`SERIES_SYSTEM_PROMPT` вместо «ассистента Студии» задаёт роль эксперта по
сериалам, четыре жёстких правила, требование формата JSON и few-shot
пример. Ключевые приёмы:

* **Модель возвращает только `id` и `why`**, а название, год, жанры и
  IMDb подставляются **из каталога на сервере** — выдуманное название
  невозможно в принципе, а выдуманный `id` ловится проверкой
  (`hallucination_rate`).
* **Явная лазейка «вернуть пустой список»** — без неё модель,
  вынужденная выбирать, придумывает подходящий сериал. Проверяется
  кейсами `g18–g20`: профиль `series` честно вернул пусто на всех трёх
  (`empty_honesty` = 100 %).
* **Каталог и правила по краям промпта** (lost-in-the-middle).

### Находка: reasoning-модели возвращают пустой ответ

Замер вскрыл проблему, невидимую «на глаз»: профиль на
`glm-4.7-flash` дал **0 рекомендаций на всех 20 кейсах** — при HTTP 200
и `eval_count` ≈ 512. Причина: модель пишет цепочку рассуждений в
**отдельное поле `thinking`**, и если бюджет `num_predict` израсходован
на размышления, поле `content` остаётся пустым.

```bash
# без флага: content пуст, 100 токенов ушли в thinking
content: ''   thinking: '1. **Analyze the user...'   eval_count: 100
# с think=false: ответ есть, 4 токена вместо 100
content: 'Привет.'                                     eval_count: 4
```

Лечение — `think=False` в нативном запросе (в OpenAI-совместимом API
такого ключа нет). После фикса профиль `series_glm` даёт **100 %
формата и 100 % соблюдения ограничений**. Вывод: оптимизация параметров
обязана включать отключение размышления для reasoning-моделей.

## День 30: Локальная LLM как приватный сетевой сервис

### Задание и что сделано

День 30 просит развернуть локальную LLM как **сервис, к которому можно
подключиться с любого устройства по сети**, с ограничениями по
**rate limit** и **max context**. Сделано и проверено на живой Ollama.

Ключевая идея: **Ollama остаётся на loopback** (`127.0.0.1:11434`), а
наружу — в локальную сеть — смотрит только **шлюз**
(`studio/backend/gateway.py`). Если открыть Ollama в LAN напрямую,
лимитов не будет ни у кого: любое устройство в сети сможет
бесконтрольно занимать GPU и память под произвольный контекст. Шлюз —
единственная точка, где есть **ключи**, **лимиты** и **учёт**.

```
  ноутбук / телефон / планшет         (любое устройство в LAN)
        │  OpenAI-совместимый HTTP + Bearer <ключ клиента>
        ▼
  ┌──────────────────────────────────────────────┐
  │  Шлюз  (FastAPI Студии, слушает 0.0.0.0)     │
  │  1. аутентификация  → ключ → клиент          │
  │  2. allow_models    → модель разрешена?      │
  │  3. rate limit      → RPM / TPM (окно)       │
  │  4. подсчёт входа   → токены промпта         │
  │  5. max_context     → влезает?               │
  │       ├─ да  → как есть                      │
  │       └─ нет → LLM-сводка старых ходов       │
  │  6. прокси          → Ollama                 │
  │  7. учёт            → токены, запросы, отказ │
  └──────────────────────────────────────────────┘
        │  http://127.0.0.1:11434
        ▼
     Ollama (наружу не смотрит)
```

Сервис **OpenAI-совместимый**: подключается любой клиент (curl,
Python `openai`, Continue, LobeChat, телефонные приложения) — достаточно
указать base_url и ключ. Правок на стороне клиента не требуется.

### Подключение с другого устройства

### 1. Ограничения: что именно лимитируется

| Лимит | Где | Поведение |
|---|---|---|
| `rpm` | на клиента | запросов в минуту → **429** + `Retry-After` |
| `tpm` | на клиента | токенов (вход+выход) в минуту → 429 |
| `max_context` | на клиента | триггер **компрессии**, затем 413 |
| `max_output_tokens` | на клиента | жёсткий потолок ответа (перебивает запрос) |
| `allow_models` | на клиента | пусто = все; поддерживается маска `gemma3:*` |
| `enabled` | на клиента | выключить, не удаляя ключ |

Значение `0` у любого лимита означает «без лимита».

**Окно — скользящее, а не «фиксированная минута».** Фиксированная
минута даёт двойной залп на стыке (клиент шлёт `rpm` запросов в 59.9 с
и ещё столько же в 60.1 с) — типовая ошибка лимитеров. Отказ окно **не
расходует**: иначе клиент блокировал бы себя собственными повторами.

**Лимит нельзя обойти через `stream: true`.** Конвейер (аутентификация,
лимиты, компрессия) выполняется до первого байта потока, поэтому
стриминговый и обычный пути лимитируются одинаково, а ошибка приходит
обычным JSON (клиент видит причину, а не оборванный SSE).

### 2. Max context: компрессия вместо отказа

Задание допускает трактовать «max context» как жёсткий отказ, но это
ломает главный сценарий — **длинный диалог с телефона**: клиент не умеет
сжимать историю сам, и вместо ответа пользователь получил бы стену 400.

Поэтому лимит — не стена, а **триггер компрессии**:

| Ситуация | Поведение |
|---|---|
| вход ≤ `max_context` | запрос уходит **бит-в-бит**, компрессии нет |
| вход > `max_context` | старые ходы → **LLM-сводка**; system-промпт и последние ходы целиком |
| хвост сам больше лимита | хвост сокращается, но **последний вопрос пользователя сохраняется всегда** |
| после всего всё ещё > лимита | **413** с точными числами (никакой молчаливой обрезки) |

Компрессия **видна клиенту** — в ответе блок `gateway` и заголовки:

```json
"gateway": {
  "client": "phone", "compressed": true, "compress_rounds": 1,
  "messages_before": 21, "messages_after": 5,
  "tokens_before_compression": 1638, "tokens_after_compression": 440,
  "max_context": 500, "tokens_in": 11, "tokens_out": 6,
  "latency_sec": 0.168, "limits": {"rpm": 3, "tpm": 20000}
}
```

```
x-gateway-client: phone
x-gateway-compressed: true
x-gateway-max-context: 500
```

Сводка формулируется так, чтобы **не терять факты молча**: промпт
требует сохранить цель, ограничения, решения, имена, числа и
технические детали, отбросив любезности и воду. Сводка инжектится
отдельным `system`-сообщением с пометкой `[СЖАТАЯ ИСТОРИЯ ДИАЛОГА]` —
модель не путает её с текущим запросом.

### 3. Находка: reasoning-модели ломают сводку

Проверено на живой Ollama 0.34.4 (M3 Max, 48 ГБ).
`glm-4.7-flash:q4_K_M` (MoE + reasoning) на служебном вызове сводки:

* через OpenAI-совместимый `/v1/chat/completions` отдаёт `content: ""`,
  а весь текст уходит в поле `reasoning` — бюджет `max_tokens` потрачен
  на размышления;
* на большом контексте падает **HTTP 500** на нативном `/api/chat`
  при `num_predict: 2048`.

`qwen3-coder:30b` на том же входе отдаёт готовую сводку (743 символа)
сразу — что согласуется с замером дня 29.

**Решение:** сводка идёт **цепочкой моделей × два пути вызова**
(`_summary_models` × `_summary_attempts`): сначала модель, выбранная для
диалога (она уже прогрета в VRAM — дешевле всего), затем
`DEFAULT_SUMMARY_PREFERENCE` (`qwen3-coder:30b`, `gemma3:27b`), затем
остальные локальные (эмбеддеры исключены). Итог — первый непустой ответ;
если всё пусто, компрессия деградирует и шлюз честно отдаёт 413.

### 4. Находка: пустой ответ модели — наблюдаемое событие

Та же reasoning-модель на **обычном** запросе с малым
`max_output_tokens` возвращает пустой `content` и
`finish_reason: length` — бюджет кончился на рассуждениях. Клиент
получал пустую строку без объяснения. Теперь шлюз помечает это явно:

```json
"gateway": {
  "empty_response": true,
  "finish_reason": "length",
  "reasoning_chars": 783,
  "empty_reason": "Модель израсходовала бюджет ответа на рассуждения
                   (finish_reason=length). Увеличьте max_output_tokens
                   клиента «phone» (сейчас 16) или выберите модель без
                   режима рассуждений."
}
```

### 5. Ключи клиентов

* Ключ генерируется шлюзом (`sk-local-<32 hex>`, 128 бит энтропии).
* Показывается **один раз** — при создании или явном повороте
  (`rotate_key`). Восстановить его невозможно.
* На диске (`studio/data/gateway.json`) хранится **только SHA-256**;
  сравнение — `hmac.compare_digest` (не течет по времени).
* В API и UI ключ всегда маскирован: `sk-local-…bd58`.
* Дефолтный клиент создаётся из `.env` (`GATEWAY_CLIENT_KEY`) при первом
  запуске, поэтому сервис доступен сразу.

Конфигурация клиентов перечитывается **без рестарта** процесса.

### Найденный и исправленный баг: панель не убиралась

Первая версия адаптива **не работала на телефоне**: сайдбар оставался
статичным и перекрывал чат, войти в диалог было нельзя.

Причина — не в media-запросе, а в конфликте с базовой анимацией.
Базовое правило `.panel` вешает `animation: panel-in ... both`, а
`@keyframes panel-in` заканчивается на `transform: none`. CSS-анимации
имеют приоритет над обычными объявлениями, поэтому
`transform: translateX(-105%)` в мобильном блоке **игнорировался** —
панель оставалась на месте.

Исправление: в мобильном блоке добавлен явный сброс `animation: none`
для `.sidebar` (и для `.chat`, которому анимация на весь экран не
нужна), плюс закреплён `overflow-y: auto` для скролла внутри оверлея.

Проверено замером геометрии в реальном браузере (Chrome DevTools
Protocol, viewport 390×844), а не только чтением CSS:

| Момент | `sidebar.getBoundingClientRect().x` | Класс `mobile-open` |
|---|---|---|
| до клика | **−336** (за экраном, `animation: none`) | нет |
| после кнопки ☰ | **0** (панель видна) | да |
| после тапа по фону | **−336** | нет |

Урок: правила внутри `@media` не гарантируют результат, если базовое
правило анимирует то же свойство с `fill-mode: both`.

### Безопасность

**Сервис предназначен только для доверенной локальной сети.** TLS не
поднимается: трафик и ключ идут по HTTP открытым текстом. Это осознанный
скоуп дня; наружу (в интернет) сервис не выставляется. Что при этом
защищено: без ключа — 401, ключ не хранится на диске, лимиты не дают
одному устройству занять GPU, а Ollama недоступна из сети напрямую.

| Слой | Что уже было | Почему не хватало |
|---|---|---|
| RAG (дни 21–24, 28) | гибридный поиск, реранкер, цитаты | корпус — только `data/kb/uploads`; документации и кода проекта в индексе **нет** |
| MCP (дни 16–20) | 10 серверов, tool-loop | работает **только из чата**; git-ветку и diff так не получить |
| Агент (дни 12–15, 25) | профили, инварианты, память задачи | умеет **отвечать**, но не менять файлы |
| Шлюз (день 30) | сетевой доступ к LLM | это про инференс, а не про работу с проектом |

Разрыв ровно один: **нет слоя, который читает проект (документацию и
код), сопоставляет изменения с контекстом и пишет результат обратно в
файлы**. Его закрывает `studio/backend/assistant.py`.

### Решение 1: отдельный индекс проекта, а не общий корпус

Соблазн — дописать документацию и код в существующий `data/kb/index.db`
дня 21. Это **неверно**, и вот почему конкретно:

* поиск по пользовательским документам начал бы выдавать чанки кода
  проекта — мусор в ответах чата;
* пересборка индекса проекта **стирала бы загрузки пользователя**;
* статистика дня 21 («сколько документов») стала бы бессмысленной.

Поэтому — **второй индекс** `data/kb/project.db` (каталог
`data/kb/project/`). `ProjectKnowledgeBase` наследует `KnowledgeBase` и
переопределяет только `corpus_files` — `kb.py` не форкается, весь
пайплайн дня 21 (chunking, эмбеддеры, SQLite, гибридный поиск, RRF)
переиспользуется как есть. Изоляция проверяется в e2e (A2): файл
`data/kb/index.db` побайтово не изменяется при сборке индекса проекта.

### Решение 2: корпус собирается явными правилами

Индексировать репозиторий целиком нельзя: `.venv` — десятки тысяч
файлов, плюс `node_modules`, `.git`, `data/kb/index.db` (бинарный),
`__pycache__`. Корпус задаётся правилами (`CORPUS_RULES`) с жёсткими
исключениями (`EXCLUDE_DIRS`, `EXCLUDE_SUFFIXES`, `MAX_FILE_BYTES` =
400 КБ), причём исключённые каталоги обрезаются **прямо в `os.walk`** —
иначе `.venv` всё равно обходится и сборка встаёт.

Результат на реальном репозитории:

| Источник | Файлов | Что входит |
|---|---|---|
| `docs` | 15 | README, RELEASE, LINKS, `docs/**` |
| `spec` | 88 | `openspec/**` (спеки, proposal, design, tasks) |
| `code` | 106 | `studio/backend/**`, `studio/frontend/src/**`, `scripts/*.py` |
| **итого** | **209** | 4234 чанка; `.venv`/`node_modules`/`data` — **0** |

### Решение 3: ревью — факты собирает код, LLM только формулирует

Ревью целиком на LLM — плохая идея: модель выдумывает номера строк и
«находит» то, чего в diff нет. Поэтому разделены обязанности:

| Слой | Кто делает | Что даёт |
|---|---|---|
| Разбор diff | код (`parse_unified_diff`) | файлы, ханки, `+`/`−` строки, номера строк в новой версии |
| 7 проверок | код (`check_diff`) | `secret`, `bare_except`, `print_call`, `long_line`, `todo`, `missing_test`, `missing_docs` |
| Сопоставление с доками | индекс (RAG) | какие документы затрагивает изменение |
| Нарратив | LLM (опционально) | связный текст рекомендаций |

Каждая находка несёт **доказательство** (файл + номер строки) и severity:

```
[OK] A6 ревью diff: правила=['bare_except','missing_docs','missing_test','secret'],
     secret в studio/backend/mod.py:3, severity={'high': 2, 'medium': 2, 'low': 0}
```

Без LLM отчёт полностью работоспособен — это проверяется Part A e2e
(офлайн, без сети). Ревью, которое не работает без модели, бесполезно
именно тогда, когда нужно.

### Решение 4: поддержка — данные CRM меняют ответ, и это видно

`TicketStore` читает `data/crm/users.json` и `tickets.json`, связывает
тикет с пользователем и его историей обращений. Эти факты инжектятся в
промпт, и персонализация **наблюдаема** — в ответе есть блок
`context.applied`:

```
[OK] A9 поддержка: персонализация из CRM — тикет T-5003, план=free,
     применено: ['план: free', 'статус оплаты: failed', 'роль: user', 'канал: email']
```

Неизвестный тикет не выдумывает данные: `found: false`, `user: null`,
`applied: ['тикет не найден — ответ общий, без персонализации']`.

### Решение 5: сценарии — цель, а не пошаговая инструкция

Задание требует работать «на уровне целей, а не пошаговых инструкций».
Пользователь говорит **что нужно** («проверь соответствие кода
правилам»), а не **как** («прочитай файл X, найди строку Y»). Сценарий
сам решает, что читать и куда писать. Реализовано **пять** (задание
просит минимум два):

| Сценарий | Автономные действия |
|---|---|
| `find_usages` | обход корпуса (код + доки), поиск вхождений как **отдельного слова** (чтобы `search` не матчился в `searcher`), группировка по файлам с номерами строк |
| `update_docs` | чтение git-diff → определение затронутых модулей → правка секции README между маркерами (идемпотентно: повторный запуск не дублирует) |
| `generate` | ADR с автонумерацией по существующим и **транслитерацией** кириллического заголовка; changelog из git-лога; README-заготовка |
| `check_invariants` | проверка файлов проекта на правила (ML-зависимости, тегированный лог, docstring) |
| `diff_report` | подготовка unified-diff отчёта: сохранение в файл **или** возврат без записи |

Пример: `find_usages` по реальному символу проекта нашёл 22 вхождения в
5 файлах, включая `gateway.py` и `test_gateway.py`.

### Решение 6: безопасность записи и отсутствие git-мутаций

Сценарии пишут **только** в allow-list (`README.md`, `CHANGELOG.md`,
`docs/`, `openspec/`) и **только** внутрь проекта. Отвергаются:
абсолютный путь, выход через `..`, путь в код бэкенда, путь в `data/`,
симлинк наружу. Проверено e2e A16 — 4 вектора атаки → HTTP 400, файл
вне проекта не создан:

```
[OK] A16 запись вне allow-list отвергнута — 4 вектора → 400, файл вне проекта не создан
```

Запись атомарна (временный файл + `os.replace`). **Git-мутаций нет
вообще**: ассистент читает `git status`/`diff`/`log` и пишет файлы в
рабочее дерево, а коммит остаётся за человеком — та же логика
human-gate, что в plan-review дня 15. Тест `test_never_mutates`
проверяет отсутствие `commit`/`push`/`checkout`/`reset` в модуле.

### Находки живой проверки

Всё ниже найдено прогоном e2e и реальных тестов, а не выведено
умозрительно. Семь находок — и шесть из них были **реальными багами**.

#### 1. Коллизия `chunk_id` при вложенном корпусе

`kb.py` строит `chunk_id` как `{basename_stem}-{strategy}-{i:04d}`. Для
корпуса дня 21 (плоские имена в `uploads/`) это безопасно, но в корпусе
проекта **18 файлов `design.md`**, 18 `proposal.md`, 19 `spec.md` — ID
совпадали, и сборка падала:

```
sqlite3.IntegrityError: UNIQUE constraint failed: chunks.chunk_id
```

Исправлено в `ProjectKnowledgeBase._chunks_out`: ID из полного пути.
`kb.py` не изменён — поведение дня 21 не затронуто.

#### 2. Префикс `b/` в путях diff отключал проверку молча

`git diff` отдаёт `+++ b/studio/backend/mod.py`. Первая версия парсера
оставляла префикс, и `_backend_module_of` (проверка по префиксу) не
срабатывала — правило `missing_test` **молча не работало**, хотя
выглядело реализованным. Исправлено: путь берётся из заголовка
`diff --git a/X b/Y`, префиксы срезаются.

#### 3. Детектор инвариантов ругался на правильный код

Правило «print в бэкенде» срабатывало на **упоминание** `print()` внутри
строкового литерала (в том числе в сообщении самого детектора) и на
корректно тегированные многострочные вызовы `print(f"[KB] …"`. То есть
детектор давал ложные срабатывания на хорошем коде — доверять ему было
нельзя. Переформулировано под реальный стиль репозитория (тегированный
`print("[Tag] …")`, дни 16–30): 13 находок → **0**, и `assistant.py`
проверяет сам себя чисто.

#### 4. Локальная модель уходила на удалённый API и получала 401

Самая дорогая находка. `agent._base_for()` отправляет на Ollama только
модели из `_local_ids` (наполняется в `list_models()`). При вызове из
ассистента локальная модель там зарегистрирована не была, уходила на
удалённый GPustack и получала **401** — у локальной модели там нет
ключа. Ошибка **глоталась** широким `except`, и «ассистент не отвечает»
выглядело как проблема ассистента, а не маршрутизации.

Исправлено: модель регистрируется перед вызовом (`_ensure_local_model`),
а причина неудачи сохраняется в `llm_error` и **возвращается в ответе**
(`ask`/`support`/`review`). После исправления живая проверка дала
`llm=true` во всех трёх модулях.

#### 5. Пустой diff молча подменялся изменениями рабочего дерева

`review_diff(diff="")` трактовал пустую строку как «не передано» и брал
изменения из git. Клиент, приславший пустой diff, получал отчёт по
**чужим** изменениям. Найдено e2e A7 (ожидался 400 — получен 200).
Исправлено: `diff=None` — читаем git, пустая строка — ошибка.

#### 6. Кириллические заголовки ADR давали `adr.md`

Слаг строился ASCII-фильтрацией, поэтому «Выбор базы данных» терял все
символы → `adr.md`, и файлы затирали друг друга. Добавлена
транслитерация: `vybor-bazy-dannyh`.

#### 7. Ловушка занятого порта: проверялся чужой сервер

Первый прогон Part B показал HTTP 405 на всех POST-роутах. Причина — не
в коде: на порту остался **процесс прошлого прогона**, новый uvicorn
порт не занял, и запросы уходили к старой сборке без роутов ассистента
(GET при этом попадал в SPA-фолбэк `/{path}` и возвращал HTML).
Проверка «прошла», ничего не проверив. Добавлен `wait_port_free()`:
e2e честно сообщает, что не может проверять свой сервер.

## День 35: CLI ассистента + агенты в Markdown

### Задание и что сделано

Задание дня 35 — сделать то же, что дни 30–34 (вопросы по проекту,
ревью изменений, поддержка с CRM, автономные файловые сценарии), но
**для CLI**; при этом агенты должны быть **в формате Markdown, в обоих
исполнениях**.

Сделано два слоя, закрывающих два разных разрыва:

| Разрыв | Решение |
|---|---|
| Ассистент был доступен только из браузера — разработчик в терминале вынужден поднимать сервер и кликать | `studio/backend/cli.py` — терминальный вход в те же модули |
| «Характер» агентов был зашит в Python (`_ASK_SYSTEM`, `_SUPPORT_SYSTEM`, `_REVIEW_SYSTEM`) — правка промпта требовала правки кода | `agents/*.md` — определения агентов: frontmatter + тело-промпт |

### Решение 1: CLI — тонкая обёртка, а не второй ассистент

Соблазн — написать в CLI свою логику: свой RAG, свой парсер diff, свой
обход CRM. Это дало бы **два поведения одного инструмента**: терминал и
веб начали бы расходиться в деталях, а багфиксы пришлось бы делать
дважды.

Поэтому CLI не содержит бизнес-логики вообще:

| Слой | Ответственность |
|---|---|
| `studio/backend/cli.py` | разбор `argv`, типизация параметров, вызов сервиса, форматирование вывода, код возврата |
| `AssistantService` | вся логика: RAG, ревью, CRM, сценарии (дни 30–34) |
| `agents/*.md` | системный промпт и метаданные агента |

Принцип закреплён тестом (`TestThinWrapper`): CLI не импортирует `kb`,
`mcp`, `gateway`, не использует сеть напрямую и не делает git-мутаций.

### Решение 2: агент — это документ, а не метод

Определение агента вынесено в Markdown с frontmatter:

```markdown
---
name: code-review
execution: cli
description: Ревью изменений — находки, severity, рекомендации
tools: [git, diff, corpus]
temperature: 0.1
---
Ты — код-ревьюер в проекте «Студия». Отчёт печатается в терминал...
```

Почему именно md, а не Python-константа:

* **читается человеком** — видно, что инструктирует модель, без чтения кода;
* **диффится построчно** — изменение промпта видно в ревью как обычный текст;
* **версионируется git** — история поведения агента доступна;
* **правится без кода** — сменить тон или ограничения можно правкой md;
* **не требует пакетов** — frontmatter `ключ: значение` парсится stdlib-ом
  (PyYAML в зависимостях проекта нет, NFR-1 запрещает новые пакеты).

### Решение 3: 4 агента × 2 исполнения = 8 файлов

Исполнения различаются **формой вывода и каналом**, а не смыслом:

| | `.api.md` (HTTP/Студия) | `.cli.md` (терминал) |
|---|---|---|
| Потребитель | браузер, JSON-клиент | человек в терминале, пайп, CI |
| Формат | структурированные поля, UI-блоки | markdown, короткие строки |
| Ссылки | на элементы интерфейса | на пути `файл:строка` и команды |
| Запреты | — | без HTML, без «нажмите кнопку» |

Разница не косметическая. В API-исполнении ревью-агент может сослаться
на панель источников рядом с ответом; в CLI такой панели нет, поэтому
prompt **обязан** требовать `файл:строка` — иначе замечание
бесполезно, по нему нельзя перейти к месту в редакторе.

Это проверяется тестом: `test_api_and_cli_prompts_differ` падает, если
тела промптов совпадут (тогда «два исполнения» были бы фикцией).

### Команды

### Решение 4: типизация `--param` — и реальная ловушка

CLI получает аргументы строками. В Python **непустая строка истинна**,
поэтому без типизации:

```
dry_run=true  → "true"  → bool True  → not dry_run = False → пропуск (ок)
dry_run=false → "false" → bool True  → not dry_run = False → ПРОПУСК (баг!)
```

То есть `--param dry_run=false` (явный запрос записи) **молча ничего не
записал бы**, отчитавшись об успехе. Поэтому значения типизируются явно:
`true/false` → bool, `none/null` → None, числа → int/float, остальное →
строка. Тест `test_dry_run_false_actually_writes` фиксирует, что запись
происходит, а e2e A18 проверяет это через реальный подпроцесс.

### Решение 5: вывод, коды возврата и ошибки

* по умолчанию — markdown в stdout (читается человеком, рендерится в
  GitHub и терминале);
* `--json` — машинный вывод для скриптов;
* `--out FILE` — запись отчёта в файл;
* код возврата `0` — успех, `1` — ошибка; `--fail-on-high` в `review`
  даёт `1` при критичных находках — удобно в CI;
* ошибки — в stderr с RU-текстом **без traceback** (он бесполезен в
  пайпе и CI-логе); traceback только при `--debug`;
* ошибка разбора аргументов — стандартный код `2` от argparse.

### Решение 6: `--no-llm` — офлайн-режим

Первый же вопрос уходит в сетевой зонд моделей (`_ensure_local_model` →
`list_models`) и может ждать таймаут, если Ollama недоступна. Для
офлайн-работы, отладки и тестов есть глобальный `--no-llm`: агент не
создаётся, ответы строятся детерминированно, сеть не трогается вовсе.

Это не украшение: тесты CLI с сетью занимали **85 секунд**, с
`--no-llm` — **0,26 секунды**.

### Находки живой проверки

#### 1. Без типизации `dry_run=false` молча пропускал запись

Описано выше — самая опасная находка дня. Скрипт сообщал бы об успехе,
не сделав ничего.

#### 2. `--no-llm` как локальный флаг не работал

`review --no-llm` отключал только LLM-часть ревью, но сервис всё равно
создавал `StudioAgent`, и первый же вызов уходил в сеть. Флаг сделан
**глобальным** (`cli.py --no-llm <команда>`): он предотвращает создание
агента целиком. Побочный эффект: в e2e флаг должен стоять ДО
подкоманды — на этом сначала упали шаги A14/A15 (код 2 от argparse).

#### 3. Неизвестный тикет ронял `support` с ошибкой

`support T-9999` без `--question` возвращал код 1: сервису нечего
искать, и он честно бросает «нечего обрабатывать». В терминале это
выглядит как отказ на ровном месте. Теперь CLI подставляет id тикета
как текст запроса и предупреждает в stderr — возвращается общий ответ
по базе знаний с явной пометкой, что тикет не найден.

#### 4. В сводке `find_usages` список файлов обрезается

Человекочитаемая сводка показывает первые 5 файлов («…»), поэтому
проверка «есть ли `gateway.py`» по тексту давала ложный провал (e2e
A16). Проверка переведена на `--json` — это и правильнее: машинный
вывод не зависит от форматирования.

#### 5. `studio/cli.py` не запускается как `python -m studio.cli`

У пакета `studio/` нет `__init__.py`, поэтому из корня репозитория
модульный запуск не работает — та же особенность, что описана в дне 30
для `uvicorn studio.backend.main:app`. CLI размещён в
`studio/backend/cli.py` и запускается из каталога бэкенда (штатный
способ для всех модулей репозитория), либо от корня по прямому пути.

## День 36: агент отвечает по запросу (RAG как источник знаний)

В этом же релизе: команда агентов в `agents/*.md` без хардкода промптов

| Вопрос | Что отвечал | Почему |
|---|---|---|
| «как устроен шлюз?» | цитаты из `docs/CLI-CHEATSHEET.md`, где просто пример команды `ask "как устроен шлюз?"` | в промпт уходили 5 «ближайших» фрагментов **без порога релевантности** |

#### Что сделано

1. **Корпус — только проект.** Кэш RAG (`*.json` в корне) и служебные
   каталоги (`.omo`, `data`, `.venv`) в корпус не попадают. Индекс
   хранит хэш корпуса (пути + размер + mtime) — **сам пересобирается**,
   когда документ появился, изменился или удалён.
2. **Гибридный поиск** (stdlib-only, как весь автономный ассистент):
   BM25 (словоформы, стоп-слова, IDF файла) + эмбеддинги **bge-m3** через
   локальную Ollama, слияние — RRF. Без Ollama поиск не падает: режим
   `bm25`, `/status` показывает причину.
3. **Эмбеддер на выбор.** `nomic-embed-text` (дефолт дня 28) на этом
   корпусе не различает вопросы: ближайшие пять фрагментов отличались по
   cosine на 0.01. `bge-m3` — различие 0.1–0.2, честный вопрос 0.6–0.7
   против ~0.45 у постороннего. Модель — `DEV_ASSISTANT_EMBED_MODEL`.
4. **Гейт релевантности.** Прежде чем отдать контекст модели, проверяем:
   плотность близости (средний cosine топ-15 / устойчивость топ-2),
   корпусность терминов (IDF: «борщ» и «биткоин» о проекте ничего не
   говорят), отсутствие термина в корпусе вовсе, редкое случайное
   совпадение. Вопрос не о проекте → **честный отказ**, а не ответ по
   соседнему разделу.
5. **Контекст — только по теме.** Из результатов в промпт попадают
   фрагменты не ниже 85 % от лучшего; контекст больше не «забивается»
   пятью фрагментами на любой вопрос.
6. **Follow-up.** «какой порт у НЕГО по умолчанию?» ищется вместе с
   предыдущим вопросом (местоимения `он/это/него`), а недостающая деталь

7. **Промпт.** Ответ только по контексту, цифры дословно, нет ответа —
   так и сказать; не пересказывать соседние разделы.
8. **Код в корпусе.** Разделы кода — по линиям-разделителям и константам
   верхнего уровня, иначе `gateway.py` на 100 КБ был одним чанком и
   строка порта из середины файла не находилась.

### День 37: расход токенов и остаток окна диалога

#### Что сделано

1. **Окно контекста берётся из модели, а не из справочника.** Раньше
   `/api/tokens` отдавал `CONTEXT_LIMITS[model]` — максимум архитектуры
   (у `gemma3:27b` — 131072), хотя `num_ctx` в Modelfile выделяет под
   контекст 8192. Теперь `StudioAgent.model_context_window()` спрашивает
   Ollama `/api/show` и берёт `min(num_ctx, *.context_length)`; справочник
   — только запасной вариант (без Ollama), и он помечен
   `context_window_method: "static"` — в UI это видно.
2. **`GET /api/tokens` сообщает не только usage**, но и окно и остаток:

   | Поле | Смысл |
   |---|---|
   | `context_window` | реальное окно модели (токенов) |
   | `max_output_tokens` | резерв под ответ (`max_tokens` конфига) |
   | `used_tokens` | промпт последнего запроса: system + инварианты + профиль + память + история |
   | `occupied_tokens` | `used_tokens + max_output_tokens` |
   | `remaining_for_dialog` | `context_window − occupied_tokens` |
   | `full_in_turns` | сколько ещё полных ходов влезает целиком |

3. **UI в шапке чата** — кольцо показывает **занято / окно**
   («2k/8.2k»), поповер — «окно диалога»: занято, **осталось для
   диалога**, резерв на ответ, «ещё влезет N ход(ов)», затем расход
   последнего запроса (prompt/completion/total), сессия и модель.
   Предупреждение (оранжевое кольцо) — с 80% окна: тревожит остаток,
   а не заполненность «до упора».
4. **Автономный ассистент** (`dev_assistant.py`) печатает после каждого
   ответа реальные числа Ollama:

   ```
   🔢 Токены: промпт 2047 + ответ 487 = 2534 | окно 8 192 | остаток 5 658 (31% занято) [██████░░░░…]
   ```

   `num_ctx` в запрос передаётся из модели (`LLMClient.context_window()`),
   а не константой 8192.

#### Проверка

| Проверка | Результат |
|---|---|
| Бэкенд | **1207 passed, 6 skipped** (`test_api.py` + новый `test_context_window.py`) |
| Фронтенд | `tsc -b` 0 ошибок, `npm run build` успешно, vitest **330 passed** |
| Автономный ассистент | `tests/test_day31_rag_relevance.py` — **25 passed** (в т.ч. строка токенов) |
| Живьём | `dev_assistant.py`: «промпт 2047 + ответ 487 = 2534, окно 8 192, остаток 5 658» |

**Ограничения.** `used_tokens` — это промпт последнего запроса: система
считает его точным, но следующий ход вырастет на длину истории, поэтому
`full_in_turns` — оптимистичная оценка «сейчас». Точный профиль памяти
(llm-токены по блокам) не измеряется — цена в отдельном вызове модели.

## День 32: автоматизация ревью кода (CLI + GitHub Action)

### Задание и что сделано

Задание — настроить пайплайн, в котором ассистент анализирует новый PR:
получает diff и изменённые файлы, использует RAG (документация + код) и
выдаёт текст ревью с тремя блоками — **потенциальные баги**,
**архитектурные проблемы**, **рекомендации**.

Реализовано **только в CLI** (без веб-вкладки): пайплайн —
`studio/backend/pr_review.py` + команда `cli.py pr-review`, запуск —
GitHub Action `.github/workflows/ai-review.yml`, который вызывает
переиспользуемое действие `.github/actions/ai-pr-review`.

```
pull_request (opened / synchronize / reopened / ready_for_review)
  │
  ▼  .github/workflows/ai-review.yml      права: contents read, pull-requests write
  │     concurrency: новый пуш отменяет ревью старой версии
  │
  ▼  .github/actions/ai-pr-review
  ├─ (1) cli.py pr-review check          что доступно пайплайну: RAG, LLM, git, PR
  ├─ (2) cli.py index                    индекс корпуса проекта (документация + код)
  ├─ (3) cli.py pr-review run
  │        ├─ diff и изменённые файлы    git diff origin/<base>...HEAD
  │        │                              или API GitHub (PR из форка)
  │        ├─ RAG                        фрагменты README/docs/openspec/кода,
  │        │                              релевантные добавленным строкам
  │        ├─ проверки                   check_diff + инварианты проекта в diff
  │        ├─ модель                     agents/pr-review.cli.md → 3 блока
  │        └─ отчёт                      review.md + review.json
  ├─ (4) комментарий в PR                идемпотентно: повторный прогон обновляет
  ├─ (5) аннотации ::error/::warning     на строки diff во вкладке Files changed
  └─ (6) $GITHUB_STEP_SUMMARY, артефакт ai-pr-review (markdown + JSON, 30 дней)
```

### Как пользоваться

```bash
# 1. Локально: ревью ветки против master (как в CI)
.venv/bin/python studio/backend/cli.py pr-review check
.venv/bin/python studio/backend/cli.py index
.venv/bin/python studio/backend/cli.py pr-review run --base origin/master \
    --out review.md --json-out review.json

# 2. Пайп: diff из stdin, отчёт в stdout
git diff origin/master...HEAD | .venv/bin/python studio/backend/cli.py \
    pr-review run --diff -

# 3. Блокирующий режим для CI: код 1 при находке уровня «критично»
.venv/bin/python studio/backend/cli.py pr-review run --diff pr.diff --fail-on-high

# 4. PR из форка: ветки нет в рабочем дереве — diff берётся из API
.venv/bin/python studio/backend/cli.py pr-review run --github-pr owner/repo#42
```

Ключи опций: `--annotations` (workflow-команды), `--comment OWNER/REPO#N`
(комментарий в PR), `--step-summary FILE` (сводка в Summary запуска),
`--title`, `--top-k` (фрагментов RAG на файл), `--json` / `--out` /
`--json-out`, `--no-llm` (детерминированный режим).

### Как включается модель в CI

В Action модель задаётся секретом и переменными репозитория
(Settings → Secrets and variables → Actions):

| Что | Где | Значение по умолчанию |
|---|---|---|
| `LLM_API_KEY` | **secret** | пусто → детерминированный отчёт |
| `LLM_MODEL` | variable | `openai/gpt-4o-mini` |
| `LLM_BASE_URL` | variable | `https://openrouter.ai/api/v1` |

Это любой OpenAI-совместимый сервер: OpenRouter, OpenAI, vLLM,
**собственная Ollama на VPS** (`LLM_MODEL=qwen3:8b`,
`LLM_BASE_URL=http://<адрес>:11434/v1`). Локальный `localhost:11434` из
GitHub Actions недоступен — поэтому `AssistantService._llm` дня 32
умеет брать модель из `LLM_*` (поведение дней 28–36 по умолчанию не
меняется: без `LLM_MODEL` используется конфиг Студии).

Без ключа пайплайн **не падает**: отчёт строится детерминированно
(изменённые файлы, находки, рекомендации по правилам проекта), а в
комментарии и Summary прямо написано, что модель недоступна и почему.

### Что сделано в деталях

1. **Diff и изменённые файлы** — три источника, один разбор
   (`assistant.parse_unified_diff`): файл, stdin (`-`), git
   (`--base <ref>...HEAD`), API GitHub для форков. Файлы получают статус
   `added`/`modified`/`renamed`/`deleted` (переименование — парой
   `old → new`) и счётчики `+/-`. Пустой diff — ошибка, а не молчаливая
   подмена изменениями рабочего дерева.
2. **RAG по документации и коду** — дифф режется на окна; из окна
   берутся термины (идентификаторы кода, имена модулей, слова без
   стоп-слов Python/JS), по ним ищется корпус проекта (`README`,
   `docs/`, `openspec/`, код бэкенда и фронтенда — индекс `cli.py
   index`, сеть не нужна). В промпт попадают фрагменты с пометкой
   «связано с `<изменённый файл>`» — модель понимает, с чем сопоставляет
   документацию. Промпты агентов `agents/*.md` ищутся отдельно: правка
   инструкции модели — тоже архитектурное изменение.
3. **Детерминированные проверки** — `assistant.check_diff`
   (`secret`, `bare_except`, `missing_test`, `missing_docs`,
   `print_call`, `long_line`, `todo`) плюс **инварианты проекта,
   сработавшие именно в добавленных строках** (`print` в бэкенде,
   документированный публичный API через `__all__`, tagged-log): правило
   применяется к «виртуальному файлу» из строк `+`, поэтому
   унаследованные нарушения в PR не шумят, а две проверки дня 32 —
   изменение зависимостей без документации и правка CI — дают
   предупреждения даже когда код не тронут.
4. **Ревью моделью** — промпт агента `agents/pr-review.cli.md`
   (frontmatter + тело, как в дне 35) и контекст: метаданные PR, дифф,
   находки, RAG-фрагменты, промпты агентов. Ответ разбирается в три
   секции: XML-теги, markdown-заголовки или пункты списка; нераспознанный
   ответ не теряется, а уходит в «Рекомендации», «нечего сказать» —
   не считается находкой.
5. **Отчёт** — markdown для комментария PR: заголовок, сводка цифр,
   таблица изменённых файлов, три блока, детерминированные находки,
   «сворачиваемый» блок RAG (на что опиралось ревью); JSON для
   машинной обработки (`review.json`); короткая сводка для
   `$GITHUB_STEP_SUMMARY`; аннотации `::error` (критично) и
   `::warning` на строки diff.
6. **Идемпотентный комментарий** — отчёт несёт маркер
   `<!-- ai-pr-review -->`; повторный прогон обновляет прежний
   комментарий (PATCH), а не плодит новые.
7. **Форки и права** — для PR из форка diff и файлы читаются через API
   (`GET /repos/{repo}/pulls/{n}` с `Accept: …v3.diff`); `GITHUB_TOKEN`
   на таких PR имеет только `read`, поэтому публикация комментария —
   «best effort»: при отказе отчёт остаётся артефактом и в Summary.
8. **Бюджет промпта** — найденная живой проверкой проблема: у Ollama
   окно **8192 токена**, и большой PR упирался в `HTTP 400 «exceeds the
   available context size»`. Промпт собирается по долям бюджета
   (метаданные 6 %, находки 14 %, дифф 44 %, RAG 26 %, промпты агентов
   10 %), усечение видно в `prompt` JSON-отчёта; лимит —
   `REVIEW_MAX_PROMPT_CHARS` (по умолчанию 26 000 символов ≈ 6–7 тыс.
   токенов).

**Ограничения (осознанные).** (1) У эмбеддера корпуса в CI —
офлайн hash-режим (`cli.py index` без ключей): семантика слабее, чем у
bge-m3 в автономном ассистенте, зато прогон детерминирован и не зависит
от сети; порог релевантности не применяется, лишние фрагменты
отсекаются бюджетом промпта. (2) Одна модель отвечает за три блока —
баг, не видимый в 26 тыс. символов контекста, не будет найден; для
больших PR сборка Action обрезает дифф и пишет об этом в отчёте.
(3) `--fail-on-high` смотрит только на детерминированные находки:
пункты модели не блокируют merge (решение за человеком). (4) Если в
CI-репозитории нет `docs/` и `agents/`, RAG работает по тому корпусу,
который есть; отсутствие индекса — предупреждение, а не провал.
(5) Комментарий в PR публикуется по маркеру отчёта, поэтому ручная
правка содержимого комментария перезапишется следующим прогоном.
