# Release Notes — day32-pr-review (день 32)

Ветка: `day32-pr-review` (от `day31-cli-assistant`).

## Что в релизе

**Автоматическое AI-ревью pull request: пайплайн в GitHub Actions,
который получает diff и изменённые файлы, поднимает RAG по документации и
коду проекта и публикует ревью с тремя блоками — потенциальные баги,
архитектурные проблемы, рекомендации. Только CLI, без веб-вкладки.**

Сделано:

1. **Пайплайн** — `.github/workflows/ai-review.yml` (триггер
   `pull_request`: opened / synchronize / reopened / ready_for_review,
   `concurrency` отменяет ревью устаревшей версии, права `contents: read`
   + `pull-requests: write`) вызывает переиспользуемое действие
   `.github/actions/ai-pr-review` (его можно подключить в другом
   репозитории): `pr-review check` → `index` → `pr-review run` →
   комментарий в PR → аннотации → Summary → артефакт.
2. **Ядро** — `studio/backend/pr_review.py`: diff из файла / stdin / git /
   API GitHub (форки), изменённые файлы со статусами, RAG-окна по
   хункам, инварианты проекта в добавленных строках, промпт с бюджетом,
   разбор ответа модели в три секции, markdown/JSON-отчёт, preflight,
   идемпотентный комментарий, workflow-аннотации.
3. **CLI** — `cli.py pr-review check|run` с `--diff` (`-` = stdin),
   `--base`, `--github-pr`, `--title`, `--top-k`, `--fail-on-high`,
   `--annotations`, `--comment`, `--step-summary`, `--json`, `--out`,
   `--json-out`, `--no-llm`.
4. **Модель в CI** — `AssistantService._llm` берёт модель из `LLM_MODEL` /
   `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_BACKEND` (Ollama или любой
   OpenAI-совместимый сервер), иначе — конфиг Студии (прежнее поведение);
   без ключа пайплайн работает детерминированно и честно об этом пишет.
5. **Агент** — `agents/pr-review.cli.md` (frontmatter + тело-промпт):
   три раздела, только факты из диффа/RAG/находок, номера строк из диффа.

# Release Notes — day31-cli-assistant (дни 30–37)

Ветка: `day31-cli-assistant` (от `day30-34-dev-assistant`).

## Что в релизе

**Шлюз локальной LLM, автономный CLI-ассистент с гибридным RAG, агенты
в Markdown без хардкода промптов, видимость токенов и остатка окна.**

Пять направлений:

1. **День 30 — шлюз локальной LLM** (`studio/backend/gateway.py`): Ollama
   остаётся на loopback, наружу в LAN смотрит только шлюз — ключи
   клиентов (SHA-256), rate limit RPM/TPM, `max_context` с LLM-компрессией,
   учёт использования, вкладка «Сервис» в UI.
2. **День 31 — автономный CLI-ассистент** (`dev_assistant.py`): вопросы по
   проекту, git-инструменты по MCP, создание файлов, встроенный RAG.
3. **День 36 — RAG отвечает по запросу**: гибридный поиск (BM25 + bge-m3
   через Ollama), гейт релевантности, отказ вместо ответа «по соседнему
   разделу», самопересборка индекса по хэшу корпуса.
4. **Промпты агентов — документы**: `agents/*.md` (4 агента × 2
   исполнения), `assistant.py` больше не содержит `_ASK_SYSTEM` /
   `_REVIEW_SYSTEM` / `_SUPPORT_SYSTEM`; карта пайплайна —
   `docs/PIPELINE.md`, команда агентов — `docs/AGENTS.md`.
5. **День 37 — токены и окно диалога**: окно берётся из `num_ctx` модели
   (`Ollama /api/show`), UI показывает «занято / окно» и «осталось для
   диалога», CLI-ассистент печатает промпт/ответ/остаток после каждого
   ответа.

```
 вопрос ──▶ agents/<name>.api.md (промпт, документ)
         ─▶ AssistantService (assistant.py) ─▶ ProjectKnowledgeBase
         ─▶ kb.py :: search_rag  (векторы Ollama + BM25 + RRF)
         ─▶ LLM (Ollama / GPustack) ─▶ ответ + sources
         ─▶ GET /api/tokens: окно модели, занято, остаток
```

## Ключевые решения

* **Один источник правды** — `AssistantService`: CLI (`studio/backend/
  cli.py`) и HTTP (`main.py`) не дублируют логику.
* **Промпт — документ.** Разбор `agents/*.md` — `agents.py` (без
  YAML-пакета), кэш по mtime: правка промпта без перезапуска.
  Нет файла/битый frontmatter → детерминированный ответ, а не молчаливая
  подмена текста.
* **RAG с порогом.** Фрагменты уходят в промпт только при достаточной
  близости (плотность cosine + IDF терминов); посторонний вопрос →
  честное «в документации этого нет».
* **Эмбеддер — по делу.** `nomic-embed-text` не различал вопросы на
  корпусе проекта (cosine топ-5 отличался на 0.01), поэтому у
  `dev_assistant.py` свой `bge-m3` (`DEV_ASSISTANT_EMBED_MODEL`).
* **Окно — не справочник.** `min(num_ctx, *.context_length)`; справочник
  `CONTEXT_LIMITS` — только fallback и помечен в API.

# Release Notes — day35-cli-md-agents (день 35)

Ветка: `day35-cli-md-agents` (от `day30-34-dev-assistant`).

## Что в релизе

**CLI ассистента и агенты в формате Markdown — в обоих исполнениях.**
Задание дня 35: сделать то же, что дни 30–34 (вопросы по проекту, ревью
изменений, поддержка с CRM, автономные файловые сценарии), но **для
CLI**; агенты должны быть **в формате md**.

Релиз закрывает два разрыва:

1. ассистент был доступен только из браузера — разработчик в терминале
   вынужден поднимать сервер и кликать;
2. «характер» агентов был зашит в Python (`_ASK_SYSTEM`,
   `_SUPPORT_SYSTEM`, `_REVIEW_SYSTEM`) — правка промпта требовала
   правки кода и перезапуска.

```
  терминал / CI / пайп                     браузер (Студия)
        │                                        │
        │  python cli.py review                  │  POST /api/assistant/review
        │      --agent code-review               │
        ▼                                        ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  studio/backend/cli.py (разбор argv → вызов → вывод)         │
  └──────────────────────────────────────────────────────────────┘
        │                                        │
        └──────────────┬─────────────────────────┘
                       ▼
         ┌────────────────────────────────┐
         │  AssistantService              │  ← ОДИН источник правды
         │  (дни 30–34, не дублируется)   │
         └────────────────────────────────┘
                       │ читает системный промпт
                       ▼
         ┌────────────────────────────────┐
         │  agents/*.md  (4 агента × 2)   │
         │  project-qa / code-review /    │
         │  support / file-ops            │
         └────────────────────────────────┘
```

## Ключевые решения

### 1. CLI — тонкая обёртка, а не второй ассистент

Соблазн — написать в CLI свою логику (свой RAG, свой парсер diff, свой
обход CRM). Это дало бы **два поведения одного инструмента**: терминал и
веб расходились бы в деталях, а багфиксы делались бы дважды.

CLI не содержит бизнес-логики: разбор `argv`, типизация, вызов сервиса,
форматирование, код возврата. Принцип закреплён тестами
`TestThinWrapper` — CLI не импортирует `kb`/`mcp`/`gateway`, не
использует сеть напрямую, не делает git-мутаций.

### 2. Агент — документ, а не метод

```markdown
---
name: code-review
execution: cli
description: Ревью изменений — находки, severity, рекомендации
tools: [git, diff, corpus]
temperature: 0.1
---
Ты — код-ревьюер в проекте «Студия». Отчёт печатается в терминал...
```

Markdown выбран потому, что определение агента — это **документ**:
читается человеком, диффится построчно, версионируется в git, правится
без кода. Frontmatter парсится stdlib-ом — PyYAML в зависимостях нет, а
NFR-1 запрещает новые пакеты.

### 3. 4 агента × 2 исполнения = 8 файлов

| | `.api.md` | `.cli.md` |
|---|---|---|
| Потребитель | браузер, JSON-клиент | терминал, пайп, CI |
| Формат | структура, UI-блоки | markdown, короткие строки |
| Ссылки | на элементы интерфейса | на `файл:строка`, команды |
| Запреты | — | без HTML, без «нажмите кнопку» |

Разница не косметическая: в API-исполнении ревью-агент ссылается на
панель источников, а в CLI такой панели нет — промпт **обязан** требовать
`файл:строка`, иначе замечание бесполезно. Тест
`test_api_and_cli_prompts_differ` падает, если тела совпадут: тогда «два
исполнения» были бы фикцией. Живая проверка (e2e B2) подтверждает, что
`--agent` действительно меняет ответ.

### 4. Типизация `--param` — реальная ловушка

В Python непустая строка истинна, поэтому без типизации:

```
dry_run=true  → "true"  → bool True → not dry_run = False → пропуск (ок)
dry_run=false → "false" → bool True → not dry_run = False → ПРОПУСК (баг!)
```

`--param dry_run=false` (явный запрос записи) **молча не записал бы
ничего**, отчитавшись об успехе. Значения типизируются:
`true/false` → bool, `none/null` → None, числа → int/float, остальное →
строка.

### 5. Вывод, коды возврата, ошибки

| Что | Как |
|---|---|
| Вывод | markdown в stdout; `--json` для скриптов; `--out FILE` для записи |
| Коды | `0` успех, `1` ошибка, `2` ошибка разбора аргументов |
| CI | `review --fail-on-high` → код 1 при критичных находках |
| Ошибки | stderr, RU-текст, **без traceback** (только при `--debug`) |
| Агент | `--agent NAME`; дефолт по команде (project-qa / code-review / support / file-ops) |
| Офлайн | глобальный `--no-llm`: агент не создаётся, сеть не трогается |

### 6. Полный список команд

```
agents list|show     каталог агентов из agents/*.md
ask <вопрос>         вопрос по проекту (RAG) + источники
review               ревью изменений (--diff/--base/--fail-on-high/--out)
tickets              тикеты CRM с фильтрами
support <ID>         ответ по тикету с персонализацией
scenarios|scenario   каталог и запуск файловых сценариев
index                сборка индекса проекта
status               корпус, индекс, CRM, LLM, git
git                  ветка, изменённые файлы, diff
```

## Находки живой проверки

Всё ниже найдено прогоном e2e и реальных тестов.

1. **`dry_run=false` молча пропускал запись** — самая опасная находка:
   скрипт сообщал бы об успехе, не сделав ничего. Исправлено типизацией.
2. **`--no-llm` как локальный флаг не работал**: `review --no-llm`
   отключал только LLM-часть, но сервис всё равно создавал
   `StudioAgent`, и первый вызов уходил в сеть. Флаг сделан глобальным.
   Побочный эффект: в e2e он должен стоять ДО подкоманды — на этом
   сначала упали шаги A14/A15 (код 2 от argparse).
3. **Неизвестный тикет ронял `support`**: `support T-9999` без
   `--question` возвращал код 1 («нечего обрабатывать») — в терминале это
   отказ на ровном месте. Теперь CLI подставляет id тикета как запрос и
   предупреждает в stderr.
4. **Сводка `find_usages` обрезает список файлов** — проверка по тексту
   давала ложный провал (e2e A16). Переведено на `--json`.
5. **`studio/cli.py` не запускается как `python -m studio.cli`**: у
   пакета `studio/` нет `__init__.py` — та же особенность, что в дне 30
   для `uvicorn studio.backend.main:app`. CLI размещён в
   `studio/backend/cli.py`.
6. **Тесты CLI с сетью занимали 85 секунд** — из-за сетевого зонда
   моделей. С `--no-llm` — **0,26 секунды**.

## Ключевые решения

### 1. Индекс проекта отдельный, а не общий корпус

Соблазн — дописать документацию и код в существующий `data/kb/index.db`
дня 21. Это **неверно**: корпус дня 21 сознательно ограничен загрузками
пользователя, и подмешивание репозитория сломало бы три вещи — поиск по
пользовательским документам начал бы выдавать чанки кода, пересборка
индекса проекта стирала бы загрузки, а статистика дня 21 стала бы
бессмысленной.

Поэтому — **второй индекс** `data/kb/project.db` (каталог
`data/kb/project/`), та же схема и тот же код: `ProjectKnowledgeBase`
наследует `KnowledgeBase` и переопределяет только `corpus_files`.
`kb.py` не форкается. Инвариант проверяется в e2e (A2): `data/kb/index.db`
побайтово не изменяется при сборке индекса проекта.

### 2. Корпус собирается явными правилами

Индексировать репозиторий целиком нельзя: `.venv` — десятки тысяч
файлов, плюс `node_modules`, `.git`, `data/kb/index.db` (бинарный),
`__pycache__`. Поэтому корпус задаётся правилами с жёсткими исключениями
(`EXCLUDE_DIRS`, `EXCLUDE_SUFFIXES`, `MAX_FILE_BYTES`), а исключённые
каталоги обрезаются **прямо в `os.walk`** — иначе `.venv` всё равно
обходится.

Результат на реальном репозитории: **209 файлов** — README, RELEASE,
LINKS, `docs/`, `openspec/`, `studio/backend/**`, `studio/frontend/src/**`,
`scripts/*.py`. Мусора нет (проверяется e2e A3).

### 3. Ревью: факты собирает код, LLM только формулирует

Ревью целиком на LLM — плохая идея: модель выдумывает номера строк и
«находит» то, чего в diff нет. Поэтому факты детерминированы, а LLM
опциональна:

| Слой | Кто | Что даёт |
|---|---|---|
| Разбор diff | код | файлы, ханки, +/- строки, номера строк |
| 7 проверок | код | `secret`, `bare_except`, `print_call`, `long_line`, `todo`, `missing_test`, `missing_docs` |
| Сопоставление с доками | индекс (RAG) | затронутые документы |
| Нарратив | LLM (опционально) | связный текст рекомендаций |

Каждая находка несёт **доказательство** — файл и номер строки в новой
версии — и severity. Без LLM отчёт полностью работоспособен (проверяется
Part A e2e). Это принципиально: ревью работает офлайн.

### 4. Поддержка: данные CRM меняют ответ, и это видно

`TicketStore` читает `data/crm/users.json` и `tickets.json`, связывает
тикет с пользователем и его историей, и эти факты инжектятся в промпт.
Персонализация **наблюдаема**: ответ содержит блок `context.applied` со
списком применённых полей («план: free», «статус оплаты: failed», …) —
можно проверить, что именно повлияло. Неизвестный тикет не выдумывает
данные пользователя: `found: false`, `user: null`.

### 5. Сценарии: цель, а не пошаговая инструкция

Пользователь говорит **что нужно**, а не **как**. Сценарий сам решает,
какие файлы читать и куда писать:

| Сценарий | Автономные действия |
|---|---|
| `find_usages` | обход корпуса код+доки, поиск вхождений как отдельного слова, группировка по файлам с номерами строк |
| `update_docs` | чтение git-diff → определение затронутых модулей → правка секции README между маркерами (идемпотентно) |
| `generate` | ADR с автонумерацией и **транслитерацией** кириллического заголовка, changelog из git-лога, README-заготовка |
| `check_invariants` | проверка файлов на правила проекта (ML-зависимости, тегированный лог, docstring) |
| `diff_report` | подготовка unified-diff отчёта: сохранение в файл или возврат без записи |

### 6. Безопасность записи

Сценарии пишут **только** в allow-list (`README.md`, `CHANGELOG.md`,
`docs/`, `openspec/`) и **только** внутрь проекта. Абсолютный путь, `..`,
путь в код бэкенда, путь в `data/` и симлинк наружу отвергаются с
`ScenarioError` → HTTP 400. Проверяется e2e A16: 4 вектора атаки → 400,
файл вне проекта не создан. Запись атомарна (временный файл +
`os.replace`).

**Git-мутаций нет.** Ассистент читает `git status`/`diff`/`log` и пишет
файлы в рабочее дерево; коммит остаётся за человеком (та же логика
human-gate, что в plan-review дня 15). Тест `test_never_mutates`
проверяет отсутствие `commit`/`push`/`checkout`/`reset` в модуле.

## Находки живой проверки

Всё ниже найдено прогоном `scripts/e2e_day31.py` и реальных тестов, а не
выведено умозрительно.

### 1. Коллизия `chunk_id` при вложенном корпусе

`kb.py` строит `chunk_id` как `{basename_stem}-{strategy}-{i:04d}`. Для
корпуса дня 21 (плоские имена в `uploads/`) это безопасно, но в корпусе
проекта есть **18 файлов `design.md`**, 18 `proposal.md`, 19 `spec.md` и
т. п. — ID совпадали, и сборка падала на `PRIMARY KEY`:

```
sqlite3.IntegrityError: UNIQUE constraint failed: chunks.chunk_id
```

Исправлено в `ProjectKnowledgeBase._chunks_out`: ID строится из полного
пути (слэши → `_`), что уникально по построению. `kb.py` не изменён —
поведение дня 21 не затронуто. Регрессионный тест
`test_chunk_ids_unique_with_same_stem`.

### 2. Префикс `b/` в путях diff отключал проверки

`git diff` отдаёт `+++ b/studio/backend/mod.py`. Первая версия парсера
оставляла префикс, из-за чего `_backend_module_of` (проверка по префиксу
`studio/backend/`) не срабатывала — правило `missing_test` **молча не
работало**, хотя выглядело реализованным. Исправлено: канонический путь
берётся из заголовка `diff --git a/X b/Y`, префиксы `a/`/`b/`
срезаются. Тест `test_strips_ab_prefix`.

### 3. Детектор инвариантов давал ложные срабатывания

Правило «print в бэкенде» сначала срабатывало на **упоминание** `print()`
внутри строкового литерала (сообщение самого детектора!) и на
корректно тегированные многострочные вызовы `print(f"[KB] …"`. То есть
детектор ругался на правильный код и пропускал бы неправильный —
доверять ему было нельзя.

Исправлено: инвариант переформулирован под реальный стиль репозитория
(тегированный `print("[Tag] …")`, дни 16–30), наличие вызова
определяется по тексту без литералов, наличие тега — по **первому
аргументу** вызова с учётом многострочности и вложенных скобок. Итог:
13 находок → 0, и `assistant.py` проверяет сам себя чисто. Тесты
`test_tagged_print_is_ok`, `test_multiline_tagged_print_is_ok`,
`test_print_mention_in_string_is_not_a_call`.

### 4. Локальная модель уходила на удалённый API и получала 401

Самая дорогая находка. `agent._base_for()` отправляет на Ollama только
модели из `_local_ids`, который наполняется в `list_models()`. При
прямом вызове из ассистента локальная модель не была там
зарегистрирована, уходила на удалённый GPustack и получала **401** (у
локальной модели там нет ключа). Ошибка **молча глоталась** широким
`except`, и «ассистент не отвечает» выглядело как проблема ассистента.

Исправлено: `_ensure_local_model()` регистрирует модель перед вызовом, а
причина неудачи сохраняется в `llm_error` и возвращается в ответе
(`llm_error` в `/api/assistant/ask`, `/support`, `/review`). Теперь
деградация наблюдаема, а не молчалива. После исправления живая проверка
дала `llm=true` во всех трёх модулях.

### 5. Пустой diff молча подменялся изменениями рабочего дерева

`review_diff(diff="")` трактовал пустую строку как «diff не передан» и
брал изменения из git. Клиент, приславший пустой diff, получал отчёт по
**чужим** изменениям — это ловушка. Найдено e2e A7 (ожидался 400,
получен 200). Исправлено: `diff=None` — «не передан» (читаем git),
пустая строка — ошибка вызывающего. Тест
`test_empty_diff_is_not_silently_replaced_by_git`.

### 6. Кириллические заголовки ADR давали `adr.md`

Слаг строился ASCII-фильтрацией, поэтому «Выбор базы данных» терял все
символы и превращался в `adr.md` — файлы затирали друг друга, по имени
нельзя было понять содержание. Добавлена транслитерация RU→EN:
`vybor-bazy-dannyh`. Тесты `test_adr_slug_transliterates_cyrillic`,
`test_two_cyrillic_adrs_do_not_collide`.

### 7. Ловушка занятого порта в e2e (проверялся чужой сервер)

Первый прогон Part B показал HTTP 405 на всех POST-роутах. Причина
оказалась не в коде: на порту остался **процесс прошлого прогона**, новый
uvicorn порт не занял, и запросы уходили к старой сборке без роутов
ассистента (а GET попадал в SPA-фолбэк `/{path}` и возвращал HTML).
Проверка «прошла», ничего не проверив.

Исправлено: `wait_port_free()` ждёт освобождения порта и явно сообщает,
что Part B не может проверять свой сервер. Плюс `base` в `http()` читается
из глобальной переменной в момент вызова — дефолт `base=BASE`
вычислялся при импорте, и смена порта в `main()` не действовала
(`Connection refused`).

# Release Notes — day30-local-llm-service (день 30)

Ветка: `day30-local-llm-service` (от `day29-local-llm-tuning`).

## Что в релизе

**Локальная LLM как приватный сетевой сервис.** Задание дня 30: развернуть
локальную модель как сервис, к которому можно подключиться **с любого
устройства по сети**, с ограничениями по **rate limit** и **max context**.
Сделано, проверено на живой Ollama и на реальном сетевом интерфейсе.

Главное решение — **не открывать Ollama в сеть**. Ollama остаётся на
loopback, а наружу смотрит только **шлюз**: единственная точка, где есть
аутентификация, лимиты и учёт. Открытая в LAN Ollama не имеет ни ключей,
ни ограничений — любое устройство в сети заняло бы GPU целиком.

```
  ноутбук / телефон / планшет   (любое устройство в LAN)
        │  OpenAI-совместимый HTTP + Bearer <ключ клиента>
        ▼
  ┌──────────────────────────────────────────────┐
  │  Шлюз  (FastAPI Студии, слушает 0.0.0.0)     │
  │  1. аутентификация  → ключ → клиент          │
  │  2. allow_models    → модель разрешена?      │
  │  3. rate limit      → RPM / TPM (окно)       │
  │  4. подсчёт входа   → токены промпта         │
  │  5. max_context     → влезает?               │
  │       ├─ да  → как есть                      │
  │       └─ нет → LLM-сводка старых ходов       │
  │  6. прокси          → Ollama                 │
  │  7. учёт            → токены, запросы, отказ │
  └──────────────────────────────────────────────┘
        │  http://127.0.0.1:11434
        ▼
     Ollama (наружу не смотрит)
```

Сервис **OpenAI-совместимый**: подключается любым клиентом (curl,
Python `openai`, Continue, LobeChat, мобильные приложения) — достаточно
указать base_url и ключ, правок на стороне клиента не требуется.

| Что | Как |
|---|---|
| Подключение с устройства | `http://<LAN-IP>:8110/v1` + `Authorization: Bearer sk-local-…` |
| Аутентификация | API-ключ клиента; на диске только SHA-256, ключ отдаётся **один раз** |
| Rate limit | `rpm` / `tpm` на клиента, **скользящее окно** 60 с → 429 + `Retry-After` |
| Max context | лимит входа → **LLM-компрессия** старых ходов, затем честный 413 |
| Потолок ответа | `max_output_tokens` клиента перебивает запрос |
| Модели | `allow_models` (пусто = все, маска `gemma3:*`) |
| Учёт | запросы, токены, сжатия, отказы по каждому клиенту; лог отказов |
| UI | вкладка «Сервис» (🌐): адрес в LAN, клиенты, живые счётчики, отказы |

## Почему компрессия, а не жёсткий отказ

Задание допускает трактовать «max context» как отказ (400/413). Но это
ломает главный сценарий — **длинный диалог с другого устройства**:
телефон не умеет сжимать историю сам, и вместо ответа пользователь
получает стену. Поэтому лимит — не стена, а **триггер компрессии**:

| Ситуация | Поведение |
|---|---|
| вход ≤ `max_context` | запрос уходит **бит-в-бит**, компрессии нет, накладных нет |
| вход > `max_context` | старые ходы → **LLM-сводка**; system-промпт и последние ходы целиком |
| хвост сам больше лимита | хвост сокращается, но **последний вопрос пользователя сохраняется всегда** |
| после всего всё ещё > лимита | **413** с точными числами (никакой молчаливой обрезки) |

Компрессия **наблюдаема клиентом**: блок `gateway` в ответе и заголовки
`x-gateway-compressed` / `x-gateway-client` / `x-gateway-max-context`.
Сводка формулируется так, чтобы **не терять факты молча**: промпт
требует сохранить цель, ограничения, решения, имена, числа; отбросить
любезности. Инжектится отдельным `system`-сообщением с пометкой
`[СЖАТАЯ ИСТОРИЯ ДИАЛОГА]`.

## Находки живой проверки

Всё ниже найдено прогоном на живой Ollama 0.34.4 (M3 Max, 48 ГБ), а не
выведено умозрительно.

### 1. Reasoning-модели ломают сводку

`glm-4.7-flash:q4_K_M` (MoE + reasoning) на служебном вызове сводки:
через OpenAI-совместимый `/v1/chat/completions` отдаёт `content: ""`
(весь текст уходит в поле `reasoning` — бюджет потрачен на размышления),
а на большом контексте падает **HTTP 500** на нативном `/api/chat`.
`qwen3-coder:30b` на том же входе отдаёт готовую сводку (743 символа)
сразу — согласуется с замером дня 29.

**Решение:** сводка идёт **цепочкой моделей × два пути вызова**: сначала
модель диалога (уже прогрета в VRAM), затем `DEFAULT_SUMMARY_PREFERENCE`
(`qwen3-coder:30b`, `gemma3:27b`), затем остальные локальные (эмбеддеры
исключены). Итог — первый непустой ответ; иначе компрессия деградирует и
шлюз честно отдаёт 413.

### 2. Пустой ответ модели — наблюдаемое событие

Та же модель на обычном запросе с малым `max_output_tokens` возвращает
пустой `content` с `finish_reason: length` — бюджет кончился на
рассуждениях. Клиент получал пустую строку без объяснения. Теперь шлюз
помечает это: `gateway.empty_response`, `empty_reason`, `finish_reason`,
`reasoning_chars`.

### 3. Пограничный случай компрессии

Первая версия цикла останавливалась, если осталось `keep_recent`
сообщений, — **даже когда сам хвост был больше лимита**. Живой прогон
поймал это: сводка дала 510 токенов при лимите 500 → 413, хотя сократить
хвост было можно. Теперь хвост сокращается, но последнее сообщение
пользователя не выбрасывается никогда.

### 4. `lan_url` указывал на неверный порт

`GET /api/gateway/status` брал порт из константы, поэтому при запуске на
нестандартном порту отдавал клиенту **неверный адрес**. Теперь порт
берётся из фактического запроса; `GATEWAY_HOST`/`GATEWAY_PORT` остались
ручным override.

### 5. Пре-существующая проблема запуска из корня (не день 30)

`uvicorn studio.backend.main:app` из корня репозитория не работает: у
пакета `studio/` нет `__init__.py`, `main.py` уходит в fallback-импорт и
подхватывает устаревший корневой `agent.py` дня 7 → `ImportError`.
Воспроизводится на HEAD, к дню 30 не относится. В e2e сервер поднимается
штатным `--app-dir studio/backend` — структура репозитория не меняется.

### Найденный и исправленный баг: панель не убиралась

Первая версия адаптива **не работала на телефоне**: сайдбар оставался
статичным и перекрывал чат, войти в диалог было нельзя.

Причина — не в media-запросе, а в конфликте с базовой анимацией.
Базовое правило `.panel` вешает `animation: panel-in ... both`, а
`@keyframes panel-in` заканчивается на `transform: none`. CSS-анимации
имеют приоритет над обычными объявлениями, поэтому
`transform: translateX(-105%)` в мобильном блоке **игнорировался** —
панель оставалась на месте.

Исправление: в мобильном блоке добавлен явный сброс `animation: none`
для `.sidebar` (и для `.chat`, которому анимация на весь экран не
нужна), плюс закреплён `overflow-y: auto` для скролла внутри оверлея.

Проверено замером геометрии в реальном браузере (Chrome DevTools
Protocol, viewport 390×844), а не только чтением CSS:

| Момент | `sidebar.getBoundingClientRect().x` | Класс `mobile-open` |
|---|---|---|
| до клика | **−336** (за экраном, `animation: none`) | нет |
| после кнопки ☰ | **0** (панель видна) | да |
| после тапа по фону | **−336** | нет |

Урок: правила внутри `@media` не гарантируют результат, если базовое
правило анимирует то же свойство с `fill-mode: both`.

## Безопасность

**Сервис предназначен только для доверенной локальной сети.** TLS не
поднимается: трафик и ключ идут по HTTP открытым текстом — это осознанный
скоуп дня, наружу сервис не выставляется. Что защищено: без ключа — 401;
ключ не хранится на диске (только SHA-256, сравнение через
`hmac.compare_digest`); лимит нельзя обойти через `stream: true`; лимиты
не дают одному устройству занять GPU; Ollama недоступна из сети напрямую.

## 1. Параметры

Профиль задачи (`studio/backend/tuning.py`, `TaskProfile`):

| Параметр | `studio` (до) | `series` (после) | Почему |
|---|---|---|---|
| `temperature` | 0.7 | **0.2** | рекомендация — выбор из списка, а не творчество |
| `max_tokens` | 2048 | **512** | ответ — 3–5 коротких JSON-объектов |
| `num_ctx` | не задан (авто) | **8192** | KV-кэш выделяется под всё окно сразу |
| `seed` | не задан | **29** | воспроизводимость замеров |

**Ключевая находка: `num_ctx` не работает через OpenAI-совместимый
API.** Проверено на Ollama 0.34.4 — `/v1/chat/completions` игнорирует
`num_ctx` и в корне тела, и внутри `options`; `ollama ps` показывал
авто-`CONTEXT 32768`. Поэтому профиль с окном идёт **нативным**
`/api/chat` (`options.num_ctx`), а профиль без окна — прежним путём
(регрессия дней 11–28 сохранена). После фикса `ollama ps` показывает
`CONTEXT 8192`.

**Модели неравны по цене контекста в 8 раз.** Формула
`KV = 2 × слои × KV-голов × head_dim × токены × байты` на `num_ctx=8192`:
`qwen3-coder:30b` — **0.75 ГиБ** (4 KV-головы), `gemma3:27b` — 3.88 ГиБ
(16), `glm-4.7-flash` — 7.34 ГиБ (20). Отсюда выбор основной модели кейса.

## 2. Квантование

**Сравнение семейств на одном кванте (Q4_K_M)** — одинаковый профиль,
промпт, кандидаты и seed:

| Модель | Формат | Ограничения | p50 | Токены/с |
|---|---|---|---|---|
| `qwen3-coder:30b` (MoE) | 100 % | 99 % | **3.38 с** | **65.7** |
| `glm-4.7-flash` (MoE+reasoning) | 100 % | 100 % | 5.95 с | 41.2 |
| `gemma3:27b` (плотная) | 100 % | 98 % | 18.45 с | 12.6 |

`qwen3-coder` быстрее `gemma3:27b` в **5.5 раза** при том же качестве —
MoE (3B активных параметров) плюс в 8 раз более дешёвый KV-кэш. «Больше
параметров» ≠ «лучше для задачи».

**A/B одной модели по кванту** — профили `series_q4` (`gemma3:4b`,
Q4_K_M) и `series_q8` (`gemma3:4b-it-q8_0`), отличаются **только**

```bash

python scripts/series_eval.py --profiles series_q4,series_q8
```

⚠️ **Честное ограничение:** в этом окружении скачать Q8_0 не удалось —

профилей заведена, протестирована и запускается одной командой, но
цифры по ней **не сняты**. Вместо подмены оценкой приведён реальный
замер, который удалось сделать: сравнение семейств на фиксированном
кванте.

Ожидание из литературы (llama.cpp PR #1684): Q4_K_M ≈ +0.9 %
перплексии к F16 при ~29 % размера; Q8_0 ≈ +0.2 %, но **медленнее**
(bandwidth-bound: 50.9 против 71.9 т/с) — то есть выигрыш Q8_0 на этой
задаче, скорее всего, лежит в пределах шума.

## 3. Prompt-шаблон

`SERIES_SYSTEM_PROMPT` вместо «ассистента Студии» задаёт роль, четыре
жёстких правила, формат JSON и few-shot пример. Ключевые приёмы:

- **модель возвращает только `id` и `why`**, а название/год/жанры/IMDb
  подставляются **из каталога на сервере** — выдуманное название
  невозможно, выдуманный `id` ловится (`hallucination_rate`);
- **явная лазейка «вернуть пустой список»** — без неё модель,
  вынужденная выбирать, придумывает сериал (кейсы `g18–g20`:
  `empty_honesty` = 100 %);
- каталог и правила — по краям промпта (lost-in-the-middle).

## Находка: reasoning-модели возвращают пустой ответ

Замер вскрыл проблему, невидимую «на глаз»: профиль на
`glm-4.7-flash` дал **0 рекомендаций на всех 20 кейсах** при HTTP 200 и
`eval_count` ≈ 512. Модель пишет цепочку рассуждений в **отдельное поле
`thinking`**, и при исчерпанном `num_predict` поле `content` пусто.

```
без флага:  content=''                  thinking='1. **Analyze...'  eval_count=100
think=false: content='Привет.'                                       eval_count=4
```

Лечение — `think=False` в нативном запросе (в OpenAI-совместимом API
такого ключа нет). После фикса `series_glm` даёт 100 % формата и 100 %
соблюдения ограничений. Вывод: оптимизация параметров обязана включать
отключение размышления для reasoning-моделей.

## Что в релизе

**Запуск локальной LLM (Ollama) и добавление её в выбор модели.**
Локальные модели, развёрнутые на макбуке в Ollama, подключены к Студии
как **второй провайдер** рядом с GPustack. Провайдер выбирается по

идут на `GPUSTACK_BASE_URL`, локальные — на `OLLAMA_BASE_URL`. В

## Что в релизе

**Мини-чат с RAG + памятью задачи (production-like).** Чат хранит
историю диалога, при каждом новом вопросе ищет контекст в базе через
RAG, отвечает с учётом найденной информации и **всегда выводит
источники** (дни 21–24), плюс усиление — **память задачи
(task state)**: что пользователь уже уточнил, какие ограничения/термины
зафиксированы, какова цель диалога. Проверка задания — 2 длинных
сценария по 10–15 сообщений: ассистент не теряет цель и продолжает
выдавать ответы с источниками.

- **Память задачи per-диалог** (`task_state` в записи диалога,
  `memory.py`): `{goal: str, clarifications: [str], constraints: [str]}`
  — цель диалога, уточнения пользователя, зафиксированные
  ограничения/термины. `get_task_state` / `update_task_state` (весь
  объект, валидация) + `_task_state_of` (бэкворд-совместимость: старой
  записи без поля — пустое состояние); новое поле в `new_dialogue`,
  отдаётся `GET /api/dialogues` и `GET /api/dialogues/{id}`.
- **Инъекция в system-промпт** (`agent.build_task_memory_block`):
  блок «Память задачи (день 25)» — `Цель диалога: …` + списки
  «Уточнения пользователя» / «Зафиксированные ограничения и термины» +
  инструкция «Не теряй цель диалога: учитывай её и ограничения в
  каждом ответе»; пустое состояние — блок не добавляется. Не коллидирует
  с методом дня 13 `build_task_state_block(t, stage, ...)` (task-машина
  stage-агентов — другое имя).
- **Авто-обновление памяти** (`agent._update_task_state`): после хода
  один non-stream LLM-вызов (T=0, max_tokens=600,
  `enable_thinking: false`, паттерн авто-заголовка дня 11; НЕ в журнал

## Исправление после релиза (kb.py: кодировки + опечатки)

Два robustness-фикса `studio/backend/kb.py` (TDD, +9 тестов в
`tests/test_kb.py`; бэкенд после фикса — **548 тестов PASS**):

- **`KnowledgeBase._read_file` — авто-определение кодировки**
  (utf-8 строгий → cp1251 строгий → utf-8/`errors="replace"`). До
  фикса Windows-1251 (ANSI) файл пользователя молча декодировался
  как utf-8 c replace: **5826 символов U+FFFD** в индексе, файл
  невидим для кириллических запросов. Байты читаются один раз,
  нормализация \r\n / \r → \n сохранена, валидный utf-8
  декодируется идентично прежнему поведению; недекодируемый
  бинарный файл не роняет сборку (U+FFFD).
- **`_match_tf` — typo-допуск в BM25-матчинге** (оба терма ≥ 5
  симв., `_PREFIX_MIN`): матчем считается также равные первые 5
  символов **или** один терм = другой минус ровно один символ
  (новый хелпер `_one_del`, детерминированный O(len)) — «телфон» ↔
  «телефон» в обе стороны. Живой кейс: запрос «Как телфон был у
  бабки…» — BM25-нога дала 0 для easter-egg чанка, одна
  векторная нога уронила его ниже top-3 на большом корпусе.
  Точный матч, substring-инфлексии (`_SUBSTR_MIN`, «телефона» ↔
  «телефон»), короткие термы (< 5) и max-tf семантика не

# Release Notes — day13-task-state-machine (День 13b)

Ветка: [`day13-task-state-machine`](https://github.com/imarkelov/ai_advent_challenge/tree/day13-task-state-machine)
(от `day12-user-profile`).

## Что в релизе

**Задача = запрос пользователя в режиме «задача».** Тумблер чат/задача у поля
ввода (глобальный, состояние в `localStorage`) — в режиме «задача» отправленное
сообщение становится задачей, в режиме «чат» — обычным сообщением. Задача
пер-диалог.

### Unified FSM

Пайплайн `planning → execution (N work-шагов) → validation → done` и FSM из
6 значений: `planning | execution | validation | done | paused | failed`
(`paused`/`failed` — значения стадии, не флаги). Stage-агенты (Планировщик /
Исполнитель / Валидатор / Оркестратор) — один и тот же LLM из конфига с
разными system-промптами; пайплайн ведёт детерминированный код
(`agent.task_run`) — LLM не управляет FSM.

### Пошаговое исполнение

- Планировщик (1 LLM-вызов) — JSON-план из 1–5 work-шагов (best-effort
  парсинг; сбой/не-JSON — фолбэк в один шаг).
- Исполнитель — по LLM-вызову на work-шаг, стримингом (`step_updated` /
  `step_delta`).
- Валидатор — сверка с планом, вердикт `<verdict>pass|fail</verdict>`; fail →
  ретрай execution (максимум 1).
- Оркестратор — финальный синтез. Итого N+3 LLM-вызова (до 2N+3 с ретраем);
  stage/work-вызовы не пишутся в журнал `requests.json`.
- Пауза вступает на границе work-шага: текущий вызов доигрывается, следующий
  не начинается; фиксируется `context_snapshot`. Инструкция на паузе
  инжектится в промпт следующего шага/стадии и используется один раз.
  Продолжение — с сохранённого состояния (выполненные шаги/стадии не
  повторяются). Ошибка LLM — стадия `failed` + `task_failed`; повтор через
  «Продолжить»/новый run (auto-resume к первой невыполненной стадии).

### Карточка процесса в чате

Якорь карточки — user-сообщение с `task_id`. Живая карточка: спавн
stage-агентов (иконка, «спавн N с назад»), чек-лист work-шагов [✓]/[⏳]/[○],
живой бокс вывода текущего шага, сворачиваемые секции стадий (DONE — всё
свёрнуто, FAILED — секция ошибки развёрнута), кнопки Пауза/Продолжить/Повтор.
История после перезагрузки восстанавливается из маркеров сообщений
(`task_id`/`task_stage`/`task_step`).

### Контекст

Task-промпты собираются только из состояния задачи (`description`, `plan`,
`work_steps`, `instruction`); история сообщений чата в task-промпты не уходит.

## Исправления после основного релиза

- **Resume, пока стримится чужой run — не теряется.** Run-слот глобальный:
  если стримится run другого диалога (`taskRunning`), клик «Продолжить» ждёт
  освобождения слота (wait-loop, `sleep(400)`), затем `POST /api/task/resume` +
  `reloadTask` + `runTask`. Раньше resume отправлялся, пока слот занят, и
  состояние бэкенда рассинхронизировалось с фронтендом. `resumeInFlight`
  защищает от двойного клика (двойной «Продолжить»/«Повтор»). Ошибка (задача
  уже не resumable — 400-гард) → перечитывается авторитетная задача.
- **Карточка: кнопка «Продолжить» в зависшем состоянии.** Если задача в
  `execution`/`planning`, но run не идёт (`!running`) — показывается кнопка
  «Продолжить», которая запускает пайплайн через `POST /api/task/run`
  (восстановление из маркеров при перезагрузке).
- **Бренд сайдбара — «◆ День 13»** (было «День 11»), соответствует номеру
