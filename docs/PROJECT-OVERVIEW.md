# Обзор проекта «Студия» (AI Advent Challenge)

Этот документ — **точка входа в проект**: что это, из чего состоит, как
устроено и где что лежит. Он отвечает на вопросы вида «расскажи как
устроен проект», «какие модули в бэкенде», «как работает RAG». Для
истории по дням см. `README.md`, для релизов — `RELEASE.md`.

## Что это

**AI Advent Challenge** — учебный челлендж: 30+ дней, каждый день
добавляет одну возможность к AI-приложению. Результат — **«Студия»**:
веб-приложение с чатом, памятью, RAG по своим документам, MCP-инстру-
ментами, локальной LLM, сетевым шлюзом и ассистентом разработчика.

Проект демонстрирует полный путь от «чат с моделью» до рабочего
инструмента: контекст, память, персонализация, инварианты, tool-loop,
поиск по документам, цитаты, локальный инференс и автономные операции с
файлами.

## Технологический стек

| Слой | Технологии |
|---|---|
| Бэкенд | Python 3.14, FastAPI, uvicorn, httpx, python-dotenv |
| Фронтенд | React 19, TypeScript, Vite, без UI-библиотек (свой CSS) |
| Хранилище | JSON-файлы + SQLite (индекс RAG), stdlib |
| LLM | внешний API (GPustack) и локальный (Ollama) |
| Принцип | только stdlib + уже используемые пакеты, новых зависимостей не добавляется |

**Особенность:** проект сознательно избегает тяжёлых зависимостей — нет
PyYAML (frontmatter агентов парсится stdlib-ом), нет векторной БД
(индекс — SQLite с BLOB-векторами), нет UI-кита.

### Как модули связаны

```
  Фронтенд (React)
       │ HTTP / SSE
       ▼
  main.py ─────────── FastAPI, 87 роутов
       │
       ├── agent.py ────── StudioAgent: чат, tool-loop, память, RAG-инъекция
       │      ├── memory.py ── 3 слоя памяти + профили
       │      ├── mcp.py ───── MCP-инструменты (10 локальных серверов)
       │      ├── kb.py ────── поиск по базе знаний
       │      └── tuning.py ── профили инференса
       │
       ├── assistant.py ── ассистент (переиспользует agent + kb + git + CRM)
       │      ├── kb.py ────── отдельный индекс проекта
       │      ├── agents.py ── промпты агентов из agents/*.md
       │      └── cli.py ───── тот же функционал из терминала
       │
       └── gateway.py ──── сетевой шлюз к Ollama (для устройств в LAN)
```

**Ключевой принцип:** модули переиспользуют друг друга, а не дублируют.
`cli.py` — тонкая обёртка над `assistant.py`; `assistant.py` использует
`kb.py` для поиска; `gateway.py` использует `tuning.py` для профилей.

## Ключевые подсистемы

### Память (дни 11–13, 25)

Три слоя: **диалог** (история сообщений), **рабочая** (текущая задача,
цель, ограничения) и **долговременная** (факты между диалогами).
Плюс профиль пользователя per-диалог (имя, роль, тон, стоп-слова) и
«память задачи» — цель диалога, уточнения, зафиксированные ограничения.

### RAG — поиск по документам (дни 21–24, 28)

* **Корпус:** загрузки пользователя (`data/kb/uploads`) — индекс
  `data/kb/index.db`; **отдельно** документация и код проекта — индекс
  `data/kb/project.db`.
* **Chunking:** две стратегии — фиксированная (1200 символов, overlap
  200) и структурная (по markdown-заголовкам).
* **Эмбеддеры:** hash (офлайн, детерминированный), API (GPustack),
  локальный Ollama (`nomic-embed-text:v1.5`, 768 dim) — без ключей.
* **Поиск:** гибрид — векторная нога (косинус) + лексическая (BM25 по
  термам), фузия Reciprocal Rank; опционально реранкер
  (`qwen3-reranker-4b`) и порог `min_score`.
* **Цитаты:** ответ содержит источники (файл, секция, chunk_id) и
  verbatim-цитаты; при отсутствии релевантных чанков — режим «не знаю»
  без вызова LLM.

### Инварианты (день 14)

Глобальные жёсткие ограничения (архитектура, стек, бизнес-правила),
хранятся отдельно от диалога и всегда активны: инжектятся в системный
промпт + server-side гард, отказывающий при противоречии.

### MCP — инструменты (дни 16–20)

Model Context Protocol: реестр серверов (`studio/data/mcp_servers.json`),
транспорты **stdio** (subprocess, JSON-RPC построчно) и **http**
(streamable). 10 локальных однопроцельных серверов (1 сервер = 1
инструмент): `weather`, `news`, `habr_news`, `digest_make`, `digest_read`,
`digest_search`, `digest_summarize`, `task_create`, `task_get`,
`file_save`. LLM сама вызывает инструменты (tool-loop, кап 15 итераций).

### Локальная LLM (дни 26, 28, 29)

Второй провайдер рядом с внешним API: **Ollama** на `127.0.0.1:11434`.
Маршрутизация по имени модели (`_base_for`): локальные модели идут на
Ollama, остальные — на внешний API. Профили инференса задают
temperature, max_tokens и `num_ctx` (через нативный `/api/chat` —
OpenAI-совместимый эндпоинт `num_ctx` игнорирует).

### Шлюз локальной LLM (день 30)

`gateway.py` — OpenAI-совместимый сервис (`POST /v1/chat/completions`,
`GET /v1/models`) для доступа с других устройств в локальной сети.
Ollama остаётся на loopback, наружу смотрит только шлюз — единственная
точка с аутентификацией, лимитами и учётом. Ключи клиентов хранятся
хэшем (SHA-256), лимиты RPM/TPM (скользящее окно) и `max_context` с
автоматической LLM-компрессией старых ходов вместо жёсткого отказа.

### Ассистент разработчика и поддержки (дни 30–34)

`assistant.py` — четыре модуля в одном инструменте:

* **Вопросы по проекту** — RAG по документации и коду, ответ с
  источниками; плюс живой git-контекст (ветка, изменения, коммиты);
* **Ревью изменений** — разбор unified diff, 7 детерминированных
  проверок со severity и номером строки, сопоставление с документацией;
  работает **без LLM**;
* **Поддержка** — ответы по тикетам с персонализацией из CRM
  (`data/crm/users.json`, `tickets.json`), применённые поля видны;
* **Файловые сценарии** — `find_usages`, `update_docs`, `generate`
  (ADR/changelog/README), `check_invariants`, `diff_report`. Работают по
  **цели**, а не по шагам; пишут только в allow-list (`README.md`,
  `CHANGELOG.md`, `docs/`, `openspec/`); git только на чтение.

### CLI и агенты в Markdown (день 35)

`cli.py` даёт терминальный вход в те же модули: 10 команд, markdown или
`--json`, коды возврата 0/1, офлайн-режим `--no-llm`.

Агенты описаны в `agents/*.md` — **4 агента × 2 исполнения** (`.api.md`
для HTTP/Студии, `.cli.md` для терминала): `project-qa`, `code-review`,
`support`, `file-ops`. Формат: frontmatter (`name`, `execution`,
`description`, `tools`, `temperature`) + тело-промпт. Правка промпта не
требует правки кода.

## Запуск

```bash
# Бэкенд (из корня репозитория; у пакета studio/ нет __init__.py)
cd studio/backend
../../.venv/bin/python -m uvicorn main:app --host 127.0.0.1 --port 8000

# Фронтенд (разработка)
cd studio/frontend && npm install && npm run dev     # нужен Node >= 20

# Фронтенд (сборка; бэкенд раздаёт dist автоматически)
cd studio/frontend && npm run build

# CLI ассистента
.venv/bin/python studio/backend/cli.py --help
```

Конфигурация — `.env` в корне (образец: `.env.example`). Ключи внешнего
API, адрес Ollama, параметры шлюза.

## Проверка

```bash
# тесты бэкенда
.venv/bin/python -m pytest studio/backend/tests -q

# e2e по дням (Part A офлайн + Part B с живой LLM)
.venv/bin/python scripts/e2e_day31.py     # ассистент
.venv/bin/python scripts/e2e_day32.py     # CLI и агенты

# тесты фронтенда
cd studio/frontend && npm test
```

e2e-скрипты устроены одинаково: **Part A** — офлайн-проверки, которые
обязаны проходить всегда; **Part B** — проверки с реальной Ollama
(пропускаются, если она недоступна).

## Соглашения разработки

* **Язык:** документация, комментарии и сообщения об ошибках — русские;
  структурные заголовки спецификаций (SHALL/MUST) — английские.
* **Спецификации:** изменения оформляются через `openspec/`
  (proposal → design → tasks → spec).
* **TDD:** тесты пишутся до реализации; офлайн-тесты не ходят в сеть.
* **Регрессия:** каждое изменение проверяется полным прогоном тестов.
* **Диагностика:** тегированный `print("[Tag] …", flush=True)` вместо
  логгера (кроме CLI, где stdout — продукт, а не лог).
* **Ошибки:** русский текст, без traceback (он бесполезен в пайпе и CI).
* **Git:** ассистент и сценарии не делают мутаций — коммит за человеком.

## Нумерация дней челленджа

Каждый день челленджа — **отдельная git-ветка**. В текущей ветке
(`day30-34-dev-assistant`) таблица `README.md` содержит дни 1–9, 11–30,
35 — **строки «День 10» в ней нет**, но это не значит, что задания не
существует.

### День 10 существует — в ветке `origin/day10`

Задание дня 10: **управление контекстом через 3 стратегии**
(`sliding_window` / `sticky_facts` / `branching`) без LLM-сводки, с
Web-переключателем стратегий и бенчмарком. Ключевые элементы ветки:

* `ContextStrategy` (ABC) + `SlidingWindowStrategy`,
  `StickyFactsStrategy` (LLM-извлечение фактов), `BranchingStrategy`
  (чекпоинт + A/B-ветки);
* `ContextManager` + роуты `/agent/strategy`, персистентность
  `strategy_state` (whitelist + round-trip);
* `StrategyBenchmarkRunner` — сравнение 3 стратегий (mock-гейт, таблица);
* Web UI: селектор стратегий, факты, ветки A/B;
* `scripts/e2e_day10.py`.

Посмотреть: `git log --oneline origin/day10`, `git show origin/day10:README.md`.

### Почему строки дня 10 нет в README текущей ветки

Ветки `day10` нет локально (только `remotes/origin/day10`), и её
изменения в текущую линию не вливались — поэтому таблица README,
унаследованная от дня 9 → 11, строку пропускает. Это особенность
истории веток, а не отсутствие задания.

### Остальные пропуски

* **День 27** — ветки нет ни локально, ни в `origin`, задания в
  репозитории не найдено.
* **Дни 31–34** — отдельных веток нет: работа дней 30–34 велась в одной
  ветке `day30-34-dev-assistant` (день 30 — шлюз локальной LLM,
  `day30-local-llm-service`).

## Известные ограничения

* **TLS у шлюза нет** — он предназначен только для доверенной локальной
  сети; наружу выставлять нельзя.
* **Тестовые фикстуры** (`studio/backend/tests/fixtures/`) попадают в
  корпус проекта и могут всплывать в результатах поиска.
* **`studio/` не пакет** (нет `__init__.py`) — запуск идёт из
  `studio/backend`, а не как `python -m studio.…`.
* **Токены** считаются эвристикой `ceil(символы / 4)`, а не
  токенизатором конкретной модели.
