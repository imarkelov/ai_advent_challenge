## Purpose

Состояние задачи как конечный автомат (день 13): задача per-диалог —
пайплайн stage-агентов (Планировщик → Исполнитель → Валидатор →
Оркестратор) под управлением детерминированного оркестратора; вход —
вкладка «Задача» в панели «Контекст». Состояние формализовано per-диалог
(стадия, пауза, описание, выводы стадий), пауза — на границе стадии с
инструкцией, продолжение — с сохранённого состояния, без повторных
объяснений.

## ADDED Requirements

### Requirement: Состояние задачи per-диалог

Система SHALL хранить состояние задачи в записи каждого диалога: стадия
`planning` | `execution` | `validation` | `done`, флаг `paused`, описание
задачи, outputs выполненных стадий, instruction (правка, данная на паузе),
счётчик повторов и отметку ошибки. Задача MUST принадлежать диалогу:
переключение диалога переключает её состояние. Состояние MUST переживать
перезапуск сервера. Для диалога, созданного до внедрения задачи, задача
SHALL считаться неактивной (поле отсутствует). Задача одного диалога
MUST NOT влиять на другие диалоги. Обычный чат (профиль дня 12, слои
памяти дня 11) MUST остаться без изменений.

#### Scenario: Состояние переживает перезапуск

- **WHEN** задача диалога на стадии `execution` (output Планировщика сохранён) и сервер перезапущен
- **THEN** состояние задачи этого диалога восстанавливается: та же стадия, тот же output, и продолжение работает без повторного планирования

#### Scenario: Задача переключается вместе с диалогом

- **WHEN** в диалогах A и B ведутся разные задачи и пользователь переключается с A на B
- **THEN** UI показывает состояние задачи диалога B; пайплайн A заморожен в своём состоянии

#### Scenario: Старый диалог без поля задачи

- **WHEN** загружен `dialogues.json` с диалогом, у которого нет поля задачи
- **THEN** задача этого диалога считается неактивной и данные диалога не повреждаются

### Requirement: Stage-агенты и FSM-переходы

Пайплайн задачи SHALL состоять из стадий-состояний конечного автомата
`planning` → `execution` → `validation` → `done`. Каждую стадию SHALL
исполнять отдельный stage-агент: тот же LLM из конфига со своим
system-промптом. Планировщик (planning) по описанию задачи составляет план
шагов; Исполнитель (execution) выполняет работу по плану; Валидатор
(validation) сверяет работу с планом и выдаёт вердикт; на `done`
Оркестратор-синтез собирает outputs всех стадий в единый финальный ответ.
Переходы между стадиями SHALL контролировать детерминированный
оркестратор бэкенда; LLM MUST NOT управлять состоянием FSM. В system-промпт
каждого stage-агента SHALL инъектироваться: описание задачи, outputs
выполненных стадий, ожидаемое действие и (если задана) instruction.
Ошибка LLM-вызова стадии MUST NOT ломать диалог: задача сохраняется в
состоянии с отметкой ошибки на текущей стадии, повтор — действием
«продолжить» (повтор той же стадии).

#### Scenario: Полный прогон стадии за стадией

- **WHEN** запущен пайплайн задачи
- **THEN** вызовы LLM идут по стадиям в порядке planning → execution → validation → синтез, system-промпт каждого stage-агента содержит описание задачи и outputs предыдущих стадий, финальный ответ — синтез Оркестратора

#### Scenario: Ошибка стадии не ломает диалог

- **WHEN** LLM-вызов стадии завершился ошибкой API
- **THEN** задача сохранена на этой стадии с отметкой ошибки, чат-история диалога не повреждена, повтор стадии возможен действием возобновления

### Requirement: Валидация и повтор выполнения

Валидатор SHALL выдавать вердикт `pass` | `fail` отдельной машиночитаемой
меткой в своём ответе (best-effort парсинг: отсутствие/сбой метки
интерпретируется как `pass`). При вердикте `fail` система SHALL повторить
стадию `execution` один раз, передав Исполнителю вердикт с замечаниями
Валидатора как фидбэк. Повторный `fail` MUST NOT приводить к бесконечному
циклу: задача завершается на `done` с сохранённым вердиктом, который
попадает в синтез финального ответа.

#### Scenario: Первый fail → повтор execution

- **WHEN** Валидатор вернул `fail` с замечаниями
- **THEN** Исполнитель вызывается повторно, его system-промпт содержит план, первую работу и замечания Валидатора

#### Scenario: Второй fail → завершение с пометкой

- **WHEN** повторная валидация снова вернула `fail`
- **THEN** цикл не продолжается, задача переходит в `done`, вердикт `fail` сохранён и учтён в финальном ответе

#### Scenario: Метка вердикта отсутствует или битая

- **WHEN** ответ Валидатора не содержит распознаваемой метки вердикта
- **THEN** задача переходит в `done` как при `pass`, без ошибки пайплайна

### Requirement: Пауза и продолжение на любом этапе

Пользователь SHALL иметь возможность остановить задачу на любом этапе
кнопкой Стоп в диалоговом окне и возобновить работу кнопкой Продолжить.
Стоп SHALL вступить в силу на границе стадий: текущий LLM-вызов стадии
доигрывается, следующий запуск стадии не происходит, состояние задачи
помечается как `paused` на границе (выполненная стадия сохранена).
При возобновлении пайплайн SHALL продолжить с первой невыполненной стадии,
получив всё необходимое из сохранённого состояния задачи — пользователь
MUST NOT объяснять контекс заново. Обычные сообщения чата во время активной
непаузанной незавершённой задачи не выполняются: `POST /api/chat` отвечает
200 с SSE-событием `error` («Задача выполняется…»), сообщение пользователя
не сохраняется; на паузе чат работает как обычно.

#### Scenario: Пауза на стадии execution

- **WHEN** задача на стадии execution и пользователь нажал Стоп
- **THEN** текущий вызов Исполнителя завершается и его output сохранён, стадия не переходит в validation, состояние `paused`

#### Scenario: Продолжение без повторных объяснений

- **WHEN** задача на паузе после execution и пользователь нажал Продолжить
- **THEN** следующая стадия (validation) получает в system-промпте описание задачи, план, work-выполнение и instruction — без новых сообщений пользователя с контекстом

#### Scenario: Чат заблокирован во время задачи

- **WHEN** задача активна и не на паузе и клиент шлёт `POST /api/chat`
- **THEN** ответ 200 с SSE-событием `error` («Задача выполняется…»), сообщение не сохраняется; на паузе чат работает как обычно

### Requirement: Instruction на паузе

Пока задача на паузе пользователь SHALL иметь возможность дать instruction
(правку/уточнение): поле инструкции во вкладке «Задача» принимает её без
LLM-вызова.
Instruction SHALL сохраняться в состоянии задачи и SHALL быть инъектирована
в system-промпт следующей выполняемой стадии при возобновлении. Instruction
для непаузанной или неактивной задачи — ошибка 400.

#### Scenario: Instruction влияет на следующую стадию

- **WHEN** задача на паузе после planning, пользователь задал instruction «шаг 3 сделать иначе» и возобновил задачу
- **THEN** system-промпт стадии execution содержит план и instruction, и instruction очищается из состояния после применения

#### Scenario: Instruction вне паузы отклоняется

- **WHEN** `POST /api/task/instruction` при непаузанной (или отсутствующей) задаче
- **THEN** 400 с RU-сообщением, состояние задачи не меняется

### Requirement: SSE-протокол пайплайна

Пайплайн задачи SHALL выполняться в отдельном SSE-эндпоинте
`POST /api/task/run` и стримовать события: начало стадии
(`stage` с именем стадии и агента), завершение стадии (`stage_done` с
output), завершение задачи (`task_done` с финальным ответом
Оркестратора), паузу (`task_paused` с достигнутой границей) и ошибку
(`error`). Output стадии SHALL сохраняться в истории сообщений диалога с
меткой стадии/агента; финальный ответ — как обычное assistant-сообщение.
Старый протокол `POST /api/chat` (delta/done/error) MUST остаться без
изменений.

#### Scenario: Стрим полного прогона

- **WHEN** клиент запустил `POST /api/task/run` для готовой к запуску задачи
- **THEN** последовательность событий: `stage`(planning) → `stage_done`(planning) → `stage`(execution) → `stage_done`(execution) → `stage`(validation) → `stage_done`(validation) → `task_done` (финальный синтез); история диалога содержит stage-сообщения и финальный ответ

#### Scenario: Стрим останавливается на паузе

- **WHEN** во время пайплайна задан стоп и текущая стадия завершена
- **THEN** стрим завершается событием `task_paused` на границе стадии, дальнейшие стадии не выполняются

### Requirement: REST API задачи

Система SHALL предоставлять (все тела с `dialogue_id`; 404 — диалог не
найден, 400 — RU-сообщение):
- `POST /api/task/start` — `{"dialogue_id", "description"}`: создать задачу
  (stage `planning`, paused=false); при любой активной задаче диалога
  (включая завершённую `done`) — 400 (сначала `reset`);
- `POST /api/task/run` — SSE-пайплайн: выполнять невыполненные стадии до
  `done`/паузы/ошибки;
- `POST /api/task/pause` — установить паузу (вступает на границе стадии);
- `POST /api/task/resume` — снять паузу;
- `POST /api/task/instruction` — `{"dialogue_id", "text"}`, только на паузе;
- `POST /api/task/reset` — завершить текущую задачу и сбросить состояние
  (готовность к новой задаче);
- `GET /api/task?dialogue_id=` — текущее состояние задачи (или
  «неактивна»).

Состояние задачи SHALL включаться в ответы выдачи диалогов
(`GET /api/dialogues`, `GET /api/dialogues/{id}`).

#### Scenario: Запуск задачи

- **WHEN** `POST /api/task/start` с описанием для диалога без задачи
- **THEN** 200: задача активна, стадия `planning`; последующий `POST /api/task/run` начинает пайплайн

#### Scenario: Двойной start отклоняется

- **WHEN** `POST /api/task/start` при любой активной задаче (включая `done`)
- **THEN** 400 с RU-сообщением, старая задача не сбрасывается

#### Scenario: Reset готовит к новой задаче

- **WHEN** `POST /api/task/reset` для завершённой задачи
- **THEN** состояние задачи очищено; следующий `start` создаёт новую задачу со стадией `planning`

#### Scenario: Состояние в выдаче диалогов

- **WHEN** клиент запрашивает диалог (GET)
- **THEN** ответ содержит состояние задачи (стадия, paused, описание, outputs, вердикт) либо отметку об отсутствии задачи

### Requirement: UI: вкладка «Задача», статус работы в чате

Вход в задачу — вкладка «Задача» (запуск по описанию, instruction на
паузе). ChatPanel SHALL иметь: кнопки Стоп/Продолжить в шапке (видимы
при активной задаче: стоп во время выполнения, продолжение на паузе),
статус-строку стадий (текущая стадия — подсвечена, пройденные — ✓) и
чип «задача» на stage-сообщениях; во время выполнения стадии поле ввода
пользователя блокируется.
Панель «Контекст» SHALL содержать вкладку «Задача»: запуск задачи по
описанию, стадии с outputs, вердикт валидации, instruction на паузе,
paused/error-индикаторы и кнопки Пауза / Продолжить / Новая задача.
Вкладка и статус-строка SHALL обновляться при переключении диалога.

#### Scenario: Статус работы агента виден в чате

- **WHEN** пайплайн выполняется и стадия execution запущена
- **THEN** статус-строка ChatPanel показывает работающего агента стадии execution; после `stage_done` стадия отмечена выполненной, поле ввода разблокировано только при паузе/завершении

#### Scenario: Вкладка показывает состояние задачи

- **WHEN** пользователь открывает вкладку «Задача» для диалога с активной задачей
- **THEN** показаны описание, выполненные стадии с их outputs, текущая стадия, вердикт (если есть) и доступные действия (Пауза/Продолжить/Новая задача по состоянию)

#### Scenario: Stage-outputs в истории чата

- **WHEN** стадия завершена
- **THEN** в истории диалога сообщение stage-агента с чипом «задача», финальный ответ Оркестратора — обычное assistant-сообщение

### Requirement: Проверка (тесты и e2e)

Репозиторий SHALL содержать тесты, доказывающие: (1) FSM-цикл — полный
прогон planning → execution → validation → done через mock-LLM
(MockTransport с сценарными stage-ответами), инъекция state в
system-промпты stage-агентов, синтез финального ответа; (2) валидация —
fail → повтор execution с фидбэком, второй fail → done с пометкой,
битая/отсутствующая метка вердикта → pass без ошибки; (3) пауза/продолжение
— стоп на границе стадии, возобновление с сохранённого состояния без новых
сообщений, instruction на паузе попадает в следующий stage-промпт и
отклоняется вне паузы; (4) API — 400/404 по всем эндпоинтам, гард
`/api/chat` (SSE `error`); (5) UI — TaskTab и ChatPanel (статус-строка,
Стоп/Продолжить, чип «задача», блокировка ввода; Vitest/Testing
Library). `scripts/e2e_studio.py` SHALL быть расширен: детерминированное
ядро (start → run до паузы через API → instruction → resume → done →
reset) + live best-effort полный пайплайн (stage-события в SSE, outputs в
истории диалога, финальный синтез); exit 0 = PASS/SKIP, 1 = FAIL.

#### Scenario: Офлайн-прогон FSM

- **WHEN** прогоняется офлайн-тест пайплайна с mock-LLM
- **THEN** все стадии выполнены в порядке, system-промпты stage-агентов содержат предыдущие outputs, задача в `done`, финальный ответ — синтез

#### Scenario: E2E прогон задачи

- **WHEN** запущен `python scripts/e2e_studio.py` (GPustack доступен)
- **THEN** пройден поток: start → SSE-пауза на границе стадии → instruction → resume → task_done → reset; exit 0
