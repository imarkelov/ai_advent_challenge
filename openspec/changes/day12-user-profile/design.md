# Design: day12-user-profile

## Context

Студия дня 11: FastAPI-бэкенд (`studio/backend/`) + React 19/Vite/TS
фронтенд (`studio/frontend/`). Ключевые точки (ветка `day11-studio`):

- `memory.py` — `MemoryStore`: диалоги (ST, `dialogues.json`, запись
  `{"id","title","created","messages":[...]}`), WM per-диалог
  (`working.json`), LT глобальный (`longterm.json`), `toggles.json`;
  `build_memory_blocks()` (:309) собирает текст блоков WM→LT;
  атомарная запись + `threading.Lock` уже есть.
- `agent.py` — `StudioAgent`: `build_payload(dialogue_id)` (:167-200)
  собирает `system = system_prompt + blocks + MEMORY_RULE (+заметка выкл.
  слоёв)` + историю; `ask_stream` (:204-294) — append user msg, авто-
  заголовок, конфликт-гард, SSE; `_generate_title` (:425) — паттерн
  best-effort нестримингового LLM-вызова (thinking-off, fallback).
- `main.py` — raw-dict body, ручная валидация, RU-ошибки 400/404;
  `GET /api/rules` показывает live-состояние system-промпта.
- Фронтенд: три панели (App.tsx); правая — табы Память/Токены/Запрос
  (`ContextPanel.tsx:8-12`); чат — `ChatPanel.tsx` (submit :33, селект
  модели :50); состояние и все API-вызовы — `state.tsx`; HTTP — `api.ts`
  (body `/api/chat` = `{dialogue_id, message}`, :69).
- **Пользователей нет**: single-tenant, единственная идентичность =
  dialogue_id. Профиль привязываем к диалогу (решение brainstorm: вариант B).

Паттерны, которые копируем: best-effort LLM-вызов (`_generate_title`),
raw-dict body с ручной валидацией (main.py), табы ContextPanel по образцу
MemoryTab.

## Goals / Non-Goals

**Goals:**
- Профиль per-диалог (4 поля + статус) в `dialogues.json`, переживает
  рестарт, переключается с диалогом.
- State machine инициализации: `pending` (приглашение → интервью /
  вручную / отказ) → `active` | `declined`; `reset` в любой момент.
- Автоматическая инъекция `active`-профиля в system-промпт каждого
  запроса диалога без изменения тела `/api/chat`.
- UI: вкладка «Профили» + бейдж-подсказка при `pending`/`declined`.
- Офлайн-тесты (fake-LLM) + e2e-прогон инициализации.

**Non-Goals:**
- Мультипользовательность/аутентификация (одна студия, один пользователь).
- Изменение слоёв памяти, тумблеров, правила конфликтов WM/LT и
  server-side гарда — профиль это предпочтения, не факты; в
  `_detect_memory_conflict` и `MEMORY_RULE` не участвует.
- Тумблер вкл/выкл профиля (статусы `active`/`declined` уже дают
  «вкл/выкл»).
- LLM-обучение/фитинг модели на профиле (только инъекция в промпт).

## Decisions

### D1. Хранение — поле `profile` в записи диалога, не отдельный файл

`dialogues.json`: запись диалога получает
`"profile": {"status": "pending"|"active"|"declined", "interview": bool,
"name": str, "role": str, "tone": str, "taboos": str}`. Отсутствие поля
= `pending` (бэкворд-совместимость).

Почему не `profiles.json` (как `working.json`): профиль 1:1 с диалогом —
отдельный файл потребовал бы синхронизации при удалении диалога
(паттерн `delete_dialogue` уже чистит WM, но ещё один внешний файл = ещё
один источник рассинхрона); запись в диалоге удаляется/переключается
автоматически. Методы (`profile_get/set/action/reset`) добавляются в
`MemoryStore` под существующим `Lock` — единая точка атомарности.

### D2. State machine в `ask_stream`, детерминированные сообщения выбора

Категории ответа на ход (проверка до LLM, по статусу профиля):

1. `status == "pending"` и не ожидаем интервью → ответ = **шаблонное**
   (без LLM) приглашение: «Нужна инициализация профиля… выберите:
   заполнить вручную / провести интервью / отказаться».
   Ответ сохраняется в диалог как assistant-сообщение.
2. `pending` + `interview == True` → ответ пользователя трактуется как
   ответы на 4 вопроса → нестриминговый LLM-вызов извлечения (см. D3).
   Успех → `active`, ответ = короткое подтверждение + продолжение темы.
   Сбой → `interview` остаётся `True`, ответ = просьба повторить.
3. `pending`, `interview == False`, сообщение не содержит ни маркер
   интервью (интерв*), ни отказа (отказ/не надо/нет, спасибо-варианты),
   ни «вручную» → повторное приглашение (детерминированно).
   «вручную» → ответ с указанием на вкладку «Профили» (статус `pending`,
   пользователь заполняет форму; сохранение формы → `active`).
4. `active` / `declined` → обычный поток LLM как сейчас.

Почему детерминированно, а не «LLM решает, что ответить»: предсказуемые
офлайн-тесты, ноль лишних LLM-вызовов, мелкие модели (glm/deepseek flash)
не должны управлять служебным потоком. Маркеры — простое ключевое
соответствие по нижнему регистру; неоднозначность покрывается повторным
приглашением (сценарий из spec).

### D3. Экстракт профиля — best-effort LLM-вызов по паттерну `_generate_title`

Нестриминговый `chat/completions`: system-инструкция «извлеки 4 поля,
верни JSON `{name, role, tone, taboos}`, ничего лишнего», user = ответ
пользователя. `max_tokens` небольшой (~400), у reasoning-моделей первая
попытка с `chat_template_kwargs: {"enable_thinking": false}` (копировать
логику `_generate_title`). Парсинг: `json.loads` с доп. попыткой вырезать
JSON-объект из ответа (паттерн авто-заголовка). Не-JSON / пустое → сбой →
просьба повторить (статус не меняется). Запрос НЕ пишется в
`requests.json` (служебный, как заголовок).

Альтернатива — сохранить «как есть» (весь ответ в поле `tone`):
отвергнута, теряет структуру, заданные 4 поля не заполнились бы.

### D4. Инъекция — отдельный блок в `build_payload`, до блоков памяти

`build_payload`: после `cfg["system_prompt"]` добавить
`profile_block = build_profile_block(dialogue_id)` — строку
`\n\nПрофиль пользователя:\n- Имя: …\n- Роль и сфера: …\n- Тон и стиль: …\n-
Стоп-слова/табу: …` + при непустых табутах `\nИзбегай: <табу>`. Блок
добавляется только при `status == "active"` и хотя бы одном непустом поле.
Порядок: базовый промпт → профиль → память → MEMORY_RULE — профиль ближе
к «личности», память к «фактам».

`GET /api/rules` дополняется полем `profile_block` (+`profile_status`) —
наблюдаемость «что автоматически учитывается» (проверка задания).
Тело `/api/chat` не меняется.

### D5. API — 2 эндпоинта + профиль в выдаче диалогов

- Профиль возвращается в `GET /api/dialogues` и `GET
  /api/dialogues/{id}` (поле `profile` у каждой записи).
- `POST /api/profile` — ручное сохранение 4 полей (все str, могут быть
  пустыми; непустое → `active`, `interview` сбрасывается). Валидация:
  ровно 4 ключа значений str, иначе 400 RU; 404 — диалог.
- `POST /api/profile/action` — `interview` (поставить `interview=True`,
  статус остаётся `pending`), `decline` (`declined`), `reset` (поля
  очищены, `pending`, `interview=False`). 400/404 — как в D5 spec.

Почему не «внутри `/api/memory/*`»: профиль — не слой памяти (нет
тумблера, нет k/v-семантики); отдельный префикс чище и не ломает
существующие маршруты.

### D6. Фронтенд — вкладка «Профили» + бейдж, состояние в `state.tsx`

- `ContextPanel.tsx`: 4-й таб «Профили» → новый компонент
  `ProfileTab.tsx` (каркас — `MemoryTab.tsx`: карточка статуса, 4
  textarea/input, кнопки «Интервью» / «Заполнить заново» / «Отказаться»;
  при `pending` — подсказка, как продолжить).
- `state.tsx`: профиль приходит вместе с `GET /api/dialogues` (уже
  перечитывается после `done` и при активации диалога — обновление
  бесплатно); действия `saveProfile`, `profileAction` (POST-хелперы в
  `api.ts`); `refreshPanels` после `done` перечитывает профиль.
- `ChatPanel.tsx`: бейдж в шапке при `status ∈ {pending, declined}`
  активного диалога: «Профиль не заполнен — после инициализации ответы
  будут точнее и лучше»; клик/кнопки → «Интервью» / «Вручную» (активирует
  вкладку «Профили»).
- `api.ts`: `chatStream` не меняется (body тот же).

### D7. Тесты

- `tests/test_memory.py`: profile-методы (get/set/action/reset,
  бэкворд-совместимость, удаление с диалогом).
- `tests/test_agent.py`: `build_payload` по статусам (active с табуб/без,
  pending/declined — блока нет, остальные блоки как раньше); state machine
  `ask_stream` на fake-LLM (`httpx.MockTransport`, как сейчас):
  приглашение → нераспознанный ответ → интервью → экстракт (успех/сбой) →
  `active`; отказ → `declined` + обычные ответы без напоминания; reset.
- `tests/test_api.py`: 2 эндпоинта (200/400/404), профиль в выдаче
  диалога, `GET /api/rules` с `profile_block`.
- Фронтенд (Vitest): ProfileTab (поля, кнопки, статусы), бейдж
  ChatPanel (появление/исчезновение).
- `scripts/e2e_studio.py`: блок «Профиль» — новый диалог → приглашение →
  `interview` action → ответ на вопросы → `active` → запрос, JSON запроса
  (журнал) содержит блок профиля; чат-часть SKIP при недоступном GPustack.
  Проверка задания «разные профили → разные ответы»: два диалога, разные
  `active`-профили (тон/табу), один вопрос, ответы различаются по
  персонализации (live-чек best-effort: табу-слово не должно встречаться
  в ответе диалога с табу).

### D8. Гард табу-слов — server-side, по паттерну конфликт-гарда дня 11

В `ask_stream` (после pending-state machine, перед LLM-вызовом, только для
`active`-профиля) — `_detect_taboo(dialogue_id, message)`: табу-поле
режется по `,`/`;`, trim, токены короче 2 символов пропускаются; если токен
встречается в `message.lower()` → в конец `messages` добавляется
system-напоминание: «запрос содержит табу-слово X из профиля пользователя —
вежливо откажись в задействующей его части (лёгкий юмор, ссылка на
конкретное табу-слово) и сообщи, что решение принято по профилю» — тот же
паттерн, что `_detect_memory_conflict` + system-сообщение в хвосте
`ask_stream` (день 11).

Почему system-напоминание, а не шаблонный отказ: отказ, составленный LLM,
вписывается в контекст диалога (аргумент дня 11 — шаблонный отказ ломает
разговор). Почему детерминированный детект: без LLM-вызова и записи в
журнал, офлайн-тестируемо (принцип D2). Отношение к D4: строка «Избегай:»
остаётся (агент не использует табу в собственном тексте); D8 — реакция на
упоминание табу пользователем. Состояние профиля гардом не меняется; с
гардом конфликтов WM/LT не пересекается (разные источники: профиль vs
память).

Риск: подстрочные false-positive (табу «мат» совпадает внутри «материал»)
→ приемлемо для обучающей студии: отказ мягкий, обратим и объясним
(ссылка на конкретное табу-слово).

## Risks / Trade-offs

- [Мелкие модели плохо извлекают JSON из свободного ответа] → паттерн
  `_generate_title` (thinking-off, fallback-парсинг, повторная попытка);
  сбой не ломает диалог (статус `pending` сохраняется, можно
  заполнять вручную).
- [Ключевое сопоставление маркеров «интервью/вручную/отказ» ловит false
  positive/miss] → пропущенный маркер = повторное приглашение (безопасно);
  ложный срабатывающий «отказ» отменяется кнопкой «Заполнить заново»
  (`reset`).
- [«Интервью» съедает первый реальный запрос] → решение задания (A3):
  в `pending` запрос по существу не выполняется; документировано в spec.
- [Профиль разрастается → рост system-промпта] → 4 текстовых поля,
  оценка токенов уже есть в `layer_stats`-паттерне; при необходимости —
  ограничение длины поля в UI (не в этой итерации).
- [Старые `dialogues.json` без `profile`] → отсутствие поля = `pending`,
  миграция не нужна; первый запрос в старом диалоге получит приглашение —
  ожидаемое поведение.

## Migration Plan

1. Бэкенд: `memory.py` (profile-методы) → `agent.py` (state machine,
   экстракт, `build_profile_block`) → `main.py` (эндпоинты, `/api/rules`).
   На каждом шаге — офлайн-тесты зелёные.
2. Фронтенд: `api.ts`/`state.tsx` → `ProfileTab.tsx` + таб → бейдж
   `ChatPanel`. Vitest зелёный.
3. E2E-расширение + live-прогон на 3 моделях.
4. README: секция «День 12» (release notes + API-таблица).

Rollback: изменения аддитивные (новое поле JSON, новые маршруты, новые
компоненты); откат = revert ветки. Данные без `profile`-поля работают как
раньше.
