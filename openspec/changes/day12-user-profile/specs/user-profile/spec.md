## Purpose

Персонализация студия (день 12): профиль пользователя per-диалог (имя,
профессиональная роль и сфера, тон и стиль общения, стоп-слова/табу) с
инициализацией через интервью или вручную и автоматической инъекцией в
system-промпт каждого запроса — чтобы ответы адаптировались под пользователя.

## ADDED Requirements

### Requirement: Профиль пользователя per-диалог

Система SHALL хранить профиль пользователя в записи каждого диалога: четыре
текстовых поля (имя пользователя, профессиональная роль и сфера, тон и стиль
общения, стоп-слова/табу) и статус `pending` | `active` | `declined`.
Профиль MUST принадлежать диалогу: переключение на другой диалог показывает
и использует профиль этого диалога. Профиль MUST переживать перезапуск
сервера. Для диалога, созданного до внедрения профиля, статус SHALL быть
`pending` (поле профиля отсутствует). Профиль одного диалога MUST NOT
влиять на другие диалоги.

#### Scenario: Профиль переживает перезапуск

- **WHEN** в диалоге создан профиль (статус `active`) и сервер перезапущен
- **THEN** профиль этого диалога присутствует с теми же полями и статусом

#### Scenario: Профиль переключается вместе с диалогом

- **WHEN** в диалоге A и B активны разные профили и пользователь переключается с A на B
- **THEN** UI показывает профиль диалога B, и следующий запрос выполняется с блоком профиля B

#### Scenario: Старый диалог без поля профиля

- **WHEN** загружен `dialogues.json` с диалогом, у которого нет поля профиля
- **THEN** статус профиля этого диалога считается `pending` и данные диалога не повреждаются

### Requirement: Инициализация профиля при первом запросе

Для диалога со статусом `pending` система SHALL не выполнять запрос по
существу на первом ходе, а SHALL отправить приглашение к инициализации с
тремя вариантами: заполнить вручную, провести интервью, отказаться.
Первоначальный запрос пользователя при этом не повторять и не отвечать на
него. Ответ пользователя, не совпадающий ни с одним вариантом, SHALL
повлечь повторное приглашение. Статус `pending` MUST NOT инъектировать
профиль в запрос.

#### Scenario: Первый ход нового диалога

- **WHEN** пользователь отправляет первый запрос в новом диалоге (статус `pending`)
- **THEN** ответ агента — приглашение выбрать способ инициализации (вручную / интервью / отказаться), без ответа по существу запроса

#### Scenario: Нераспознанный ответ

- **WHEN** на приглашение инициализации пользователь отправляет сообщение, не содержащее ни один из трёх вариантов
- **THEN** агент повторно предлагает инициализацию

### Requirement: Интервью для создания профиля

При выборе интервью агент SHALL задать все четыре вопроса профиля одним
сообщением. Из следующего ответа пользователя система SHALL извлечь
структурированный профиль отдельным нестриминговым LLM-вызовом (best-effort,
не входящим в журнал основного ответа) и SHALL установить статус `active`.
Сбой извлечения (ошибка API, не-JSON) MUST NOT ломать диалог: агент
SHALL вежливо попросить повторить ответ, статус остаётся `pending`.

#### Scenario: Профиль создан по интервью

- **WHEN** пользователь выбрал интервью, ответил на все четыре вопроса одним сообщением и извлечение удалось
- **THEN** профиль диалога заполнен извлечёнными значениями, статус `active`, следующий запрос содержит блок профиля

#### Scenario: Неудачное извлечение

- **WHEN** LLM-вызов извлечения профиля упал или вернул невалидный результат
- **THEN** диалог не сломан, профиль не создан, агент просит повторить ответ на вопросы, статус `pending`

### Requirement: Ручное заполнение профиля

Система SHALL позволять заполнить или изменить все четыре поля профиля
диалога явным действием пользователя (UI-форма или API), без LLM-вызова.
Сохранение непустого профиля SHALL установить статус `active`. Не-str
значения полей — ошибка 400.

#### Scenario: Ручное сохранение

- **WHEN** пользователь заполнил форму профиля (хотя бы одно непустое поле) и сохранил
- **THEN** профиль диалога содержит эти значения, статус `active`, следующий запрос содержит блок профиля

#### Scenario: Валидация полей

- **WHEN** запрос сохранения профиля содержит не-textual значение поля или неизвестное поле
- **THEN** ответ 400 с RU-сообщением, профиль не меняется

### Requirement: Отказ от инициализации

Пользователь SHALL иметь возможность отказаться от инициализации профиля;
статус становится `declined`. В диалоге `declined` запросы выполняются как
обычно (без блокировки и без напоминаний в тексте ответа), профиль не
инъектируется. Система SHALL показывать в UI постоянную подсказку о том, что
после инициализации ответы будут точнее и лучше, с возможностью вернуться к
инициализации (вручную или интервью) по действию пользователя.

#### Scenario: Отказ

- **WHEN** на приглашение инициализации пользователь ответил отказом
- **THEN** статус профиля `declined`, агент подтверждает и продолжает работать как обычно

#### Scenario: Подсказка при отказе

- **WHEN** диалог в статусе `declined` и пользователь отправляет запрос
- **THEN** ответ выполняется без напоминания в тексте, а UI показывает подсказку о невыполненной инициализации с доступным действием вернуться к ней

### Requirement: Инъекция профиля в каждый запрос

При статусе `active` система SHALL добавлять блок профиля в system-промпт
каждого запроса LLM данного диалога: четыре поля в формате
«- ключ: значение»; при непустых стоп-словах/табу — строка указания избегать
их. Подключение профиля MUST быть автоматическим по диалогу: тело запроса
чат-эндпоинта не меняется. Пустой блок (все поля пусты) и статусы
`pending`/`declined` MUST NOT добавлять блок. Поведение слоёв памяти
(инъекция WM/LT, тумблеры, правило конфликтов, server-side гард)
MUST остаться без изменений.

#### Scenario: Активный профиль в каждом запросе

- **WHEN** профиль диалога `active` и пользователь отправляет запрос
- **THEN** system-промпт в JSON запроса к LLM содержит блок профиля со всеми непустыми полями

#### Scenario: Табу влияют на промпт

- **WHEN** поле «стоп-слова/табу» непусто
- **THEN** блок профиля содержит строку указания избегать перечисленных слов/тем

#### Scenario: Non-active статусы без блока

- **WHEN** профиль в статусе `pending` или `declined`
- **THEN** блока профиля в system-промпте нет, остальные блоки (память, правило конфликтов) — как раньше

### Requirement: Реакция на упоминание табу-слов

При статусе `active` и непустом поле «стоп-слова/табу» система SHALL
детерминированно (без LLM-вызова) детектировать вхождение табу-слова в запрос
пользователя: поле режется на отдельные слова/фразы по запятой и точке с
запятой, сопоставление — по нижнему регистру; токен короче 2 символов
пропускается. При обнаружении система SHALL добавлять в конец списка
сообщений system-напоминание по тому же паттерну, что server-side гард
конфликтов памяти (день 11): агент вежливо отказывает в части запроса,
задействующей табу-слово (лёгкая доброжелательная интонация, ссылка на
конкретное табу-слово), сообщая, что решение принято по профилю
пользователя. Детект MUST NOT менять профиль или его статус, MUST NOT
вызывать LLM для самого детекта и MUST NOT писать служебную запись в журнал
запросов. Гард MUST NOT быть активен для статусов `pending`/`declined` и при
пустом поле «стоп-слова/табу». Избежание табу-слов в собственных ответах
агента (строка «Избегай:» из инъекции) сохраняется.

#### Scenario: Запрос содержит табу-слово

- **WHEN** профиль `active`, «стоп-слова/табу» = «мат, эмодзи», пользователь отправляет «напиши фразу, используя мат»
- **THEN** запрос к LLM содержит в конце списка сообщений system-напоминание о табу-слове, а агент вежливо отказывает, не употребив табу-слово

#### Scenario: Запрос не содержит табу-слов

- **WHEN** запрос не содержит ни одного из табу-слов
- **THEN** system-напоминания не добавляется, запрос выполняется как обычно

#### Scenario: Non-active статусы — гард неактивен

- **WHEN** профиль в статусе `pending` или `declined` (или поле табу пусто) и сообщение содержит табу-слово
- **THEN** system-напоминания не добавляется

### Requirement: REST API профиля

Система SHALL предоставлять:
- выдачу профиля в ответах с диалогом (получение диалога и список диалогов содержат поля профиля и статус);
- `POST /api/profile` — `{"dialogue_id", "name", "role", "tone", "taboos"}` (все значения — строки, могут быть пустыми) → сохранить профиль, при непустом содержимом статус `active`; 400 на не-str значения/неизвестные поля, 404 на несуществующий диалог;
- `POST /api/profile/action` — `{"dialogue_id", "action"}`, action ∈ `interview` | `decline` | `reset` → 200: `interview` запускает поток интервью (статус остаётся `pending` с пометкой ожидания интервью), `decline` устанавливает `declined`, `reset` сбрасывает профиль в `pending` (очищая поля); 400 на неизвестное action, 404 на диалог.

#### Scenario: Профиль в выдаче диалога

- **WHEN** клиент запрашивает диалог (GET)
- **THEN** ответ содержит поля профиля и статус

#### Scenario: Запуск интервью через API

- **WHEN** POST /api/profile/action с action=`interview`
- **THEN** 200; следующий запрос в чате получает вопросы интервью (все четыре — одним сообщением)

#### Scenario: Reset возвращает в pending

- **WHEN** POST /api/profile/action с action=`reset` для `active`-диалога
- **THEN** поля профиля очищены, статус `pending`, следующий запрос снова получает приглашение инициализации

#### Scenario: Неизвестный action

- **WHEN** POST /api/profile/action с action=`bogus`
- **THEN** 400 с RU-сообщением, статус не меняется

### Requirement: Вкладка «Профили» и бейдж в UI

Панель «Контекст» SHALL содержать вкладку «Профили»: четыре поля активного
диалога (редактируемые), статус, кнопки «Интервью», «Заполнить заново»
(интервью или ручное сбросом) и «Отказаться». Вкладка SHALL обновляться при
переключении диалога. При статусах `pending`/`declined` в чате SHALL
показываться бейдж/подсказка о невыполненной инициализации («после
инициализации ответы будут точнее и лучше»), по действию на который
пользователь может запустить ручное заполнение или интервью.

#### Scenario: Вкладка показывает профиль активного диалога

- **WHEN** пользователь переключает диалоги
- **THEN** вкладка «Профили» показывает поля и статус профиля текущего активного диалога

#### Scenario: Бейдж исчезает после инициализации

- **WHEN** профиль диалога стал `active`
- **THEN** подсказка о инициализации в чате исчезает

### Requirement: Проверка персонализации (тесты и e2e)

Репозиторий SHALL содержать тесты, доказывающие: (1) разные профили →
разные ответы — одно и то же сообщение в двух диалогах с разными
активными профилями (например, разный тон/стоп-слово) даёт разные ответы
(офлайн — через fake-LLM, различающийся по блоку профиля в payload;
live — в e2e); (2) автоматичность — профиль `active` присутствует в
payload каждого запроса без явной передачи в чат-запросе; (3) state machine
(pending → active/declined, reset, неудачное интервью не ломает диалог)
покрыта офлайн-тестами. `scripts/e2e_studio.py` SHALL быть расширен
прогоном: создание диалога → приглашение → интервью/ручное заполнение →
запрос с блоком профиля в JSON; exit 0 = PASS/SKIP, 1 = FAIL.

#### Scenario: Разные профили — разные ответы (mock)

- **WHEN** прогоняется офлайн-сценарий с двумя диалогами, чьи `active`-профили отличаются (тон / стоп-слово)
- **THEN** payloads двух запросов содержат разные блоки профиля и fake-LLM-ответы различаются по персонализации

#### Scenario: E2E прогон инициализации

- **WHEN** запущен `python scripts/e2e_studio.py` (GPustack доступен)
- **THEN** пройден поток: новый диалог → приглашение инициализации → интервью → ответ → `active` → запрос, JSON которого содержит блок профиля; exit 0
