# Design: day13-task-state-machine

## Обзор

Задача = явный режим диалога. Детерминированный оркестратор (Python)
гоняет пайплайн stage-агентов (тот же LLM, разные system-промпты) и
ведёт FSM. LLM не управляет состоянием — только генерирует output стадии;
FSM-переходы, паузы, повтор валидации и синтез — код. Паттерны из дня 12
(детерминированный служебный поток, state в записи диалога, best-effort
LLM-вызовы) и дня 11 (SSE, бэкворд-совместимость, RU-ошибки 400/404).

## FSM и stage-агенты

```
        start
          |
          v
  +-----------+    +--------------+    +--------------+    +------+
  | planning  |--->|  execution   |--->|  validation  |--->| done |
  | План-рщик |    |  Исполнитель |    |  Валидатор   |    |Синтез|
  +-----------+    +--------------+    +--------------+    +------+
                          ^                  |
                          |  fail (1 раз)    | pass / fail(2) / битая метка
                          +------------------+
```

- **Stage-агенты** (model из конфига, temperature как в чате):
  - Планировщик: описание задачи (+instruction) → план шагов.
  - Исполнитель: описание + план (+instruction; при повторе — +work1 +
    замечания Валидатора) → результат.
  - Валидатор: план + результат → ответ + метка `<verdict>pass|fail</verdict>`.
  - Оркестратор-синтез: описание + outputs всех стадий + вердикт +
    instruction → финальный ответ (non-stream; `answer` уходит в
    событии `task_done`).
- **Оркестратор** — `StudioAgent.task_run(dialogue_id)`, синхронный
  генератор (паттерн `ask_stream`): цикл «выполнить текущую стадию →
  сохранить output → проверить stop-флаг/паузу/ошибку → следующая
  стадия» до `done`/паузы/ошибки. Каждые стадии — отдельный LLM-вызов
  (все стадии non-stream, включая синтез).
- **4–5 LLM-вызовов на задачу** (с повтором валидации — 5).

## Состояние задачи (storage)

Новое поле `task` в записи диалога (`dialogues.json`), паттерн `profile`
дня 12. Методы `MemoryStore` под единым `threading.Lock`, атомарная запись:

```json
{
  "active": true,
  "stage": "planning",
  "paused": false,
  "description": "...",
  "instruction": "",
  "stages": {
    "planning":   {"output": "...", "ts": "..."},
    "execution":  {"output": "...", "ts": "...", "attempts": 1},
    "validation": {"output": "...", "verdict": "pass|fail|null", "ts": "..."}
  },
  "retries": 0,
  "error": null,
  "updated": "..."
}
```

- Отсутствие поля = задача неактивна (бэкворд-совместимо).
- Пауза — флаг `paused` + stop-запрос: `POST /api/task/pause` ставит флаг,
  оркестратор проверяет его **между стадиями** (текущий LLM-вызов
  доигрывается) и завершает стрим событием `task_paused`.
- `resume` — снимает флаг; `POST /api/task/run` снова запускает цикл с
  первой невыполненной стадии (outputs уже в state → без повторных
  объяснений).
- Сброс после `done`: `POST /api/task/reset` → `active=false`,
  поля очищены; `start` создаёт новое состояние со стадией `planning`.
- `instruction`: пишется только при `paused` (иначе 400), при запуске
  следующей стадии копируется в её system-промпт и очищается.

## Инъекция state в stage-промпты

Блок «Состояние задачи» строится оркестратором для каждой стадии
(детерминированный текст, паттерн блоков памяти/профиля):

```
Текущая задача: <description>
Выполнено:
- planning: <output>
- execution: <output>          (если есть)
Ожидаемое действие: <текст стадии>
Инструкция пользователя (учти): <instruction>   (если задана)
```

Stage-промпты (константы, паттерн `MEMORY_RULE`/`PROFILE_*_TEXT` дня 12):
роль агента стадии + правила (только output по существу; Валидатор —
обязательная метка `<verdict>` в конце).

## SSE-протокол `POST /api/task/run`

Старый протокол `/api/chat` не меняется. Новые события (те же SSE-кадры
`data: {json}\n\n`):

| type | payload | смысл |
| --- | --- | --- |
| `stage` | `{stage, agent}` | стадия запущена (агент: «Планировщик»/«Исполнитель»/«Валидатор») |
| `stage_done` | `{stage, output}` | стадия завершена, output сохранён |
| `task_paused` | `{stage}` | стоп на границе стадии (stage = следующая невыполненная) |
| `task_done` | `{answer}` | задача завершена; `answer` — полный финальный синтез (non-stream, авторитетный текст ответа) |
| `error` | `{message}` | ошибка LLM-вызова стадии; задача сохранена с `error`, повтор через resume |

Stage-outputs пишутся в `messages` диалога с меткой `task_stage`
(паттерн `model`-чипа дня 11: служебное поле, в тело LLM-запроса не
уходит); чип «задача» на stage-сообщениях в UI. Финальный синтез —
обычное assistant-сообщение с `model`.

## REST API

Все тела с `dialogue_id`; 404 — диалог не найден, 400 — RU-detail (паттерн
`main.py`).

| Метод | Путь | Тело | Результат |
| --- | --- | --- | --- |
| POST | `/api/task/start` | `{dialogue_id, description}` | задача: `active`, `stage=planning`; 400 — уже есть активная незавершённая |
| POST | `/api/task/run` | `{dialogue_id}` | SSE-пайплайн (выше); 400 — задача неактивна |
| POST | `/api/task/pause` | `{dialogue_id}` | stop-флаг + `paused` (между стадиями); 400 — нет активной задачи |
| POST | `/api/task/resume` | `{dialogue_id}` | снять паузу; 400 — нет паузы |
| POST | `/api/task/instruction` | `{dialogue_id, text}` | instruction; 400 — не на паузе |
| POST | `/api/task/reset` | `{dialogue_id}` | сброс состояния (новая задача готова) |
| GET | `/api/task?dialogue_id=` | — | состояние задачи или `{"active": false}` |

`task` добавляется в ответы `GET /api/dialogues` и
`GET /api/dialogues/{id}` (как `profile`). Гард в `ask_stream`/`/api/chat`:
активная непаузанная незавершённая задача → ответ 200 с SSE-событием
`error` «Задача выполняется…» (сообщение в диалог не пишется); на паузе
чат работает как обычно.

## Фронтенд

- **`state.tsx`**: `task` в reducer (загружается вместе с диалогами),
  экшены start/pause/resume/instruction/reset; SSE-клиент `taskRun`
  (fetch + ReadableStream, паттерн `chatStream` из `api.ts`) с
  обработчиками `stage`/`stage_done`/`task_paused`/`task_done`/`error`
  (после `done`-событий — перечитать `/api/dialogues` и `/api/task`, как
  после чата).
- **`ChatPanel.tsx`**: кнопки **Стоп/Продолжить** в шапке (видимы при
  активной задаче: стоп → `pause`, на паузе — Продолжить → `resume`);
  статус-строка стадий (4 чипа: planning/execution/validation/done,
  текущая — подсвечена, пройденные — ✓); чип «задача» на
  stage-сообщениях; во время выполнения стадии поле ввода
  заблокировано. Запуск задачи по описанию и instruction на паузе — в
  `TaskTab.tsx`.
- **`TaskTab.tsx`** (вкладка «Задача» в `ContextPanel`): описание,
  список стадий с outputs (скролл), вердикт валидации, instruction,
  paused/error-чипы, кнопки Пауза / Продолжить / Новая задача (доступны по
  состоянию). Обновляется при переключении диалога (паттерн ProfileTab).
- `styles.css`: чипы стадий, статус-строка, paused/error-индикаторы
  (существующие дизайн-токены).

## Тесты

**Backend** (`studio/backend/tests/`, tmp_path + MockTransport, без сети):
- `test_task.py`:
  - FSM-цикл: сценарный mock-LLM (ответ по system-промпту стадии) →
    planning→execution→validation→done, outputs в state и messages,
    финальный синтез; system-промпты содержат предыдущие outputs.
  - Валидация: fail → повтор execution (проверка фидбэка в промпте),
    2-й fail → done с пометкой; битая/отсутствующая метка → pass.
  - Пауза: pause-флаг между стадиями → `task_paused`, следующая стадия не
    вызвана; resume → продолжение с state; instruction на паузе в
    stage-промпт и очищается, вне паузы 400.
  - Ошибка LLM: `error`-событие, состояние с `error`, повтор стадии через
    run.
  - API (`test_api.py`): start (400 при активной), run (400 без задачи),
    pause/resume/instruction/reset (400/404), GET /api/task, task в
    выдаче диалогов, гард `/api/chat` (SSE `error`, сообщение не пишется).
- Адаптация существующих тестов при изменении подписей.

**Frontend** (Vitest + Testing Library):
- `TaskTab.test.tsx`: рендер состояния (стадии/outputs/вердикт/paused),
  кнопки по состоянию, переключение диалога.
- `ChatPanel.test.tsx`: кнопки стоп/продолжить, статус-строка
  (stage-события), чип «задача», блокировка поля ввода на время стадии.

**E2E** (`scripts/e2e_studio.py`): блок «Задача»:
1. Детерминированное ядро (без LLM-зависимости где возможно):
   start → run (SSE: минимум stage(planning)+stage_done) → pause →
   instruction → resume → до task_done → reset; проверка state через
   `GET /api/task` и task в выдаче диалога.
2. Live best-effort (GPustack доступен): полный пайплайн на каждой из
   3 моделей — stage-события в стриме, stage-сообщения с метками в
   истории, финальный синтез; различие live-выполнений не
   гарантировано — ядро детерминированное (паттерн дня 12).
   Exit 0 = PASS/SKIP, 1 = FAIL.

## Риски и ограничения

- **Мелкие модели и метка `<verdict>`**: может не поставить/испортить —
  best-effort → `pass`, пайплайн не ломается (риск принят: цикл повторов
  ограничен одним, бесконечных нет).
- **Стоп на границе стадии**: «остановить на любом этапе» реализуется
  на границах — текущий LLM-вызов (до минуты на flash-моделях)
  доигрывается. Отмена в полвызова не поддерживается (documented).
- **Токен-расход**: задача = 4–5 LLM-вызовов против 1 в чате; outputs
  стадий копирование в последующие промпты растёт prompt — для
  задач приемлемо, лимитов на длину стадий нет (YAGNI).
- **Оркестратор синхронный** в рамках одного SSE-запроса (паттерн
  `ask_stream`): параллельных задач в одном диалоге нет; между диалогами —
  независимые state.
