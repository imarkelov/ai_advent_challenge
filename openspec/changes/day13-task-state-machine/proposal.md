# Proposal: day13-task-state-machine

## Why

День 13: состояние задачи как конечный автомат. Сегодня студия ведёт обычный
чат: если пользователь ставит многшаговую задачу, «где мы остановились»
живёт только в истории сообщений — при паузе/перезапуске агент должен
перечитывать диалог и пользователь повторно объяснять контекст. Задание:
сформализовать состояние задачи (этап, текущий шаг, ожидаемое действие) как
конечный автомат с паузой на любом этапе и продолжением без повторных
объяснений.

Ветка: `day13-task-state-machine` от `day12-user-profile`.

## What Changes

- **Задача как пайплайн stage-агентов**: явный режим «Задача» в диалоге.
  Каждую стадию FSM (`planning` → `execution` → `validation` → `done`)
  исполняет отдельный stage-агент — тот же LLM из конфига, свой
  system-промпт: Планировщик (план шагов), Исполнитель (работа по плану),
  Валидатор (вердикт против плана), Оркестратор-синтез (финальный ответ
  из outputs всех стадий).
- **Оркестратор**: детерминированный код бэкенда — цикл по стадиям в
  отдельном SSE-эндпоинте, хранит state, проверяет паузу/ошибку между
  стадиями, парсит валидацию (fail → один повтор execution с вердиктом как
  фидбэком). LLM не управляет FSM: служебный поток детерминирован (паттерн
  дня 12).
- **Состояние задачи per-диалог**: в записи диалога (`dialogues.json`) —
  стадия, paused, описание, instruction (правка на паузе), outputs стадий,
  retries, error. Переживает перезапуск и переключается с диалогом.
  «Продолжение без повторных объяснений» = state + outputs предыдущих
  стадий инъектируются в system-промпт следующего stage-агента.
- **Пауза/продолжение на любом этапе**: кнопка Стоп/Продолжить в диалоговом
  окне; стоп действует на границе стадии (текущий LLM-вызов доигрывается).
  На паузе пользователь может дать instruction — следующая стадия получает
  её вместе со state.
- **Статус работы в UI**: SSE-события `stage`/`stage_done`/`task_done`/
  `task_paused`; stage-outputs отображаются в чате как сообщения с чипом
  «агент + стадия»; статус-строка стадий в ChatPanel (агент работает… /
  выполнено) и новая вкладка «Задача» в панели «Контекст» (описание,
  стадии с outputs, вердикт, instruction, кнопки Пауза/Продолжить/Новая
  задача).
- **API**: `POST /api/task/run` (SSE-пайплайн), `POST /api/task/start`,
  `POST /api/task/pause`, `POST /api/task/resume`,
  `POST /api/task/instruction`, `POST /api/task/reset`,
  `GET /api/task?dialogue_id=`; `task` в ответах `/api/dialogues`. Гард:
  `/api/chat` при активной непазованной задаче → 400 RU.
- **Проверка**: pytest (бэкенд, MockTransport: FSM-цикл, пауза/резюм,
  retry-валидация, парсинг verdict, инъекция state, API 400/404,
  guard), Vitest (TaskTab, task-режим ChatPanel), расширение
  `scripts/e2e_studio.py` (детерминированное ядро через API + live
  best-effort полный пайплайн).

## Capabilities

### New Capabilities

- `task-state-machine`: формализованное состояние задачи per-диалог как
  конечный автомат (planning → execution → validation → done) с
  stage-агентами, детерминированным оркестратором в SSE, паузой/продолжением
  на любом этапе, instruction на паузе, статусом работы в UI и REST API.

## Impact

- **Код**: `studio/backend/memory.py` (task-методы `MemoryStore`),
  `studio/backend/agent.py` (оркестратор `task_run`, stage-промпты,
  парсинг verdict, гард в `ask_stream`), `studio/backend/main.py`
  (эндпоинты `/api/task/*`); фронтенд: новый `components/TaskTab.tsx`,
  правки `ChatPanel.tsx` (режим «Задача», кнопка Стоп/Продолжить,
  статус-строка стадий), `ContextPanel.tsx` (таб), `state.tsx`, `api.ts`
  (SSE `/api/task/run`).
- **Данные**: `dialogues.json` — новое поле `task` в записи диалога
  (бэкворд-совместимо: отсутствие поля = задача неактивна).
- **Совместимость**: тело `/api/chat`, слои памяти, профиль (день 12) не
  меняются; новый SSE-эндпоинт, старые протоколы не трогает.
