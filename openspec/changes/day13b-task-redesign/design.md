# Design: day13b-task-redesign

## Context

День 13 реализован: hand-rolled оркестратор `agent.task_run`, FSM
`planning→execution→validation→done` с паузой на границе стадии,
вкладка «Задача» как вход, 191 бэкенд-тест / 99 фронтенд-тест /
e2e 19/19 (см. archived change `2026-09-20-day13-task-state-machine`).
Ручная проверка дала фидбек: задача = запрос пользователя (не форма во
вкладке), спавн и работа агентов должны быть видны в диалоге, выводы —
со сворачиванием, вкладка «Задача» — убрать, нужен тумблер
чат/задача. Пользовательская целевая модель: unified stage
(PLANNING/EXECUTION/VALIDATION/DONE/PAUSED/FAILED), `plan` +
`work_steps`, `context_snapshot`, видимый спавн, живая работа.

## Goals / Non-Goals

**Goals:**
- Запуск задачи — сообщением чата в режиме «задача» (во всех диалогах,
  без вкладки).
- Видимый спавн stage-агентов и живая работа в карточке процесса
  (work-чек-лист, стрим текущего шага, «спавн X с назад»).
- Schema-апгрейд состояния задачи (unified stage, `task_id`,
  `expected_action`, `context_snapshot`) без новых зависимостей.
- Пауза на границе work-шага (финьше, чем стадия), resume/retry с
  сохранённого состояния.

**Non-Goals:**
- Миграция на LangGraph/Temporal (рассмотрено, отклонено — Decisions).
- Ограничение числа work-шагов/длины выводов (YAGNI).
- Параллельные задачи в одном диалоге, отмена в полвызова LLM.
- Миграция старых `dialogues.json` (dev-данные; отсутствие/старые
  поля обрабатываются как «задачи нет»).

## Decisions

### D1. Архитектура: расширение hand-rolled оркестратора (не LangGraph/Temporal)

**Выбор**: существующий детерминированный цикл `task_run` расширяется
(new schema, per-step loop, new events).

**Альтернативы и почему нет**:
- **LangGraph 1.2.11** — `interrupt()`/`Command(resume)` +
  checkpointer дают pause/resume из коробки, но: чекпоинтеров в JSON
  нет (Sqlite/Postgres) → вторая хранилищная подсистема рядом с
  JSON-файлами; 4–6 новых пакетов (langchain-core, checkpoint, sdk,
  prebuilt, …); при resume узел перезапускается с начала (LLM-вызовы
  до паузы повторно) — пауза на границе стадии требует разбивки на
  узлы; 32 task-теста целятся во внутренний цикл `task_run` —
  переписывание, а не адаптация. Для обучающего проекта («состоянный
  автомат построен сам») цена неоправданна.
- **Temporal** — 3 процесса (dev-сервер, worker, app), gRPC,
  детерминизм workflow-кода, 30–60 мин до first run; durable-replay
  для 4 фиксированных шагов не окупается.
- **Обоснование выбора**: hand-rolled FSM + snapshot/event log —
  легитимный production-паттерн фиксированных пайплайнов (payment
  state machines, PaymentIntent в Stripe — тот же shape). Наш
  event-стрим — и есть event log; снапшот — сериализованное состояние.
  0 новых зависимостей, одно хранилище, тесты наращиваются.

**Дверь открыта**: модель состояния (stages, plan/work_steps,
snapshot) 1:1 соответствует StateGraph-схеме LangGraph — перенос
возможен позже без перестройки архитектуры.

### D2. Пошаговое исполнение (N LLM-вызовов на N work-шагов)

**Выбор**: `execution` = цикл по `work_steps`, на каждый шаг —
отдельный LLM-вызов (промпт: описание + план + выводы завершённых
шагов + instruction). Статусы шагов `pending→in_progress→completed`,
вывод шага сохраняется, пауза проверяется между вызовами.

**Альтернатива**: один вызов с отчётом по шагам (дешевле, но живого
пошагового прогресса нет — против макета пользователя: чек-лист
[✓]/[⏳] + живой бокс «> Генерация вариантов…»).

**Побочный выигрыш**: гранулярность паузы — граница шага (было:
граница стадии).

### D3. Структурированный план Планировщика (best-effort JSON)

**Выбор**: Планировщик возвращает JSON-массив имён шагов
(`["Анализ ЦА", "Тексты", …]`); best-effort парсинг (тот же паттерн,
что авто-название дня 11 и интервью дня 12); сбой парсинга — план из
1 шага «Выполнить запрос». Лимит шагов: 1–5 (больше — обрезка).

**Альтернатива**: free-text план как сейчас — отклонено: без
структуры чек-лист карточки и per-step цикл невозможны.

### D4. Unified stage (6 значений) + expected_action

**Выбор**: `stage` ∈ `planning|execution|validation|done|paused|failed`
(флаги `paused`/`error` убираются); `expected_action` ∈
`agent_response|resume_wait|human_input`. Позиция при resume —
производная от статусов `plan[]`/`work_steps` (первый неполный
element).

**Альтернатива**: `stage` (4) + `paused` + `error` (текущая схема) —
отклонено: целевая схема пользователя, меньше комбинаторики
состояний.

### D5. Контекстная передача: промпты только из `context_snapshot`

**Выбор**: `context_snapshot = {description, work_steps(+outputs),
instruction}`; `build_task_state_block` (узкое место уже существует)
строго из snapshot; история чата в task-промпты не уходит.

**Альтернатива**: подмешивать последние сообщения чата — отклонено по
принципу пользователя: «чат — лишь представление, не источник
промптов».

### D6. Straming work-шагов (`step_delta`)

**Выбор**: LLM-вызовы work-шагов Исполнителя — streaming (инфраструктура
уже есть: `ask_stream`, httpx sync client); дельты транслируются
событием `step_delta`. Планирование/валидация/синтез — non-stream (как
сейчас; `task_done` несёт авторитетный ответ).

**Альтернатива**: статическая строка «выполняется…» — отклонено:
живой бокс — ядро визуализации в макете.

### D7. Персистентность: маркеры сообщений (паттерн дня 11)

**Выбор**: outputs стадий/work-шагов пишутся в `messages` диалога с
служебными полями `task_id`, `task_stage` (для execution-шагов —
`task_step`), в тело LLM-запроса не уходят; финальный синтез — обычное
assistant-сообщение. Карточка восстанавливается из маркеров
(`group by task_id`).

**Альтернатива**: один «snapshot-сообщение» на задачу — отклонено:
мутирует append-only историю; маркеры — уже проверенный e2e-паттерн.

### D8. Тумблер режимов: глобальный, localStorage

**Выбор**: состояние тумблера — глобальное (не per-диалог), default
«чат», persist в `localStorage`; заблокирован при активной непаузанной
задаче (предотвращает смену режима на середине пайплайна).

**Альтернатива**: per-диалог режим — отклонено: усложняет state без
сформулированной потребности.

### D9. API-семантика: `start` после `done`/`failed` = новая задача; `run` на `failed` = повтор

**Выбор**: `start` при незавершённой (включая `paused`) задаче — 400;
при `done`/`failed` — новая задача (новый `task_id`, старая уходит в
историю сообщений). `run` на `failed` — повтор упавшей стадии/шага.
`run` на `done` — 400.

**Альтернатива**: обязательный `reset` перед новой задачей (текущая
семантика) — отклонено: лишний ручной шаг против «запрос = новая
задача».

## Risks / Trade-offs

- **Мелкие модели и JSON-план** → best-effort + фолбэк 1 шаг:
  пайплайн не ломается (риск принят, паттерн дня 11/12).
- **Токен-расход**: N+3 LLM-вызовов (до 2N+3 с ретраем); выводы
  шагов копирование в последующие промпты растит prompt — для задач
  приемлемо, лимитов нет (YAGNI).
- **Пауза на границе шага**: текущий LLM-вызов (до ~минуты на
  flash-моделях) доигрывается; отмена в полвызова не поддерживается
  (documented, как и раньше).
- **Старые task-сообщения** (маркер `task_stage` без `task_step`):
  карточка рендерит их как секции стадий без work-чек-листа
  (бэкворд-совместимость рендера).
- **Стриминг в синхронном генераторе** (`step_delta`): тот же
  механизм, что `ask_stream` (sync httpx + yield) — проверено днём 11.
- **Удаление `TaskTab`/кнопки Стоп**: 3 task-tab-теста и
  chat-panel-тесты на кнопки — заменяются тестами карточки/тумблера
  (счёт тестов меняется, baseline фиксируется в e2e-прогоне).

## Migration Plan

1. Бэкенд (memory → agent → main) — TDD, коммиты по блокам; старые
   task-тесты адаптируются в каждом блоке (не «все сразу»).
2. Фронтенд — api/state → TaskCard + ChatPanel → удаление TaskTab/
   5-й вкладки; vitest+tsc после каждого блока.
3. E2E-блок «Задача» переписывается под новые события/семантику.
4. Rebuild `dist` + перезапуск uvicorn (ручная проверка).
5. Rollback: ветка `day13-task-state-machine` — отдельные коммиты;
   revert последним блока возвращает предыдущее состояние (ветка
   несмержена в `day12-user-profile`).
