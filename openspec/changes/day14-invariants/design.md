# Design: day14-invariants

## Goal

Добавить ассистенту (студия, backend `studio/backend/` + frontend
`studio/frontend/`) категорию **инвариантов** — жёстких, неизменяемых правил,
которые он не имеет права нарушать и не может изменять. Инварианты хранятся
отдельно от диалога, явно учитываются в рассуждениях, а при конфликте запроса
с инвариантом ассистент отказывается предлагать нарушающее решение.

## Scope

- **In**: новое глобальное хранилище `invariants.json`, методы `MemoryStore`,
  инъекция + правило + server-side гард в `StudioAgent`, REST-эндпоинты,
  5-я вкладка «Инварианты» в UI, автотесты.
- **Out**: изменение модели памяти/профиля/задач, изменение тумблеров слоёв,
  свободнотекстовые (не key-value) инварианты, добавление инвариантов
  ассистентом (только пользователь), live-часть проверки (офлайн-тесты,
  детерминированное ядро — как прошлые дни).

## Context

Аналогичные цепочки в коде:

- **Память (день 11)**: `build_memory_blocks(dialogue_id)` →
  `\n\nТекущая задача:` (WM) / `\n\nДолговременная память:` (LT); порядок
  сборки system-промпта в `build_payload` (базовый → профиль → память →
  MEMORY_RULE); server-side `_detect_memory_conflict(dialogue_id, message)`
  (ключ в msg, значение не в msg, глагол действия) → system-напоминание в
  конец `messages`. `_detect_taboo` (профиль) — тот же паттерн.
- **Профиль (день 12)**: `build_profile_block(dialogue_id)` между базовым
  промптом и памятью; статусы pending/active/declined.
- Инъекция происходит в `StudioAgent.build_payload` (`agent.py` ~line 291);
  конфликт-гарды вызываются в `ask_stream` перед запросом к LLM.

## Decisions

### D1: Модель инварианта — key-value (как память), а не свободный текст

Инвариант = `{id, key, value}` (id — авто-генерируемый, напр.
`"inv_" + 4 hex`). Причина: детерминированный server-side гард
(ключ/значение/глагол) надёжнее и офлайн-тестируемее свободного текста;
мелкие модели подчиняются противоречащему запросу вопреки промпту, поэтому
нужен жёсткий детект. Свободные «бизнес-правила» вышли бы за масштаб дня.
Некорректный/неполный `{key, value}` → 400.

### D2: Инварианты — глобальные, всегда активны, не отключаемы

Файл `invariants.json` рядом с `longterm.json`. Тумблеров слоя инвариантов
нет (вопреки st/wm/lt), тумблеры памяти на инварианты не влияют. `layer_stats`
показывает инварианты отдельным блоком.

### D3: Инъекция — инварианты приоритетнее памяти и профиля

Порядок в `build_payload`: базовый → профиль → **ИНВАРИАНТЫ** → память
(WM→LT) → правило конфликтов. Блок — перед памятью, чтобы модель учла
инварианты как высшую норму. `GET /api/rules` → + `invariants_block`.

### D4: Правило `INVARIANTS_RULE` — жёстче MEMORY_RULE

В конец system-промпта (после MEMORY_RULE) добавляется правило: инварианты —
неукоснительные; при противоречии запроса инварианту ассистент НЕ предлагает
нарушающее решение, а вежливо отказывает, называет конкретный инвариант,
объясняет отказ и предлагает альтернативу в рамках инвариантов. С сам
инвариант ассистент не изменяет и не удаляет.

### D5: Server-side гард `_detect_invariant_conflict`

Сигнатура `(dialogue_id, message) -> list[(key, value)]`. Логика — зеркало
`_detect_memory_conflict`, но по `invariants_items()`, без учёта тумблеров
(всегда активен). В `ask_stream` после `_detect_memory_conflict`/
`_detect_taboo`: если сработали инварианты — в конец `messages` добавляется
system-напоминание «запрос противоречит инварианту X — откажись» (паттерн дня
11/12). Ключ < 4 символов пропускается (неоднозначность).

### D6: API

- `GET /api/invariants` → `{"invariants": [{id,key,value}]}`.
- `POST /api/invariants` `{key, value}` (оба непустые str) → 201 запись.
  400 — ключ/значение не str или пустые, либо отсутствуют.
- `DELETE /api/invariants/{id}` → 200; 404 — id не найден.
- `GET /api/rules` → + `invariants_block` (наличие непустых инвариантов).
- `GET /api/memory` → + `invariants` (в `layer_stats`).

### D7: Фронтенд — 5-я вкладка «Инварианты»

`ContextPanel.tsx` — новый таб; `InvariantsTab.tsx` по каркасу `MemoryTab`
(список key-value, поля добавления, удаление по id, побузуджетное «неизменяемые»).
Без свитчей вкл/выкл. `state.tsx`/`api.ts` — хелперы `getInvariants`/
`addInvariant`/`deleteInvariant`.

### D8: Тесты

- `tests/test_memory.py`: CRUD инвариантов (set/items/remove/clear), пустой
  файл → [], `build_invariants_block` (пусто → "", непустое → блок), изоляция
  от пар и WM/LT.
- `tests/test_agent.py`: `build_payload` включает инварианты в system (выше
  памяти), `INVARIANTS_RULE` присутствует; `_detect_invariant_conflict`
  (срабатывание / не-срабатывание, глагол, ключ < 4); `ask_stream` добавляет
  system-напоминание при конфликте; существующие тесты не сломаны.
- `tests/test_api.py`: `GET/POST/DELETE /api/invariants` (200/201/400/404),
  `GET /api/rules` с `invariants_block`, `GET /api/memory` с `invariants`.
- Фронтенд (Vitest): `InvariantsTab` — список, добавление, удаление, «не
  отключаемые».

## Risks

- **Конфликт с памятью**: инвариант и пункт памяти могут дать оба срабатывания.
  Решение: инварианты проверяются первыми и их system-напоминание добавляется
  тоже (в конец `messages`, после напоминаний памяти) — отказ ссылается на
  инвариант как на высшую норму.
- **Backward-compat**: `invariants.json` может отсутствовать (пустой) →
  блоки/гард не срабатывают, ничего не ломается; `layer_stats` считает 0.
- **Черный список ключей памяти/инвариантов**: инварианты живут отдельно,
  не пересекаются с WM/LT — изоляция за счёт отдельного файла и методов.
