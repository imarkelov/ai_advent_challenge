## Purpose

Жёсткие, неизменяемые инварианты ассистента «Студия» (день 14): правила
(выбранная архитектура, принятые технические решения, ограничения по стеку,
бизнес-правила), которые ассистент не имеет права нарушать. Инварианты
хранятся отдельно от диалога, явно учитываются в рассуждениях, а при
конфликте запроса с инвариантом ассистент отказывается предлагать нарушающее
решение. Управлять инвариантами может только пользователь.

## ADDED Requirements

### Requirement: Хранилище инвариантов

Система SHALL хранить инварианты в глобальном файле `invariants.json`,
отдельно от диалога и от других слоёв памяти (WM/LT). Каждый инвариант —
`{id, key, value}` (id — авто-генерируемый). `MemoryStore` SHALL
предоставлять `invariants_items()` (пустой dict при отсутствующем/битом
файле), `invariants_set(key, value)` (непустые str), `invariants_remove(id)`
(True если была) и `invariants_clear()`. Изменения SHALL быть атомарными.
Инварианты MUST быть независимы от тумблеров слоёв памяти (`st`/`wm`/`lt`):
всегда активны и не отключаемы. Управление — только пользователем:
ассистент MUST NOT создавать, изменять или удалять инварианты.

#### Scenario: Инварианты переживают перезапуск

- **WHEN** сохранён инвариант и сервер перезапущен
- **THEN** `invariants_items()` возвращает тот же инвариант с теми же key/value

#### Scenario: Пустой/битый файл

- **WHEN** `invariants.json` отсутствует или повреждён
- **THEN** `invariants_items()` возвращает пустой dict, соотв. методы работают без ошибок

#### Scenario: Изоляция от памяти

- **WHEN** инварианты заданы и слои WM/LT также непусты
- **THEN** инварианты не смешиваются с WM/LT в `layer_stats()` — инварианты в отдельном блоке

#### Scenario: Ассистент не меняет инварианты

- **WHEN** ассистент выполняет запрос в рамках инвариантов
- **THEN** файл инвариантов не изменяется ни одним полевым значением (CRUD — только через API/UI пользователя)

### Requirement: Блок инвариантов в system-промпте

Если инварианты непусты, система SHALL добавлять в system-промпт каждого
запроса блок `"\n\nИнварианты (неукоснительно):\n- key: value"` (по одному
`- key: value` на инвариант). Порядок сборки: базовый промпт → профиль →
инварианты → память (WM→LT) → правило конфликтов. При пустых инвариантах
блок MUST NOT добавляться.

#### Scenario: Инварианты выше памяти

- **WHEN** заданы и инварианты, и память (WM/LT)
- **THEN** в system-промпте блок инвариантов идёт перед блоками памяти

#### Scenario: Пустые инварианты — блока нет

- **WHEN** инвариантов нет
- **THEN** блока инвариантов в system-промпте нет, остальные блоки без изменений

### Requirement: Правило инвариантов (INVARIANTS_RULE)

При непустых инвариантах система SHALL добавлять к system-промпту правило:
инварианты — высший приоритет над памятью, профилем и запросами диалога; при
противоречии ассистент отказаться предлагать нарушающее решение, назвать
конкретный инвариант, объяснить отказ и предложить альтернативу в рамках
инвариантов. Ассистент MUST NOT изменять или удалять инварианты.

#### Scenario: Правило при непустых инвариантах

- **WHEN** задан хотя бы один инвариант
- **THEN** system-промпт содержит правило инвариантов (упоминание «неукоснительно»/«отказаться»)

#### Scenario: Правило доминирует над памятью

- **WHEN** запрос конфликтует и с инвариантом, и с пунктом памяти
- **THEN** агент отказывает, ссылаясь на инвариант как на высшую норму

### Requirement: Server-side гард конфликта инвариантов

Система SHALL детерминированно (без LLM) детектировать конфликт запроса с
инвариантом: ключ инварианта встречается в сообщении, значение не
встречается, в сообщении есть глагол действия; ключ короче 4 символов —
пропуск. Гард MUST быть активен всегда (инварианты не отключаемы) и MUST
проверяться до конфликта памяти. При срабатывании система SHALL добавлять в
конец списка сообщений (самое свежее место) system-напоминание «запрос
противоречит инварианту X — откажись» (паттерн дня 11). Детект MUST NOT
менять инварианты.

#### Scenario: Запрос противоречит инварианту

- **WHEN** инвариант «Стек: Kotlin» и пользователь запрашивает «напиши на Python»
- **THEN** запрос к LLM содержит в конце списка сообщений system-напоминание о противоречии инварианту

#### Scenario: Запрос в рамках инварианта

- **WHEN** запрос согласуется с инвариантом (значение встречается)
- **THEN** system-напоминания конфликта не добавляется

#### Scenario: Короткий ключ пропускается

- **WHEN** ключ инварианта короче 4 символов
- **THEN** конфликт по такому ключу не детектируется

### Requirement: REST API инвариантов

Система SHALL предоставлять:
- `GET /api/invariants` → `{"invariants": [{id, key, value}]}`;
- `POST /api/invariants` `{key, value}` (оба непустые str) → 201; 400 — значение не str, пустое или отсутствует;
- `DELETE /api/invariants/{id}` → 200; 404 — id не найден;
- `GET /api/rules` → + `invariants_block`; `GET /api/memory` → + `invariants` (в `layer_stats`).

#### Scenario: Добавление инварианта

- **WHEN** POST /api/invariants с корректными key/value
- **THEN** 201, инвариант присутствует в GET /api/invariants и в `build_invariants_block`

#### Scenario: Валидация

- **WHEN** POST /api/invariants с пустым/не-str ключом или значением
- **THEN** 400 с RU-сообщением, инвариант не сохранён

#### Scenario: Удаление

- **WHEN** DELETE /api/invariants/{id} для существующего id
- **THEN** 200, инвариант удалён; для несуществующего — 404

### Requirement: Вкладка «Инварианты» в UI

Панель «Контекст» SHALL содержать вкладку «Инварианты»: список инвариантов
key-value активного контекста, форма добавления, удаление по id. Вкладка
MUST NOT отображать свитчи включения/выключения слоя (инварианты неизменяемы
и всегда активны) — с пометкой «неизменяемые».

#### Scenario: Список инвариантов

- **WHEN** заданы инварианты
- **THEN** вкладка показывает их key-value списком

#### Scenario: Добавление и удаление

- **WHEN** пользователь добавляет новый инвариант и затем удаляет его
- **THEN** состояние обновляется соответственно, без свитчей вкл/выкл

### Requirement: Проверка инвариантов (тесты)

Репозиторий SHALL содержать тесты, доказывающие: инъекцию блока инвариантов и
правила в system-промпт, срабатывание server-side гарда при конфликте, отказ и
неизменность инвариантов при запросах. `scripts/e2e_studio.py` SHALL быть
расширен блоком «Инварианты»: добавить → конфликт → удалить; exit 0 =
PASS/SKIP, 1 = FAIL.

#### Scenario: Инъекция в payload (mock)

- **WHEN** задан инвариант и выполняется офлайн-запрос
- **THEN** payload LLM-запроса содержит блок инвариантов и правило; при конфликте — system-напоминание гарда

#### Scenario: E2E прогон

- **WHEN** запущен `python scripts/e2e_studio.py` (GPustack доступен)
- **THEN** пройден блок «Инварианты» (добавление, конфликт-напоминание в JSON, удаление); exit 0
