## Purpose

Жёсткие, неизменяемые инварианты ассистента «Студия» (день 14): правила
(выбранная архитектура, принятые технические решения, ограничения по стеку,
бизнес-правила), которые ассистент не имеет права нарушать. Инварианты
хранятся отдельно от диалога, явно учитываются в рассуждениях, а при
конфликте запроса с инвариантом ассистент отказывается предлагать нарушающее
решение. Управлять инвариантами может только пользователь.

## ADDED Requirements

### Requirement: Хранилище инвариантов

Система SHALL хранить инварианты в глобальном файле `invariants.json`,
отдельно от диалога и от других слоёв памяти (WM/LT). Каждый инвариант —
`{id, title, description, forbidden[], is_active}`; `id` = `"inv_" + 4 hex`.
`MemoryStore` SHALL предоставлять `invariants_items()` (пустой dict при
отсутствующем/битом файле), `invariants_set(title, description, forbidden=None,
is_active=True)` (обновление по `title` сохраняет прежний `id`;
`ValueError` на пустой title/description, forbidden не-списке строк или
is_active не-bool), `invariants_set_active(iid, active)` (True/False тумблер),
`invariants_remove(id)` (True если была), `invariants_clear()` и
`build_invariants_block()`. Изменения SHALL быть атомарными (tmp + `os.replace`).
Старое представление `{key, value}` SHALL мигрировать на чтении:
`title=key`, `description=value`, `forbidden=[]`, `is_active=true`. Управление —
только пользователем: ассистент MUST NOT создавать, изменять или удалять
инварианты.

#### Scenario: Инварианты переживают перезапуск

- **WHEN** сохранён инвариант и сервер перезапущен
- **THEN** `invariants_items()` возвращает тот же инвариант с теми же полями

#### Scenario: Пустой/битый файл

- **WHEN** `invariants.json` отсутствует или повреждён
- **THEN** `invariants_items()` возвращает пустой dict, соотв. методы работают без ошибок

#### Scenario: Изоляция от памяти

- **WHEN** инварианты заданы и слои WM/LT также непусты
- **THEN** инварианты не смешиваются с WM/LT в `layer_stats()` — инварианты в отдельном блоке

#### Scenario: Ассистент не меняет инварианты

- **WHEN** ассистент выполняет запрос в рамках инвариантов
- **THEN** файл инвариантов не изменяется ни одним полевым значением (CRUD — только через API/UI пользователя)

### Requirement: Блок инвариантов в system-промпте

Если есть **активные** (`is_active=true`) инварианты, система SHALL добавлять в
system-промпт каждого запроса блок `"\n\nИнварианты (неукоснительно):\n- title:
description"` (по одному `- title: description` на инвариант). Порядок сборки:
базовый промпт → профиль → инварианты → память (WM→LT) → правило конфликтов.
При отсутствии активных инвариантов блок MUST NOT добавляться.

#### Scenario: Инварианты выше памяти

- **WHEN** заданы и инварианты, и память (WM/LT)
- **THEN** в system-промпте блок инвариантов идёт перед блоками памяти

#### Scenario: Пустые/все неактивные — блока нет

- **WHEN** активных инвариантов нет
- **THEN** блока инвариантов в system-промпте нет, остальные блоки без изменений

### Requirement: Правило инвариантов (INVARIANTS_RULE)

При непустых **активных** инвариантах система SHALL добавлять к system-промпту
правило `INVARIANTS_RULE`: инварианты — высший приоритет над памятью, профилем
и запросами диалога; при противоречии ассистент отказаться предлагать
нарушающее решение, назвать конкретный инвариант, объяснить отказ и предложить
альтернативу в рамках инвариантов. Ассистент MUST NOT изменять или удалять
инварианты. Правило требует явно сверять запрос/ответ с инвариантами в шаге
рассуждения.

#### Scenario: Правило при активных инвариантах

- **WHEN** задан хотя бы один активный инвариант
- **THEN** system-промпт содержит правило инвариантов (упоминание «неукоснительно»/«отказаться»)

#### Scenario: Правило доминирует над памятью

- **WHEN** запрос конфликтует и с инвариантом, и с пунктом памяти
- **THEN** агент отказывает, ссылаясь на инвариант как на высшую норму

### Requirement: Server-side гарды инвариантов (pre- и post-)

System SHALL детерминированно (без LLM) проверять инварианты в двух местах.

**Pre-guard (до LLM):** `_detect_invariant_conflict(dialogue_id, message)`
детектирует попытку переопределения: в сообщении присутствует forbidden-паттерн
активного инварианта (подстрока, без учёта регистра) И глагол действия из
`CONFLICT_VERBS`; вопросы про инварианты без глагола конфликтом не считаются.
При срабатывании система SHALL добавлять в конец списка сообщений (самое свежее
место) system-напоминание «запрос противоречит инварианту X — откажись».
Гард активен только на активных инвариантах и MUST NOT менять их.

**Post-guard (после ответа):** `_postcheck_invariants(answer)` (уровень L1)
сканирует ответ модели `answer` на forbidden-паттерны активных инвариантов
(`_forbidden_hits`). При срабатывании система SHALL заменять `answer` отказом с
указанием нарушающего паттерна, а в SSE-потоке перед `done` отдавать событие
`{"type": "invariant_violation", "patterns": [...]}`. Семантический L2-чек
(вторичный LLM) — задел на будущее, код структурно готов.

#### Scenario: Запрос противоречит инварианту

- **WHEN** инвариант «Стек: Kotlin» с `forbidden:["python"]` и пользователь запрашивает «напиши на Python»
- **THEN** запрос к LLM содержит в конце списка сообщений system-напоминание о противоречии инварианту

#### Scenario: Запрос в рамках инварианта

- **WHEN** запрос согласуется с инвариантом (forbidden-паттерн не встречается)
- **THEN** system-напоминания конфликта не добавляется

#### Scenario: Пост-гард заменяет нарушающий ответ

- **WHEN** ответ модели содержит forbidden-паттерн активного инварианта
- **THEN** `answer` заменяется отказом с паттерном; в SSE-потоке перед `done` событие `invariant_violation`

### Requirement: REST API инвариантов

Система SHALL предоставлять:
- `GET /api/invariants` → `{"invariants": [{id, title, description, forbidden, is_active}]}`;
- `POST /api/invariants` `{title, description, forbidden?, is_active?}` → 201; 400 — пустой title/description, forbidden не список строк, is_active не bool;
- `POST /api/invariants/{id}/toggle` → 200 (переключает `is_active`); 404 — id не найден;
- `DELETE /api/invariants/{id}` → 200; 404 — id не найден;
- `GET /api/rules` → + `invariants_block`; `GET /api/memory` → + `invariants` (в `layer_stats`).

#### Scenario: Добавление инварианта

- **WHEN** POST /api/invariants с корректными title/description/forbidden/is_active
- **THEN** 201, инвариант присутствует в GET /api/invariants и в `build_invariants_block`

#### Scenario: Валидация

- **WHEN** POST /api/invariants с пустым title/description, не-списком forbidden или не-bool is_active
- **THEN** 400 с RU-сообщением, инвариант не сохранён

#### Scenario: Тумблер is_active

- **WHEN** POST /api/invariants/{id}/toggle для существующего id
- **THEN** 200, значение `is_active` инвертируется; при неактивном инвариант не инжектится и не проверяется, но не удаляется; для несуществующего — 404

#### Scenario: Удаление

- **WHEN** DELETE /api/invariants/{id} для существующего id
- **THEN** 200, инвариант удалён; для несуществующего — 404

### Requirement: Вкладка «Инварианты» в UI

Панель «Контекст» SHALL содержать вкладку «Инварианты»: список инвариантов
`{title, description, forbidden[], is_active}` активного контекста, форма
добавления (title, description, forbidden-строки через запятую, is_active),
удаление по id и свитч вкл/выкл `is_active`. Неактивный инвариант виден в UI и
задиммлен. Слой помечен как контролируемый пользователем: ассистент его не
изменяет.

#### Scenario: Список инвариантов

- **WHEN** заданы инварианты
- **THEN** вкладка показывает их `{title, description, forbidden[], is_active}` списком, активность — свитчем

#### Scenario: Добавление, тумблер и удаление

- **WHEN** пользователь добавляет новый инвариант, выключает его тумблером и затем удаляет
- **THEN** состояние обновляется соответственно; неактивный остаётся видимым (задиммлен)

### Requirement: Проверка инвариантов (тесты)

Репозиторий SHALL содержать тесты, доказывающие: инъекцию блока инвариантов и
правила в system-промпт, срабатывание pre-guard при конфликте, срабатывание
post-guard (замена ответа + `invariant_violation`), тумблер `is_active` и
неизменность инвариантов при запросах. `scripts/e2e_studio.py` SHALL быть
расширен блоком «Инварианты»: GET → POST → GET содержит → `/api/rules` блок →
`/api/memory` entries → POST пустое → 400 → DELETE 200 → повтор DELETE 404;
exit 0 = PASS/SKIP, 1 = FAIL.

#### Scenario: Инъекция в payload (mock)

- **WHEN** задан активный инвариант и выполняется офлайн-запрос
- **THEN** payload LLM-запроса содержит блок инвариантов и правило; при конфликте — system-напоминание гарда

#### Scenario: E2E прогон

- **WHEN** запущен `python scripts/e2e_studio.py` (GPustack доступен)
- **THEN** пройден блок «Инварианты» (CRUD, 400, правила-блок, статистика); exit 0
