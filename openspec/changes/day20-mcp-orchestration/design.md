# Design: day20-mcp-orchestration

Ключевые решения и их обоснование. Детали реализации — в proposal + код.

## 1. 1 сервер = 1 тул (разбивка мультитул-серверов)

**Решение.** `task_manager` (2 тула), `news_weather` (4 тула),
`pipeline_tools` (3 тула) — 3 файла с 9 тулами — заменены **10
едицельными** серверами (1 сервер = 1 тул, без дублей): `weather`,
`news`, `digest_make`, `digest_read`, `task_create`, `task_get`,
`digest_search`, `digest_summarize`, `file_save`, `habr_news`. Общие
части вынесены в каркас `_mcp_base.py` (`run_server`) и
`_tasks_store.py`; `collector.py`/`pdf_writer.py` переиспользуются без
изменений. Поведение тулов — 1:1 с прежними (e2e day17–19 зелёные после
переноса).

**Почему.** (а) Едицельный сервер — атомарная единица маршрутизации:
имя сервера = имя его единственного тула, у модели нет выбора «какой из
9 тулов на этом сервере»; (б) нет дублей: до переноса `search`/
`summarize`/`saveToFile` были только в `pipeline_tools`, а `get_weather`
/`get_news` — в `news_weather`; после — каждый тул на своём сервере;
(в) каркас `call(args) -> (payload, is_err)` — один протокольный слой
на все 10 серверов, новый сервер = 1 файл ~100 строк.

## 2. Always-префикс `{server}__{tool}` (без логики коллизий)

**Решение.** Имена тулов в LLM-payload **всегда** `{slug}__{tool}`
(`_llm_tools`), `slug = re.sub(r"[^a-z0-9]+","_", name.lower()).
strip("_")` (фолбэк `server`). Логики детекта/разрешения коллизий **нет**
— префикс снимает проблему по построению (`weather__get_weather`,
`digest_search__search`). `tool_map: llm_name -> (server_id, real_tool)`
— обратный маршрут на сервер.

**Почему.** Дни 17–19 префиксовали только при коллизии — модель видела
набор имён, где `search` и `digest_search__search` могли сосуществовать,
и мелкая модель путалась. С always-префиксом имя уникально по
построению, rule в system-промпте тривиален («вызывай строго под именами
из каталога»), тесты детерминированы.

## 3. Каталог серверов в system-промпте + имена LLM = имена в истории

**Решение.** При подключённых серверах после `MCP_TOOLS_RULE` (v2)
добавляется `_mcp_catalog_block()`: строки `- {server} ({slug}):
{tool} — описание (до 120 симв.)` по каждому подключённому серверу.
Assistant-`tool_calls` и `role:"tool"`-сообщения **хранятся с
префиксированными именами** (те же, что в `tools` payload) —
routing proof: из payload журнала видно, что модель вызывает
`server__tool`; следующая итерация цикла и история диалога не имеют
расхождения «вызвал под одним именем, результат пришёл под другим».

**Почему.** Каталог — таблица «какой сервер даёт какой тул» в самом
«свежем» месте system-промпта; без него модель должна была угадывать
адресацию из описаний. Хранение LLM-имён в истории — требование
routing-proof задания (маршрутизация доказуема по данным диалога, а не
по интроспекции кода).

## 4. Кап tool-loop 15 (env `TOOL_LOOP_CAP`)

**Решение.** Лимит итераций tool-loop: 5 → **15**,
`_tool_loop_cap()` читает env `TOOL_LOOP_CAP` на каждый вызов
(тесты переопределяют). Превышение — SSE `error` «Tool-loop: превышен
лимит итераций (15)».

**Почему.** 10-шаговый кросс-серверный флоу = 10 tool-итераций +
итерация финального ответа; лимит 5 физически не пропускает задание.
15 — запас на рефайн-вызовы; env-переопределение — детерминированный
тест капа без ожидания 15 итераций.

## 5. Миграция реестра (12 дефолтов, идемпотентно)

**Решение.** `_ensure_defaults_locked` (`mcp.py`, под lock, при каждом
обращении): (1) старые мультитул-серверы `Task Manager`/`News &
Weather`/`Pipeline Tools` удаляются **по имени** (открытые клиенты
закрываются); (2) недостающие дефолты добавляются по имени
(id-генерация `mcp_<4 hex>`); (3) custom-серверы не трогаются. Пустой
файл — seed всех 12. Повторный вызов — no-op.

**Почему.** Миграция по имени (не по command-путям): удаляются ровно
канонические 3 имени дефолтов дня 17–19 — детерминировано, без
анализа команд. Идемпотентность обязательна: реестр живёт в реальном
`data/mcp_servers.json` (gitignored runtime-состояние) — повторный
старт/повторный вызов должны быть no-op, а не дублировать записи.

## 6. File-backed задачи (`data/tasks.json`)

**Решение.** Задачи `task_create`/`task_get` хранятся в файле
(`_tasks_store`), а не в памяти процесса: seed `TASK-42` (`in_progress`)
/`TASK-7` (`done`) — задачи дня 17; новая задача — `TASK-<max(числовые
id)+1>` (первая созданная — `TASK-43`). Атомарная запись (tmp +
`os.replace`); env `TASKS_FILE` — путь (тесты/e2e — tmp, репозиторий не
засоряется; `data/tasks.json` в `.gitignore`, seed регенерируется из
кода).

**Почему.** Едицельные сервера — **разные процессы**: in-memory store
дня 17 невозможен (`task_create` не увидит задачу `task_get`).
Файл — единственный общий слой между процессами (паттерн
`data/digests` дня 18).

## 7. Деградация live-источников (isError, no crash)

**Решение.** Тулы с сетью (`get_weather`, `get_news`, `get_habr_news`)
обёрнуты try/except: сбой fetch → `{"error": ...}` + `isError: true`,
процесс жив (каркас дополнительно ловит исключения `call`). В e2e
Part A сеть отрезана proxy-переменными `_NO_NET` (127.0.0.1:1) —
live-тулы детерминированно деградируют, офлайн-тулы (`digest_*`,
`task_*`, `file_save`) работают на реальных данных.

**Почему.** Офлайн-детерминированность Part A критична (MUST PASS
без сети); деградация в `isError` — поведение дня 18 (`news_weather`),
сохраняется 1:1. Живой баг, пойманный Part B: реальный контент Habr
(U+2011) не кодировался в cp1251 stdout → `UnicodeEncodeError` убивал
процесс — фикс `_mcp_base.py` (reconfigure `errors="replace"`, паттерн
дня 18 из `agent.py`) + регресс-тест на реальном subprocess
(`PYTHONIOENCODING=cp1251`).

## 8. E2E-гибрид 10-шагового флоу (Part A MUST PASS / Part B best-effort)

`scripts/e2e_day20.py`, stdlib, порт **8104** (17=8101, 18=8102,
19=8103):
- **Part A** (офлайн, в-процессе, без uvicorn): fake-LLM (скриптованный
  10-шаговый tool-цикл, стадии — по счётчику `role:"tool"` в payload) +
  `MCPRegistry` + **реальные MCP-субпроцессы всех 10 серверов**
  (`_NO_NET` у каждого); assert: tool-сообщения `{server}__{tool}` в
  порядке FLOW, **маршрутизация** (spy на `reg.call_tool`: (server,
  tool) пары == FLOW), передача данных между серверами, **кап**
  (скриптованный цикл > `TOOL_LOOP_CAP` → SSE `error` с текстом
  лимита). MUST PASS.
- **Part B** (live, uvicorn :8104, реальный LLM): подключение 10
  серверов через API → чат с 10-шаговым сценарием → PASS (≥10
  tool-сообщений + финальный ответ) или **SKIP** (поведение модели /
  занят порт — чужой сервер не убивается, ожидание до 10 мин). SSE
  `error`-кадр модели = SKIP (контракт: модельное поведение не FAIL).
  Cleanup всегда; exit 0 для PASS/SKIP, 1 для FAIL.

## 9. UI: бейджи «server · tool» (минимальный срез)

**Решение.** В шапке блока «🧩 Шаги агента» бейджи рендерят
`server · tool`: `formatToolName` режет префикс-имя по **первому** `__`
(`digest_search__search` → `digest_search · search`), `title={n}` —
полное имя на hover. Чипы StepRow сохраняют полное префиксированное имя
(детали шага — без усечений). Остальной UI дня 19 не трогается.

**Почему.** После always-префикса бейдж `search` (день 19) потерял
информацию о сервере — адресация `server · tool` в шапке — точная
картина «что и куда вызывала модель» без разворачивания блока.
