# Design: day21-knowledge-base

Ключевые решения и их обоснование. Детали реализации — в proposal + код.

## 1. Корпус = доки репозитория + код бэкенда + загрузки (20–30 страниц)

**Решение.** Корпус собирается автоматически из трёх источников:
`docs` (README.md, RELEASE.md, `docs/superpowers/**/*.md`,
`openspec/**/*.md`), `code` (`studio/backend/*.py`), `upload`
(`data/kb/uploads/*`, whitelist `UPLOAD_EXTS`). Замеренный корпус —
67 файлов, 139 261 слово (~в 11 раз больше минимума задания 20–30
страниц).

**Почему.** Задание требует корпус 20–30 страниц без внешнего
контента: собственные документы репозитория (спеки/планы/openspec
дней 12–20) — реальный корпус нужного объёма, а `studio/backend/*.py`
даёт агенту знания о собственном коде (live-проверка: на вопрос «какой
лимит tool-loop» модель ответила «15» из `agent.py`). Загрузки
пользователя (upload) — расширение корпуса; whitelist + basename-safe —
безопасность без параноидальных ограничений (паттерн `saveToFile` дня
19/20).

## 2. Две стратегии chunking (fixed 1200/200 + structural по заголовкам)

**Решение.** `FixedChunker` (1200 символов, overlap 200) и
`StructuredChunker` (markdown-заголовки `#..######`; секция > 2400 →
суб-чанки по fixed; код — файл целиком, > 2400 → суб-чанки).
Метаданные чанка: `{chunk_id, source, file, section, chars, text,
vector}`, `chunk_id = "{stem}-{strategy}-NNNN"`.

**Почему.** Задание требует 2 стратегии + метаданные. Fixed —
детерминированная «нулевая» стратегия; structural — использует
структуру документов (заголовок попадает в `section` — источник
цитируется в RAG-блоке `[file · section]`). Оверлэп 200 и суб-чанки >
2400 удерживают чанки в пределах разумного размера для эмбеддинга.
Честный результат сравнения (8 gold-запросов, api-эмбеддинги): fixed
hit@3 = 0.5, structural hit@3 = 0.25 — structural-чанки больше и их
меньше (целостность секции); метрики не скрываются, а показываются в
таблице сравнения.

## 3. Два эмбеддера (hash stdlib — офлайн/дефолт + api GPustack)

**Решение.** `HashEmbedder` (char 3-граммы → md5 → 256 бакетов,
L2-норм; только hashlib — встроенный `hash()` salted per-process) и
`APIEmbedder` (GPustack OpenAI-совместимый `/embeddings`,
`qwen3-vl-embedding-8b`, dim 4096, батчи 16, ключ
`GPUSTACK_KEY_EMBED`).

**Почему.** Тесты и Part A e2e обязаны быть офлайн/детерминированными
(конвенция дней 11–20) — hash-эмбеддер даёт это без зависимостей;
API-эмбеддер — «настоящий» путь (реальные эмбеддинги, dim 4096) для
live-проверки. Батчи 16 — разумный размер запроса для 1791 чанка
(162 с на сборку). Отдельный ключ `GPUSTACK_KEY_EMBED` — у провайдера
у ключа доступ к «своей» модели (паттерн per-model ключей дня 11).

## 4. Один локальный JSON-индекс, активная стратегия — одна, сравнение в индексе

**Решение.** `data/kb/index.json` (в `.gitignore`): метаданные
(strategy, embedder, model, dim, built_at, stats) + `comparison` (обе
стратегии: чанки, avg/max символов, hit@3, precision@3, MRR по 8
gold-запросам) + `chunks` **только активной** стратегии. Атомарная
запись (tmp + `os.replace`, паттерн `memory.py` дня 11). Сборка
`build()` считает чанки обеих стратегий (метрики сравнения), но
персистит одну.

**Почему.** Задание — «локальный индекс» как результат: JSON-файл —
прозрачен, debuggable, без новых зависимостей/сервисов (векторная БД —
YAGNI). Одна активная стратегия — простой поиск (один набор векторов),
сравнение остаётся видимым (отчёт в индексе + таблица в UI).
`chunk_id` с индексом в пределах файла — стабильная адресация чанка
для цитирования.

## 5. RAG — top-k выдержек в system-промпт на каждое сообщение (сбой не ломает чат)

**Решение.** `agent.build_kb_block(query, top_k)` — top-k (настройка
`rag_top_k`, дефолт 3) выдержек поиска по сообщению пользователя,
каждая ≤ 300 символов, блок добавляется в system-промпт на каждый
запрос; инструкция — цитировать источник `[file · section]`. Нет
индекса / сбой поиска / нет результатов → пустой блок + лог `[KB]`.

**Почему.** System-промпт — «самое свежее» место (паттерн
MCP-каталога дня 20, правил дня 12/14), RAG-контекст релевантен
именно текущему сообщению. Усечение 300 символов — контроль роста
system-промпта (top-k до 10). «Сбой не ломает чат» — жёсткое
требование: тумблер/база знаний не должны рвать диалог (тот же
паттерн, что best-effort авто-заголовка дня 11 и деградация
источников дня 18).

## 6. Тумблеры в `data/kb/settings.json` (чтение на каждый запрос)

**Решение.** `data/kb/settings.json` (в `.gitignore`), дефолты
`{agent_loop: true, rag: true, rag_top_k: 3, strategy: "structural",
embedder: "hash"}`; частичное обновление с валидацией (RU
`ValueError` → 400; лишние ключи игнорируются); агент читает settings
**на каждый запрос**. `agent_loop=false` → без `tools`-пейлоада, без
tool-loop (один LLM-вызов, паттерн дня 16 «без MCP-серверов»), без
MCP-каталога дня 20.

**Почему.** Задание требует тумблеры RAG и цикла-агента; файл +
чтение на каждый запрос — переключение без рестарта, детерминированно
тестируется (переключил между запросами — поведение сменилось).
`agent_loop` выключает ровно tool-loop дня 17/20 (единая точка —
сборка `tools` в `ask_stream`), остальной функционал дней 16–20 не
трогается.

## 7. `create_app(agent, kb)` — DI для тестов

**Решение.** `main.py` строит приложение функцией `create_app(agent,
kb)` (по умолчанию — реальные `StudioAgent`/`KnowledgeBase`); тесты
и Part A e2e инжектят свои экземпляры (tmp `kb_dir`, fake-MCP).

**Почему.** Паттерн DI `StudioAgent(mcp=...)` дня 16/17: офлайн-тесты
роутов `/api/kb/*` через TestClient без реального `data/kb/` и без
сети; роуты описываются внутри `create_app` — замыкаются на
инжектированных объектах.

## 8. E2E-гибрид (порт 8105): Part A детерминированный, Part B live

**Решение.** `scripts/e2e_day21.py` (stdlib): Part A — офлайн, без
uvicorn/сети, 10 assert (корпус, оба чанкера, hash build/rebuild/
search, settings-валидация, `/api/kb/*` через TestClient,
`agent_loop` с fake-MCP, RAG on/off в LLM-payload), MUST PASS; Part B
— live (uvicorn :8105, реальный LLM + API-эмбеддер), best-effort
(10/10 PASS на этой машине: индекс 1791 чанк / 162 с / dim 4096,
поиск «tool-loop», RAG-чат — ответ «15» на вопрос про `TOOL_LOOP_CAP`,
`agent_loop=false` → без `tools`).

**Почему.** Конвенция e2e дней 17–20: доказательство корректности —
детерминированное ядро (MUST PASS), проверка живого RAG — best-effort
(поведение модели не FAIL; бессмысленный ответ — не FAIL, отсутствие
KB-блока в payload — FAIL). Порт 8105 продолжает последовательность
(8101–8104 — дни 17–20); port-busy — ожидание до 10 мин (паттерн дня
20).
