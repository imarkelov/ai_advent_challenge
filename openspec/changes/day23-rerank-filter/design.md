# Design: day23-rerank-filter

Ключевые решения и их обоснование. Детали реализации — в proposal + код.
Контекст: реранкер (cross-encoder `qwen3-reranker-4b`) и 2-этапный поиск
уже есть с дня 21 (`search_rag`: гибридный recall top-`rag_recall` →
опциональный rerank → top-`rag_top_k`), сравнение двух рук — с дня 22
(`POST /api/rag/compare`). День 23 добавляет порог, rewrite и 4-режимное
сравнение поверх существующего, без пересборки пайплайна.

## 1. Фильтр: после stage1-отбора (и rerank), до top_k-среза

**Решение.** Отсечение по порогу выполняется в `search_rag` ровно в одной
точке: после stage1-сбора выдачи (и после rerank-пересортировки, если
`reranker=api` сработал) и до среза `[:top_k]`. При `min_score <= 0.0`
ветка не меняется (байт-в-байт текущее поведение). Ответ поиска
дополняется аддитивными полями `filtered: bool` (true, если
`min_score > 0`) и `dropped: int` (сколько результатов отброшено);
существующие поля (`score`, `rerank_score`, `stage1_rank`,
`recall_total`, `reranked`) не меняются.

**Почему.** Порог отвечает на вопрос «достоверна ли релевантность
нашедшегося?», а достоверность определяется **последней** стадией
оценки: если сработал cross-encoder — его `rerank_score`, если нет —
гибридный RRF-счёт stage1. Фильтровать до rerank нельзя: reranker как
раз пересматривает оценки (stage1-топ может уехать вниз), и порог по
устаревшим счётам отбросил бы то, что cross-encoder потом признал бы
релевантным. Фильтровать после `top_k`-среза тоже нельзя: сначала
отсечено N−k «хвостовых» нерелевантных, затем взят top_k из
остатков — «топ-K до и после фильтрации» (задание дня) требует, чтобы
top_k выбирался из прошедших порог. Позиция «после оценки, до среза»
также единая для всех 3 потребителей `search_rag` (`_rag_retrieve`
live-чата, `/api/kb/search`, `rag_compare`) — консистентность: фильтр
в чате, поиске и compare работает одинаково.

## 2. Семантика `min_score`: on/off, `>=`, relative-нормализация при `reranker=off`

**Решение.** `min_score` — число 0..1, default **0.0**.
- `min_score = 0.0` (default) → **фильтр выключен, поведение байт-в-байт
  как до дня** (регрессия закреплена снимком-сравнением списков).
- `min_score > 0` → семантика `>=`: результат проходит, если его
  (актуальная) оценка `>= min_score`.
- `reranker=api` (rerank сработал) → отсечение по **`rerank_score >=
  min_score`** (шкала cross-encoder 0..1, абсолюта).
- `reranker=off` (или rerank деградировал на stage1) → отсечение по
  **относительной нормализации: `score >= min_score * best`**, где
  `best = max(score)` по прошедшей stage1 выдаче (guard: `best == 0`
  → вернуть пустой список, деления нет).
- `min_score = 1.0` — допустим: единственный результат с оценкой,
  равной максимуму, остаётся (`>=`, не `>`).

**Почему.** Абсолютная шкала 0..1 осмыслена только для cross-encoder:
его `rerank_score` — вероятность-подобная оценка пары (query, doc).
Сырой RRF-счёт гибридной выдачи = Σ 1/(60+rank) ≈ **0.003–0.033**:
абсолютный порог 0.5 на нём отсекал бы ВСЕГДА (даже perfect top-1),
а 0.01 — почти никогда. Поэтому без реранкера порог интерпретируется
**относительно лучшей выдачи**: «отбрось чанки, заметно хуже лучшего
для ЭТОГО запроса» — нормализация `score/best ∈ (0, 1]` даёт ту же
0..1-семантику для обоих режимов. Побочное следование (принято
осознанно): в relative-режиме лучший результат всегда проходит любой
порог < 1.0 (`score/best = 1.0`) — порог без реранкера фильтрует
хвост относительно лидера, а не лидер. `>=` (а не `>`) — порог 1.0
с перфект-совпадением не пустит выдачу в пустоту. Default 0.0 = off —
обязательный регрессионный гард: включение дня не должно менять
поведение существующих потребителей (548 backend-тестов, e2e_day21/22)
до тех пор, пока пользователь сам не задаст порог.

## 3. Четыре армы compare: plain | rag | rag+filter | rag+rewrite

**Решение.** `agent.rag_compare` расширяется с 2 рук до 4 арм:
- **plain** — голый system-промпт, без retrieval. Без изменений.
- **rag** — `config.system_prompt` + `kb_block` из `search_rag`.
  Без изменений.
- **rag+filter** — retrieval тем же `search_rag`, но с `min_score`
  (из body-override `min_score` запроса; если не задан — из
  `settings["min_score"]`); ответ на оригинальном вопросе.
- **rag+rewrite** — сначала `rewrite_query(question)`; retrieval
  выполняется на **перефразированном** вопросе; ANSWER-LLM отвечает на
  **оригинальный** вопрос.

**plain/rag НИКОГДА не фильтруют** — даже если `min_score > 0` в
settings или body: это контрольные руки, их задача — показать «RAG без
фильтра», иначе фильтр невозможно отличить от baseline. Ответ
эндпоинта — **аддитивный**: старые поля дня 22 (`answer_plain`,
`answer_rag`, `kb_block`, `chunks`, `rag_context`) сохраняются с теми
же именами/типами; добавляются `answer_rag_filter`,
`answer_rag_rewrite`, per-arm `chunks_rag_filter`/`chunks_rag_rewrite`
и `rag_context_rag_filter`/`rag_context_rag_rewrite`,
`rewritten_query`, `rewrite_applied`.

**Почему.** Задание дня требует сравнить «качество без фильтра/
rewriting» и «качество с фильтром» — это минимум 4 конфигурации
(база × {фильтр, rewrite} × {plain, rag}); единый эндпоинт с 4
руками повторяет аргумент дня 22 (§1 дизайна дня 22): атомарное
сравнение, одна точка согласованности, все руки на одном индексе и
settings в один момент. Body-override `min_score` обязателен: при
default 0.0 арма rag+filter без override дублировала бы rag, и
сравнение «фильтр vs без фильтра» было бы невозможно без изменения
глобальных settings. Ответ на оригинальном вопросе в rewrite-арме —
rewrite улучшает **retrieval**, а не вопрос: отвечать на перефраз
изменило бы задачу сравнения (пользователь спрашивал своё). Все 4
руки — non-stream `_task_llm_call` (T=0, max_tokens=1024, bare
промпт, как у существующих рук; журнал `requests.json` не пишется,
паттерн дня 22); сбой LLM-вызова руки — строка «Ошибка: …»
(существующий per-arm паттерн), статус 200.

## 4. Query rewrite: один вызов, compare-only, graceful fallback

**Решение.** `StudioAgent.rewrite_query(question) -> (str, bool)`:
один non-stream LLM-вызов (тот же механизм, что в `rag_compare` —
`_task_llm_call`), **T=0, max_tokens=200**. System-промпт (RU):
«Ты перефразируешь вопрос пользователя для точного поиска по базе
документов. Ответь ОДНИМ предложением, ключевыми словами, без
приветствий и объяснений». Возврат:
- непустой (после `.strip()`) ответ, **не идентичный** оригиналу
  (case-insensitive) → `(rewritten.strip(), True)`;
- пустой/whitespace/идентичный → `(question, False)`;
- исключение из LLM → `(question, False)` + log warning (НЕ «Ошибка:»
  наружу).

Метод вызывается **только** из `rag_compare` (rewrite-арма). Из
`ask_stream`/чат-пайплайна — никогда (guardrail-тест: monkeypatch
`rewrite_query` на spy → `ask_stream` завершается, spy не вызван;
статический grep-тест «rewrite_query не упоминается в ask_stream»
допускается).

**Почему.** Rewrite решает проблему формулировки: пользовательский
вопрос («какой отпуск у инженера») и корпусная лексика («отпускной
стаж», «отпускные дни») лексически расходятся → BM25-нога слабеет.
Перефраз «ключевыми словами под поиск» приближает запрос к корпусу.
Один вызов (не multi-query fan-out) — scope-гард дня: multi-query
(несколько перефразов + фузия) удраил бы LLM-вызовы и время сравнения
без гарантированного выигрыша; auto-tuning порога — тоже вне scope.
T=0/max_tokens=200 — детерминизм и жёсткий бюджет (200 токенов
хватает на одно предложение; больше — мусор). Фолбэк на оригинал
при сбое — rewrite это оптимизация, а не обязатель: LLM down не
должен ломать compare-арму (арма отвечает на оригинале,
`rewrite_applied=false`, без «Ошибка:» — арма жива). Compare-only —
решение пользователя на интервью: live-чат остаётся предсказуемым
(rewrite добавляет задержку и неопределённость в каждый запрос),
пока эффект rewrite не доказан сравнением; guardrail-тест фиксирует
границу.

## 5. Degradation: rewrite-sбой, reranker-down, всё-отфильтровано

**Решение.** Три деградационных сценария — все «ответ остаётся,
качество ниже», ни один не даёт 5xx/«Ошибка:» на живой руке:
- **Rewrite-сбой** (LLM down/таймаут/не-строка): `(question, False)` —
  retrieval на оригинале, `rewrite_applied: false`,
  `rewritten_query` = оригинал, `answer_rag_rewrite` — обычный ответ
  (не начинается «Ошибка:»).
- **Reranker down при `min_score > 0`** (нет ключа `GPUSTACK_KEY_
  RERANK` / API-сбой → деградация дня 21 на stage1, `reranked=false`):
  фильтр **не отключается и не падает** — переключается на
  relative-режим §2 (`score >= min_score * best` по stage1-счётам).
- **Всё отфильтровано** (`min_score=0.999`, все оценки ниже): 200,
  `chunks_rag_filter == []`, `kb_block` пустой, `answer_rag_filter` —
  непустой ответ без контекста (LLM отвечает на голом промпте;
  «не знаю по базе» — это честный ответ, не ошибка).

**Почему.** Каждый сбой деградирует на ближайшую рабочую конфигурацию,
а не прерывает запрос: это паттерн дней 18/21 (деградация источника —
не фейл). Reranker-down → stage1-фильтр важнее «отменить фильтр»:
пользователь явно захотел порог; stage1-оценка (relative) — лучшее
доступное приближение. Всё-отфильтровано → пустой контекст допустим:
это и есть **смысл** фильтра (лучше «нет ответа из базы», чем ответ на
нерелевантном чанке); ответ всё равно генерируется — пользователь
видит, что рука работала.

## 6. Аддитивный контракт compare (e2e_day22 остаётся green)

**Решение.** Ответ `POST /api/rag/compare` расширяется **только
добавлением полей**: имена, типы и значения существующих day22-полей
(`answer_plain`, `answer_rag`, `kb_block`, `chunks`, `rag_context`)
не меняются; plain/rag-руки выполняются ровно как в дне 22 (те же
вызовы, те же параметры, retrieval без `min_score`). Новые поля —
`answer_rag_filter`, `answer_rag_rewrite`, `chunks_rag_filter`,
`chunks_rag_rewrite`, `rag_context_rag_filter`, `rag_context_rag_
rewrite`, `rewritten_query`, `rewrite_applied`. Фронтенд читает новые
поля как опциональные (undefined-safe при старом бэкенде). Регрессия
закреплена: `scripts/e2e_day22.py` Part A (7 шагов, ~51 ссылка на
старые поля) должен пройти 7/7 без правок; дополнительно — тест
«day22-формы byte-совместимы» (сравнение с эталонным payload).

**Почему.** Контракт дня 22 уже потребителями: e2e_day22.py,
compare_day22.py, UI-секция «Сравнение RAG». Breaking-изменение
(переименование/типы) сломало бы их и стёрло доказательную базу
дня 22. Аддитивность = старый consumer работает без изменений, новый
видит новые армы. 5-я арма (filter+rewrite) запрещена scope-гардом:
каждая рука = +1 LLM-вызов (~10–30 c), 5 рук утрируют время сравнения
и размывают интерпретацию (2 фактора сразу).

## 7. Валидация `min_score`: bool первым, 400 RU

**Решение.** Валидация в `kb.update_settings` (settings) **и** в body-
override `POST /api/rag/compare` (одна и та же логика): (1)
`isinstance(v, bool)` → 400 **первым** — Python-ловушка
`isinstance(True, int)` пропустила бы `true` как 1.0; (2) `isinstance(
v, (int, float))` и `0.0 <= v <= 1.0` → 200, сохранение как float;
(3) всё остальное (строки, `"0.5"`, None, контейнеры) → 400. Detail —
RU в существующем стиле `update_settings` («min_score должен быть
числом от 0 до 1»). Диапазон инклюзивный: 0 и 1 валидны.

**Почему.** JSON не различает bool/int явно для Python-парсинга:
`true` декодируется в `True`, и наивная `isinstance(v, (int, float))`
пропустила бы `{"min_score": true}` как 1.0 — фильтр с порогом 1.0
без ведома пользователя (см. §2: 1.0 — агрессивный порог). Bool-гвард
первым устраняет ловушку. Строки-числа (`"0.5"`) — 400, а не
парсинг: settings-контракт дня 21 строго типизирован (паттерн
`rag_top_k`/`rag_recall`), имплицитный cast скрывал бы ошибки клиента.
Два места валидации (settings + compare body) — одна функция, одна
семантика: body-override не может обойти проверку, которую settings
не проходит.

## 8. E2E-порт 8107

**Решение.** `scripts/e2e_day23.py` — на порту **8107** (продолжение
последовательности: 8100 — `e2e_studio.py`, 8101–8104 — дни 17–20,
8105 — день 21, 8106 — день 22), каркас `e2e_day22.py`: Part A —
офлайн-детерминированное ядро (net cut `_NO_NET`, TestClient +
fake-LLM + fake-reranker, MUST PASS), Part B — live (uvicorn :8107,
реальный GPustack LLM + API-реранкер) best-effort (down → SKIP,
port-busy → wait 10 мин → SKIP), cleanup всегда, exit 0 для
PASS/SKIP, 1 для FAIL. Детерминированные фикстуры — те, что в
`test_kb.py`/`test_rag_compare.py` (fake-reranker scores
`[0.99, 0.5, 0.1]`, egg-book-корпус из `studio/backend/tests/
fixtures/`), runtime-артефакты `data/kb/` Part A не использует.

**Почему.** По 1 порту на e2e-скрипт — устоявшаяся схема (дни 17–22),
не даёт e2e-прогонам вставать друг у друга; `data/kb/` gitignored →
Part A на committed-фикстурах детерминирован на любом клоне без сети
(аргумент §6 дизайна дня 22). Part A MUST PASS — гейт дня: фильтр,
валидация, 4 армы, rewrite fallback, регрессия day22-формы —
проверяются офлайн; live-смысл (качество перефразов, живые оценки
cross-encoder) — best-effort, т.к. непредсказуем (методология hard/
soft дня 22 §5).
