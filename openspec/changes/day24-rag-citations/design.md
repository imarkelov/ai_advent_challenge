# Design: day24-rag-citations

Ключевые решения и их обоснование. Детали реализации — в proposal +
код. Контекст: RAG-чат (`ask_stream` + `kb_block` + `rag_context` в
assistant-сообщении) есть с дня 21, per-диалог RAG-режим — с дня 22,
`min_score`-фильтр во всех 3 потребителях `search_rag` — с дня 23.
`search_rag` уже отдаёт `{chunk_id, source, file, section, score,
text, ±rerank_score, stage1_rank}`, а `chunks[].text` — уже verbatim-
выдержка ≤2400 (чанк ≤2400 — полный текст, иначе фокус-окно 300;
`_focus_snippet`). День 24 добавляет обязательные
источники+цитаты, [n]-правило и dont-know в live-чат, без пересборки
пайплайна и без правок `kb.py`.

## 1. Гибрид A+B: код прикладывает цитаты, модель ссылается маркерами

**Решение.** Цитаты НЕ генерируются моделью: код берёт verbatim-
выдержки из результатов `search_rag` (`chunks[].text` — чанк ≤2400
символов: полный текст (фиксы дня 24 после релиза), иначе
300-символьное фокус-окно, центрируется на характерном токене запроса
— механика дня 21). Модель получает instruction ссылаться на выдержки
маркерами [n]: `kb_block` уже нумерован (`1. [file · section] — …`),
в конец непустого блока добавляется строка `CITE_RULE`
(«Ссылайся на выдержки в ответе маркерами [1], [2], … по номерам.
Опирайся только на приведённые выдержки; если выдержки не покрывают
факт — так и скажи.»). Чанки в `rag_context` дополняются
аддитивным `chunk_id`.

**Почему.** Задание дня: «модель обязательно возвращала ответ, список
источников (source + section/chunk_id), цитаты (фрагменты из найденных
чанков)». Если цитаты генерировала бы модель, «цитата» стала бы
перефразом — анти-галлюцинационная цель утрачена (мелкие модели
упрямствуют и «цитируют» своими словами). Вариант A (только код)
даёт гарантированные verbatim-фрагменты и точные source/section/
chunk_id; вариант B (только модель) — естественные ссылки [n], но
ненадёжные цитаты. Гибрид (выбор пользователя) берёт надёжность A
(цитаты/источники — код) и читаемость B (ссылки [n] — модель).
Почему не хранить полный текст чанка: guardrail дня — только focused
snippet ≤300 (полный текст раздувает сообщение и хранится в индексе);
фикс дня 24 после релиза: окно 300 не накрывало иголку в хвосте
1200-чанка (якорь-токен запроса у головы чанка, пасхалка «Sony 3310»
в хвосте — live-проверка пользователя) → чанки ≤1300 символов уходят
в сообщение целиком, чанки >1300 сохраняют фокус-окно 300; второй
фикс (порог 1300 → 2400): live-кейс — целый файло-чанк 1671 символов
без markdown-заголовков (один чанк «whole file»), пасхалки-имена в
хвосте, якорь у головы — при пороге 1300 модель видела только 300-
символьное окно у головы и не видела имён → теперь ВСЕ структурные
секции/файлы ≤2400 символов (2400 = порог субчанков
`StructuredChunker`) уходят в сообщение целиком, чанки >2400
сохраняют фокус-окно 300.
Почему `chunk_id` аддитивно в `_kb_context`: `search_rag` уже отдаёт
его в каждом результате, не хватает только поля в объекте чанка
`rag_context` (Oracle-1 watch-out); аддитивность — старые сообщения
читаются undefined-safe.

## 2. CITE_RULE — только в `kb_block`, только когда блок непустой

**Решение.** Строка правила добавляется в конец `kb_block` ровно
тогда, когда блок непустой (есть выдержки). Пустой результат,
RAG-off, нет индекса → правила нет. Точная строка вынесена в
константу `CITE_RULE` (ассерт в тестах и e2e по константе, не по
hardcoded-строке в каждом месте).

**Почему.** Правило «ссылайся на выдержки [n]» без самих выдержек —
бессмыслица для модели (ссылаться не на что) и шёпот в пустоту
при RAG-off. Пустой блок и RAG-off — разные пути, но для
system-промпта результат один: правило не появляется. Единообразная
точка инъекции (`_render_kb_block`) — один механизм для всех
потребителей `ask_stream`. E2e ассертит **наличие строки в LLM-
payload** (детерминированно, fake-LLM capture), НЕ комплаенс модели
маркерам: мелкие модели (glm/deepseek flash) ссылаются на [n]
ненадёжно, и ассерт на комплаенс дал бы false-FAIL на live-
сценариях (паттерн дня 22: live-семантика — best-effort WARNING,
структура — MUST PASS).

## 3. Dont-know: триггер A′, 0 LLM-вызовов, точный done-контракт

**Решение.** В `ask_stream`, после retrieval и до LLM/tool-loop:
если RAG-вкл (эффективный per-диалог режим дня 22), поиск **успешен**
(не KBError) и `len(results) == 0` — при ЛЮБОМ `min_score`, включая
0 — агент сохраняет assistant-сообщение (content = `DONT_KNOW_TEXT`,
`rag_context = {recall_total, reranked, chunks: [], dont_know: True}`)
и отдаёт `done` с `usage: None`, `request_id: None` — **без LLM-
вызова** (паттерн no-LLM done profile-turn, agent.py:797-798).
Константа (контракт): `DONT_KNOW_TEXT = "Не знаю. В базе знаний не
нашлось релевантных материалов. Уточните, пожалуйста: о каком
документе или теме вы спрашиваете?"`.

**Почему.** Триггер A′ (0 чанков после поиска/фильтра) — единственный
детерминированный сигнал «в базе нет релевантного»: score-порог —
вопрос настройки (день 23), а «0 результатов при фильтре off»
означает, что retrieval вообще ничего не нашёл. Условия разведены
осознанно: **нет индекса / KBError** → обычный LLM-чат (индекс —
опция, не обязательность; «не знаю» из-за отсутствия индекса было бы
ложным — модель знает ответ по-своему); **RAG-off диалог** →
retrieval не идёт, dont-know по построению невозможен (режим
выбран пользователем явно). 0 LLM-вызовов (assert: fake-LLM count ==
0) — смысл усиления задания: модель не должна «додумывать» ответ на
пустом контексте; `usage: None`/`request_id: None` — честный учёт
(токенов не было, запроса в журнале нет; паттерн profile-turn).
`rag_context` с `chunks: []` + `dont_know: true` — всё внутри
существующего поля (новых message-полей нет, UI и история
undefined-safe). Intercept стоит ПОСЛЕ task-guard и profile-turn
(они выше и не трогаются) и ДО tool-loop: dont-know не должен
пускать модель в MCP-цикл на пустом RAG-контексте.

## 4. UI: вариант B — панель «Источники и цитаты» + «Не знаю»

**Решение.** `SourcesPanel` (props `{ragContext, minScore?}`)
рендерится под assistant-ответом рядом с `RagContextInspector` (оба
инспектора сосуществуют — выбор пользователя; `RagContextInspector`
не удаляется и не меняется, `FlowInspector` не трогается). Панель
(вариант B, мокап `.omo/mockup/day24-b.html`): заголовок «📖
ИСТОЧНИКИ И ЦИТАТЫ» + счётчик; карточки — номер 1..N, `file ·
section`, score-чип (🟢 ≥0.8 / 🟡 0.5–0.8 / 🔴 <0.5 — та же шкала,
что RagContextInspector), «из #N» (`stage1_rank`) при `reranked`,
verbatim-цитата в «» из `text`. `dont_know: true` → красная карточка
«🚫 Не знаю» с причиной (min_score/отсечено — `minScore` из
kb-settings, undefined-safe) и подсказкой «Уточните вопрос»;
чанк-карточки НЕ рендерятся. Старое сообщение (без `dont_know`/
`chunk_id`) → панель рендерится без краха; `chunks` пусто и
`dont_know` нет → null (панели нет). Маркеры [n] во фронтенде НЕ
рендерятся — панель автономна от текста ответа.

**Почему.** Вариант B выбран пользователем после сравнения трёх
мокапов (A, A2, B): B даёт «карточки как документы» (номер,
метаданные, score, цитата в кавычках) — самая читаемая верификация
«откуда ответ»; красная «Не знаю» карточка явно отделяет dont-know
от обычного ответа. Оба инспектора — осознанное решение
пользователя (RagContextInspector — отладочный детальный view,
SourcesPanel — пользовательский view; дублирование данных допустимо,
удаление старого — breaking для отладочного флоу дня 21). Счётчик и
«из #N» повторяют семантику RagContextInspector — один дизайн-язык.
[н]-рендер не нужен: панель и текст ответа независимы, подгонка
маркеров к номерам чанков — хрупкая (модель может не сослаться).

## 5. E2E: порт 8108, Part A MUST PASS / Part B best-effort

**Решение.** `scripts/e2e_day24.py` (stdlib, порт **8108**, каркас
`e2e_day23.py`): Part A — офлайн-детерминированное ядро (net cut
`_NO_NET`, TestClient + fake-LLM + tmp-БЗ, MUST PASS): A1 — 10
контрольных вопросов × `POST /api/chat` (RAG-вкл, min_score=0):
per-question `(chunks непусто → citations непусто И sources-поля
(source/file/section/chunk_id) присутствуют) OR rag_context.
dont_know == true`; A2 — dont-know-детерминизм (вопрос без
совпадений, min_score=0 → `done.answer == DONT_KNOW_TEXT`,
usage `None`, request_id `None`, fake-LLM count == 0, dont_know:
true); A3 — CITE_RULE-строка в captured LLM-payload (kb_block
непустой); A4 — verbatim: `chunks[i].text` ⊂ сохранённого текста
чанка из БЗ И `len <= 2400` (чанк ≤2400 — полный текст);
A5 — chunk_id в rag_context совпадает
с chunk_id из БЗ; A6 — регрессия shape rag_context (recall_total/
reranked/chunks) и min_score-поля дня 23. Part B — live
(uvicorn :8108, реальный GPustack), best-effort: B1 — wipe →
корпус (`fetch_books.py`: primary → fallback → committed seed) →
индексация (structural + api-эмбеддер; API недоступен → SKIP всей
Part B); B2 — 10 вопросов в одном диалоге: 10/10 done — MUST,
sources/citations при <10/10 — **WARNING, не FAIL** (retrieval-
качество на 1666 чанках не гарантирует 10/10 — факт дня 22:
sources_ok 7/10); B3 — dont-know live (min_score=0.999 →
DONT_KNOW_TEXT + dont_know:true; API-сбой → SKIP); B4 — сброс
min_score в 0 (cleanup). Смысл ответа ↔ цитат — **вне e2e**
(документирован в скрипте: user manual check).

**Почему.** По 1 порту на e2e-скрипт — устоявшаяся схема (8100 —
`e2e_studio.py`, 8101–8104 — дни 17–20, 8105 — день 21, 8106 — день
22, 8107 — день 23; 8108 свободно). Part A MUST PASS — гейт дня:
контракт dont-know, verbatim-цели, chunk_id, CITE_RULE проверяются
офлайн и детерминированно; live-смысл (качество retrieval,
комплаенс модели [n]) непредсказуем → WARNING/SKIP (методология
hard/soft дня 22). Смысл ответа ↔ цитат — «глазами пользователя»
(решение на интервью): LLM-judge и эмбеддинговые близости —
косвенные и ложноположительные (день 22 показал: judge-вердикты
не разделяют режимы), поэтому e2e проверяет только структуру, а
смысл — ручной live-чек пользователя (User-Verification плана).
