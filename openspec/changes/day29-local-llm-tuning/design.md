# Design: day29-local-llm-tuning

## Контекст

День 29 — оптимизация локальной LLM под задачу «поиск новых сериалов».
Опирается на дни 26 (локальная Ollama как провайдер: `LOCAL_MODELS`,
`_base_for()`) и 28 (полностью локальный RAG-пайплайн: эмбеддер
`ollama`). Обе части уже есть; день 29 добавляет **слой настройки под
задачу** и **измерение**.

## Ключевое инженерное открытие: `num_ctx` через OpenAI-совместимый API не работает

Задание требует настроить context window. Проверка на живой Ollama
0.34.4 (M3 Max, 48 ГБ) показала, что **через OpenAI-совместимый
эндпоинт `/v1/chat/completions` параметр `num_ctx` игнорируется**:

```
$ ollama ps                                    # после холодного запуска
qwen3-coder:30b   20 GB   100% GPU   CONTEXT 32768
```

Ситуация не меняется ни при `num_ctx` в корне тела, ни внутри
`options`. `CONTEXT` остаётся 32768 — это автоматический размер по
VRAM (исследование подтверждает: `OLLAMA_CONTEXT_LENGTH=0` →
авто-подбор 4k/32k/256k по видеопамяти; на 48 ГБ попадаем в бакет
32k).

**Следствие:** настройка context window обязана идти через **нативный**
эндпоинт `/api/chat` (там `options.num_ctx` — документированный
параметр). Поэтому профиль применяется так:

* параметры, которые понимает OpenAI-совместимый API
  (`temperature`, `top_p`, `max_tokens`, `seed`, `stop`) — уходят как
  есть (текущий путь дней 11–28 не меняется);
* `num_ctx` — уходит **только** нативным вызовом `/api/chat`, и только
  для локальных моделей (у GPustack такого понятия нет).

Это добавляет в `agent.py` второй путь вызова локальной модели, но
только для тех запросов, у которых профиль задаёт `num_ctx`. Запросы
с `num_ctx=None` (профиль `studio`, все удалённые модели) идут
прежним путём — регрессия гарантирована.

## Почему выбран кейс «поиск сериалов»

Кейс проверяем **машиной**, а не на вкус:

* есть реальный каталог (Wikidata, 400 сериалов после нормализации) с
  жанрами, годами, странами;
* у запроса есть жёсткие ограничения (жанр/год/страна/длина) —
  значит, `constraint_satisfaction` считается точно;
* выдуманный сериал ловится сразу: его `id` нет в каталоге —
  `hallucination_rate` считается точно;
* «пустые» запросы (например, «вестерн 2025 года», которого в
  каталоге нет) проверяют честность отказа.

Так оптимизация превращается в эксперимент с метриками, а не в
подбор «на ощупь».

## Три рычага оптимизации и что именно менялось

### 1. Параметры (`temperature`, `max_tokens`, context window)

| Параметр | Дефолт (`studio`) | Кейс (`series`) | Обоснование |
|---|---|---|---|
| `temperature` | 0.7 | **0.2** | рекомендация — задача выбора из списка; нужна воспроизводимость и верность каталогу, а не креатив |
| `max_tokens` | 2048 | **512** | ответ — 3–5 коротких JSON-объектов; 2048 — перерасход латентности |
| `num_ctx` | не задан (авто 32k) | **8192** | хватает на каталог-кандидаты + правила; явное окно дешевле по KV-кэшу и снимает «context rot» |
| `top_p` | 0.9 | 0.9 | не трогаем: главный рычаг — `temperature` |
| `seed` | не задан | **29** | воспроизводимость замеров |

**Почему `num_ctx` не «чем больше, тем лучше».** Ollama выделяет
KV-кэш **сразу под весь `num_ctx`**, а не по факту промпта. Формула:

```
KV = 2 × n_layers × n_kv_heads × head_dim × n_ctx × bytes_per_element
```

Для `qwen3-coder:30b` (48 слоёв, 4 KV-головы, head_dim 128) это
**96 КиБ/токен** → 3.00 ГиБ на 32k. Авто-дефолт 32k впустую держит
3 ГиБ, тогда как промпту кейса достаточно 8k (0.75 ГиБ). Плюс
деградация качества на длинном контексте («Lost in the Middle»,
RULER) — поэтому окно берётся по реальному размеру полезной нагрузки.

### 2. Квантование

В Ollama уже лежат три модели в `Q4_K_M`. Замер квантования сделан
**двумя способами** — потому что скачать более точный квант в этом
окружении не удалось (реестр Ollama отдавал 503, а загрузка 29-ГБ
`Q8_0` оборвалась на 28.7 ГБ из-за нестабильного DNS к хранилищу R2):

1. **Сравнение семейств моделей на ОДНОМ кванте** (`Q4_K_M`) —
   `qwen3-coder:30b` (MoE), `gemma3:27b` (плотная),
   `glm-4.7-flash` (MoE + reasoning). Одинаковый профиль, один
   промпт, одни кандидаты, один `seed`. Это измеряет практический
   компромисс «качество ↔ память ↔ скорость», который и определяет
   выбор модели.
2. **Готовая A/B-пара** `series_q4` / `series_q8` (`gemma3:4b` в
   `Q4_K_M` против `gemma3:4b-it-q8_0`) — профили заведены и
   протестированы, отличие в них **только квант**. Запускается одной
   командой, когда `ollama pull gemma3:4b-it-q8_0` доедет:

   ```bash
   python scripts/series_eval.py --profiles series_q4,series_q8
   ```

Протокол сравнения — контролируемый: одинаковые промпты и кандидаты,
`temperature=0.2`, фиксированный `seed` (дефолт Ollama — случайный),
одинаковые `num_ctx` и `num_predict`, прогрев перед замером.

Ожидание из литературы: Q4_K_M ≈ +0.9 % перплексии к F16 при ~29 %
размера; Q6_K — в пределах 0.1 % от F16; Q8_0 даёт ~+0.2 %, но
**медленнее** (bandwidth-bound: 50.9 против 71.9 т/с в бенчмарке
llama.cpp). То есть на задаче рекомендаций выигрыш Q8_0 может оказаться
в пределах шума, а цена — вдвое больше памяти и ниже скорость.

### Ключевой вывод по KV-кэшу: модели неравны в 8 раз

Формула `KV = 2 × n_layers × n_kv_heads × head_dim × n_ctx × bytes`
показывает, что при **одинаковом** `num_ctx=8192` цена контекста
различается радикально (архитектуры сняты с живой Ollama):

| Модель | Слоёв | KV-голов | f16 КиБ/токен | KV на 8192 |
|---|---|---|---|---|
| `qwen3-coder:30b` | 48 | **4** | **96** | **0.75 ГиБ** |
| `gemma3:27b` | 62 | **16** | 496 | 3.88 ГиБ |
| `glm-4.7-flash` | 47 | 20 | 940 | 7.34 ГиБ |

`qwen3-coder` в 8 раз дешевле по контексту, чем `gemma3` (4 KV-головы
против 16 — GQA 8:1). Это и есть главный аргумент выбрать его основной
моделью кейса: при том же окне он тратит 0.75 ГиБ вместо 3.88 ГиБ, а
по качеству на замере не уступает.

### 3. Prompt-шаблон

Дефолтный `system_prompt` — «ассистент Студии, отвечай кратко». Он не
знает ни про каталог, ни про формат. Для кейса написан
`SERIES_SYSTEM_PROMPT` с четырьмя элементами:

1. **роль** — «эксперт по сериалам, подборщик рекомендаций»;
2. **вход** — каталог кандидатов с `id`/годом/жанрами/страной/IMDb;
3. **жёсткие правила** — четыре ограничения, из которых главное:
   «рекомендуй ТОЛЬКО из каталога, используй ровно те id»;
4. **формат** — JSON + few-shot пример.

Приёмы, взятые осознанно:

* **Id как единственный машиночитаемый идентификатор.** Модель
  возвращает `id` и `why`; название подставляется из каталога на
  сервере. Тогда выдуманное *название* невозможно в принципе, а
  выдуманный *id* ловится проверкой — это лучший анти-галлюцинационный
  приём по результатам исследования.
* **Явная лазейка «вернуть пусто».** Без неё модель, вынужденная
  выбирать, придумывает подходящий сериал (проверяется кейсами
  `g18–g20`).
* **Few-shot с примером отказа** — учит поведению «ничего не подошло».
* **Каталог и правила по краям промпта** (lost-in-the-middle): правила
  в system, каталог в конце пользовательского сообщения.

### 4. Неожиданная находка: reasoning-модели возвращают пустой ответ

Замер вскрыл проблему, которую не видно «на глаз»: профиль на
`glm-4.7-flash` дал **0 рекомендаций на всех 20 кейсах** — при этом
HTTP 200 и `eval_count` около 512. Причина: это reasoning-модель, она
пишет цепочку рассуждений в **отдельное поле `thinking`**, и если
бюджет `num_predict` израсходован на размышления, поле `content`
остаётся пустым.

Проверка на одном запросе:

```
# без флага: content пуст, 100 токенов ушло в thinking
$ curl -s localhost:11434/api/chat -d '{"model":"glm-4.7-flash:q4_K_M", ...,
  "options":{"num_predict":100}}'
content: ''   thinking: '1. **Analyze the user's request:** ...'   eval_count: 100

# с think=false: ответ есть, 4 токена вместо 100
content: 'Привет.'   eval_count: 4
```

Лечение — флаг `think=False` в нативном запросе (в OpenAI-совместимом
API такого ключа нет). После фикса профиль `series_glm` вернул
валидные рекомендации. Вывод для кейса: **оптимизация параметров
обязана включать отключение размышления для reasoning-моделей**, иначе
весь бюджет ответа уходит в невидимое поле.

### Что НЕ делаем и почему

* **Не включаем `response_format: json_object` по умолчанию.** Профиль
  `series` полагается на промпт (проверяем послушание), а профиль
  `series_json` — контрольная арм для гипотезы «грамматика повышает
  format-validity». Исследование предупреждает: жёсткие ограничения
  формата могут *снижать* качество рассуждения, поэтому решение
  принимается по замеру.
* **Не просим модель сортировать список.** Порядок — детерминированная
  операция; если понадобится, сортируем в коде, а не делегируем
  4-битной модели.
* **Не делаем второй LLM-вызов «rank → format».** Для 3–5 позиций
  выигрыш не оправдывает удвоения латентности; отмечаем как
  возможное развитие.

## Каталог: источник и нормализация

Источник — **Wikidata Query Service** (открытые данные, без ключей).
Во время аварии WDQS действует лимит «1 запрос/мин» (HTTP 429),
поэтому загрузчик делает один большой SPARQL-запрос и терпеливо
повторяет при 429; результат кэшируется.

Нормализация (`build_series_catalog.py`) решает реальные проблемы
данных:

* **дубли**: у сериала много строк (жанры × страны) → склейка по
  IMDb id;
* **грязные жанры**: Wikidata отдаёт «драматический сериал»,
  «драматический фильм» и «драма» как разные метки → сведение к 18
  каноническим жанрам по упорядоченным правилам;
* **не-сюжетное**: реалити, ток-шоу, новости, спорт, кулинарные шоу →
  отсев (рекомендательная задача про сюжетные сериалы);
* **битые названия**: если русская метка не нашлась, Wikidata отдаёт
  голый QID (`Q104907097`) → отсев;
* **стабильные id** — по номеру в отсортированном каталоге, чтобы
  `[n]` в промпте и `id` в ответе совпадали между прогонами.

Итог: 400 сериалов, 18 жанров, 52 страны (2010–2025).

## Метрики

| Метрика | Формула | Что ловит |
|---|---|---|
| `format_validity` | доля ответов, разобранных как JSON | неумение держать формат |
| `hallucination_rate` | доля id вне каталога | выдуманные сериалы |
| `constraint_satisfaction` | доля рекомендаций, удовлетворяющих всем ограничениям | игнор жанра/года/страны |
| `coverage` | доля кейсов с >= `min_picks` подходящих | слишком короткие ответы |
| `empty_honesty` | доля «пустых» кейсов с честным отказом | выдумка вместо «нет» |
| `latency_p50/p95`, `tokens_per_sec` | замер вызова | стоимость оптимизации |

Кандидаты в промпт отбираются **детерминированно и без LLM** (по
совпадению ограничений и слов запроса), поэтому у всех профилей
одинаковый вход — измеряется именно модель. Кандидатов намеренно
больше, чем подходящих: в списке есть «ловушки», иначе задача выбора
тривиальна и метрика ничего не измеряет.

## Границы

Оптимизация — только на инференсе (параметры, квант, промпт).
Fine-tuning вне scope. Профиль `studio` воспроизводит поведение до
дня 29: `POST /api/chat`, память, инварианты, RAG, task-пайплайн, MCP
не меняются.
