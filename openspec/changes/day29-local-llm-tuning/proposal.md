# Proposal: day29-local-llm-tuning

## Why

День 29: **оптимизация локальной LLM под конкретную задачу — поиск
новых сериалов**. Задание просит три вещи:

1. настроить параметры (`temperature`, `max tokens`, context window);
2. попробовать квантование (если доступно);
3. изменить prompt-шаблон под конкретный кейс.

К дню 29 в Студии есть локальная LLM (день 26: `LOCAL_MODELS`,
`_base_for()`, `list_models()`) и полностью локальный RAG (день 28:
эмбеддер `ollama`, `nomic-embed-text:v1.5`). Но **оптимизации как
таковой нет**, и это видно по коду:

- **context window не настраивается вообще.** В `CONTEXT_LIMITS`
  лежат паспортные окна моделей (`qwen3-coder:30b` → 262144), и это
  только верхняя граница для обрезки истории. В тело запроса
  `num_ctx` не уходит — Ollama берёт свой дефолт (2048/4096 в
  зависимости от модели). То есть фактическое окно **неизвестно и
  неконтролируемо**, а KV-кэш не планируется.
- **`temperature` и `max_tokens` — общие для всех задач.**
  `DEFAULT_CONFIG` (`0.7` / `2048`) — компромисс «на всё сразу». Для
  рекомендательной задачи 0.7 вредна (нужна воспроизводимость и
  следование каталогу), а 2048 токенов на список из 5 сериалов —
  перерасход.
- **prompt-шаблон один.** `DEFAULT_CONFIG["system_prompt"]` —
  «ассистент в обучающем приложении». Он не знает ни про каталог, ни
  про формат вывода, ни про запрет выдумывать сериалы.
- **квантование не измерено.** В Ollama лежат три модели, все
  `Q4_K_M`, но ни разу не сравнивались ни между собой, ни с более
  точным квантом (`Q8_0`) на одной задаче — нет ответа на вопрос
  «сколько качества стоит экономия памяти».

Задача дня 29 закрывает все три пункта и даёт **измеримый** результат:
оптимизированный под поиск сериалов профиль локальной модели с
цифрами (качество по золотому набору, латентность, токены/с,
память), обоснованный замером, а не на глаз.

Кейс «поиск новых сериалов» выбран потому, что он **проверяем
объективно**: есть реальный каталог (Wikidata), у запросов есть
жёсткие ограничения (жанр/год/страна/длина), а выдуманный сериал
легко поймать (его нет в каталоге). Это превращает «оптимизацию LLM»
из вкусовщины в измеримую инженерную задачу.

Ключевые решения:

- **Оптимизация — это профиль, а не константа.** Новый модуль
  `tuning.py` описывает `TaskProfile` (модель + sampling + `num_ctx` +
  промпт-шаблон + правила формата). Профиль «series» — один из
  профилей; дефолтный профиль `studio` повторяет текущее поведение
  бит-в-бит, поэтому регрессия дней 11–28 гарантирована.
- **`num_ctx` наконец уходит в запрос.** Локальным моделям
  добавляется `num_ctx` (Ollama-специфичный ключ в теле
  `/chat/completions`), для удалённых — ничего не меняется. Плюс
  бюджет-гард: `max_tokens` не может превышать окно, иначе хвост
  ответа обрезается молча.
- **Каталог подаётся в контекст, а не «в голову модели».** Поиск
  сериалов идёт по RAG-индексу из реального каталога; модель обязана
  выбирать **только из переданных id** и не выдумывать тайтлы. Это
  то же правило цитирования, что в дне 24 (`CITE_RULE`), но с
  проверкой по каталогу.
- **Качество меряется золотым набором.** `series_eval.py` считает
  constraint-satisfaction (жанр/год/страна), format-validity (валидный
  JSON) и hallucination-rate (id вне каталога). Оптимизация
  засчитывается только если цифры выросли — до/после в отчёте.
- **Квантование меряется тем же набором.** Одна и та же задача,
  `temperature=0`, фиксированный `seed`, одинаковые промпты — так
  сравнение `Q4_K_M` vs `Q8_0` честное.

## What Changes

### Новый модуль `studio/backend/tuning.py`
- `TaskProfile` (dataclass): `name`, `title`, `model`, `temperature`,
  `top_p`, `num_predict`, `num_ctx`, `seed`, `system_prompt`,
  `stop`, `format_json`, `description`, `notes`.
- `PROFILES`: `studio` (дефолт = текущее поведение), `series` (цель
  дня 29), `series_q8` (тот же профиль на `gemma3:27b-it-q8_0` для
  замера квантования).
- `profile_for(name)` — профиль по имени, `None`/неизвестный →
  `studio` (обратная совместимость).
- `SERIES_SYSTEM_PROMPT` — промпт-шаблон под кейс: роль, вход
  (каталог с id), жёсткие правила (только id из каталога, не
  выдумывать, учитывать год/жанр/страну), формат JSON, few-shot.
- `build_series_user_prompt(query, candidates)` — сборка
  пользовательского сообщения: запрос + пронумерованный каталог.
- `parse_series_answer(text)` — устойчивый разбор JSON (терпит
  ```json-обёртку, лишний текст, одиночный объект вместо массива).

### Настройка параметров (`agent.py`)
- `num_ctx` в `DEFAULT_CONFIG`-совместимом виде: новый ключ конфига
  `num_ctx` (валидация 512…1 048 576), уходит в тело запроса только
  для локальных моделей.
- `top_p` и `seed` — тоже настраиваемые (для воспроизводимости
  замеров), с валидацией.
- Применение профиля: `POST /api/tuning/profile` выбирает активный
  профиль; активный профиль переопределяет модель/sampling/промпт.

### Квантование
- `POST /api/tuning/quant` — сравнение квантов одной модели на
  золотом наборе: качество, латентность, токены/с, память
  (`ollama ps`).
- Отчёт сохраняется в `data/series/quant_report.json`.

### Каталог и индекс (`kb.py` / новые скрипты)
- `scripts/fetch_series.py` — загрузка реального каталога из Wikidata
  (уже есть, SPARQL, устойчив к 429).
- `scripts/build_series_catalog.py` — нормализация: дедупликация по
  IMDb id, склейка жанров, отсев не-сериалов (шоу/реалити/новости),
  компактный `catalog.json` + `catalog.txt` для индексации.
- `scripts/series_eval.py` — золотой набор запросов + метрики +
  прогон по профилям (`--profiles studio,series,series_q8`), отчёт.

### Роуты (`main.py`)
- `GET /api/tuning/profiles` — список профилей + активный.
- `POST /api/tuning/profile` — выбор активного профиля (400 на
  неизвестный).
- `GET /api/series/catalog` — статистика каталога.
- `POST /api/series/search` — поиск сериалов активным профилем
  (RAG-кандидаты → LLM → разобранный JSON + метрики запроса).
- `GET /api/tuning/report` — последний отчёт оптимизации (профили +
  кванты).

### Фронтенд
- Вкладка «Сериалы»: поле запроса, выбор профиля, карточки
  рекомендаций (тайтл/год/жанры/страна/IMDb), панель метрик
  (латентность, токены, `num_ctx`, попадание в каталог), панель
  сравнения профилей.

### Документация
- `openapi`/README/RELEASE — как обычно; отчёт с цифрами до/после.

## Вне scope (guardrails)

- Провайдер/маршрутизация дней 26–28 (`LOCAL_MODELS`, `_base_for`,
  `list_models`, `ollama`-эмбеддер) не меняются — только
  аддитивно используются.
- Дефолтный профиль `studio` воспроизводит текущее поведение:
  схема `POST /api/chat`, `build_payload`, память, инварианты,
  task-пайплайн, MCP, реранкер/`min_score`, `CITE_RULE` — без
  изменений.
- RAG-поиск (`search` / `search_rag` / `_rrf` / `_bm25_scores`) не
  трогаем: каталог индексируется существующим пайплайном.
- Новых pip/npm-зависимостей нет (stdlib + уже имеющиеся fastapi/httpx).
- Формат `index.db` (version 1) не меняется.
- Модели не переобучаются (fine-tuning вне scope) — оптимизация на
  уровне инференса: параметры, квант, промпт.
