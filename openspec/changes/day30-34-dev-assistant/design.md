# Design: day30-34-dev-assistant

## Контекст

Дни 30–34 — **связать** уже существующие слои Студии в единого
ассистента. Ничего не ломается: ассистент — новый модуль и новый
префикс путей, старые роуты (чат, RAG, MCP, шлюз) не редактируются.

Опирается на:

* дни 21–24, 28 — `kb.py`: chunking, эмбеддеры (hash офлайн / Ollama
  локальный), гибридный поиск (вектор + BM25, RRF), реранкер,
  цитаты, индекс в SQLite;
* дни 16–20 — `mcp.py`: реестр серверов, tool-loop, git-инструменты;
* дни 12–15, 25 — `agent.py`: профили, инварианты, память задачи;
* день 30 — `gateway.py`: `estimate_tokens`, паттерн TDD + e2e.

## Схема

```
   цель пользователя (не пошаговая инструкция)
        │
        ▼
  ┌──────────────────────────────────────────────────────────┐
  │  AssistantService  (studio/backend/assistant.py)         │
  │                                                          │
  │  А. ask_project   → RAG по docs+коду → ответ + цитаты    │
  │  Б. review_diff   → diff → сопоставление → отчёт         │
  │  В. support       → тикет + CRM → персонализированный    │
  │                     ответ                                │
  │  Г. scenario      → 5 автономных файловых сценариев      │
  └──────────────────────────────────────────────────────────┘
        │                    │                    │
        ▼                    ▼                    ▼
  ProjectCorpus        GitReader            TicketStore
  (docs + код)        (ветка/diff)        (CRM: users+tickets)
        │
        ▼
  kb.SQLiteIndex  data/kb/project.db   ← ОТДЕЛЬНО от data/kb/index.db
  (переиспользует kb.py: chunking, эмбеддер, гибридный поиск, RRF)
```

## Решение 1: отдельный индекс проекта, а не общий корпус

Соблазн — дописать документацию и код в существующий `data/kb/index.db`.
Это **неверно**: корпус дня 21 сознательно ограничен загрузками
пользователя, и если подмешать туда весь репозиторий, то:

* поиск по пользовательским документам начнёт выдавать чанки кода
  проекта (мусор в ответах чата);
* пересборка индекса проекта будет стирать пользовательские загрузки;
* статистика дня 21 («сколько документов») станет бессмысленной.

Поэтому — **второй индекс** `data/kb/project.db`, та же схема и тот
же код (`kb.py` не форкается, переиспользуется через параметр пути).
Пользовательские загрузки и проект живут раздельно.

## Решение 2: явный список файлов корпуса

Индексировать репозиторий целиком нельзя: `.venv` (десятки тысяч
файлов), `node_modules`, `data/kb/index.db` (бинарный), `.git`,
`__pycache__`. Поэтому корпус собирается **правилами** с явными
include-паттернами и жёстким списком исключений (`EXCLUDE_DIRS`,
`EXCLUDE_SUFFIXES`), а также ограничением на размер файла
(`MAX_FILE_BYTES`). Это детерминированно и проверяемо в тестах:
`.venv/x.py` в корпус не попадает, `studio/backend/kb.py` — попадает.

## Решение 3: ревью — гибрид «детерминированное ядро + LLM-нарратив»

Ревью кода нельзя целиком отдать LLM: модель галлюцинирует номера
строк и «находит» то, чего в diff нет. Поэтому **факты собирает код, а
LLM — только формулирует**:

| Слой | Кто делает | Что даёт |
|---|---|---|
| Разбор diff | код (`parse_unified_diff`) | файлы, ханки, +/- строки, номера строк |
| Детерминированные проверки | код (правила) | длинные строки, `bare except`, `print(`, секреты, `TODO`, отсутствие тестов к изменённому модулю, изменения без документации |
| Сопоставление с документацией | `ProjectCorpus` (RAG) | какие доки/спеки затрагивает изменение |
| Нарратив и рекомендации | LLM (опционально) | связный текст отчёта |

Каждая находка имеет **доказательство** (файл + номер строки) и
severity (`high` / `medium` / `low`). Если LLM недоступна — отчёт всё
равно формируется из детерминированной части (деградация, не отказ).
Это ключевое свойство: ревью работает **офлайн**.

## Решение 4: поддержка — данные пользователя меняют ответ

Задание требует «учитывать контекст конкретного пользователя или
тикета из CRM». Реализация: `TicketStore` отдаёт тикет и связанного
пользователя (план, историю обращений, статус оплаты, роль), и эти
факты **инжектятся в промпт** и **возвращаются в ответе** отдельным
блоком `context`. То есть персонализация наблюдаема: видно, какие
именно поля CRM повлияли на ответ.

Если тикет не найден — не выдумываем, а отвечаем общим ответом по
базе знаний и помечаем `context.found = false`.

## Решение 5: сценарии — цель, а не инструкция

Сценарий принимает **цель** и сам решает, что читать и куда писать:

| Сценарий | Вход | Автономные действия |
|---|---|---|
| `find_usages` | символ/API | обход корпуса кода+доков, поиск вхождений, группировка по файлу с номерами строк |
| `update_docs` | (git diff) | чтение diff → определение затронутых модулей → правка секции README (идемпотентный маркер) |
| `generate` | kind (readme/adr/changelog) | генерация файла: ADR нумеруется по существующим, changelog — из git-лога |
| `check_invariants` | (правила проекта) | проверка файлов на инварианты (запрещённые импорты, секреты, `print`, отсутствие docstring) |
| `diff_report` | список файлов | подготовка unified-diff отчёта, сохранение в файл или вывод |

**Безопасность записи.** Сценарии пишут **только** внутрь проекта и
**только** по явному allow-list путей (`docs/`, `README.md`,
`openspec/`, `CHANGELOG.md`). Попытка записи вне проекта (абсолютный
путь, `..`, симлинк наружу) → отказ `ScenarioError`, а не тихая
запись. Каждый сценарий возвращает `changed_files` и `diff`, чтобы
результат был проверяем, а не «поверьте, я обновил».

## Ограничения и компромиссы

* **Токены** — та же эвристика `estimate_tokens` (`gateway.py`), что
  и в днях 8–30: согласованность чисел важнее абсолютной точности.
* **Эмбеддер** — по умолчанию hash-эмбеддер (офлайн, детерминированно,
  тесты без сети); при выборе Ollama-эмбеддера индекс проекта
  собирается локальной моделью (день 28).
* **LLM опциональна.** Все четыре модуля дают результат без модели:
  А — поиск с цитатами, Б — детерминированные находки, В — ответ по
  базе знаний, Г — файловые операции. LLM повышает качество текста,
  но не является условием работоспособности. Это проверяется Part A
  e2e (офлайн, без сети).
* **Никаких git-мутаций.** Ассистент читает git (`git status`,
  `git diff`, `git log`) и пишет файлы в рабочее дерево. Коммит — за
  человеком.

## Регрессия

Новый модуль + новый префикс `/api/assistant/*` + новый файл
`data/kb/project.db`. Единственная точка касания `main.py` —
регистрация роутов. Существующие пути не редактируются, поэтому
регрессия дней 11–30 гарантируется структурно; полный прогон
бэкенд-тестов это подтверждает.
