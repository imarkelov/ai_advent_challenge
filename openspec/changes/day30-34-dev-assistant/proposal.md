# Proposal: day30-34-dev-assistant

## Why

Дни 30–34: собрать всё, что уже построено в Студии, в **единый
AI-ассистент разработчика и поддержки** — один инструмент, который
отвечает на вопросы по проекту, ревьюит изменения, разбирает тикеты с
учётом данных пользователя и **сам правит файлы проекта** по
высокоуровневой цели.

К этому моменту в репозитории уже есть все кирпичи, но они **не
связаны между собой**:

* **RAG** (дни 21–24, 28) — гибридный поиск по базе знаний с
  реранкером и цитатами, но корпус ограничен `data/kb/uploads`
  (загрузки пользователя). Документации и кода проекта в индексе
  **нет** (это зафиксировано как исправление после релиза дня 21), а
  именно они нужны для вопросов «как устроен проект».
* **MCP** (дни 16–20) — 10 серверов, tool-loop, но всё это работает
  **только из чата**; как получить git-ветку, diff или обработать
  тикет — нет.
* **Агент** (дни 12–15, 25) — профили, инварианты, память задачи,
  plan-review — но агент **только отвечает**. Он не меняет файлы:
  ни README, ни ADR, ни changelog он не напишет.
* **Шлюз** (день 30) — сетевой доступ, но это про инференс, а не про
  работу с проектом.

Разрыв ровно в одном: **нет слоя, который читает проект (документацию
и код), сопоставляет изменения с контекстом и пишет результат обратно
в файлы**. Дни 30–34 закрывают его модулем `studio/backend/assistant.py`
и вкладкой «Ассистент».

### Ключевое решение: цель вместо пошаговой инструкции

Задание требует работать «на уровне целей, а не пошаговых инструкций».
Это и есть главное отличие ассистента от обычного чата: пользователь
говорит **что нужно** («проверь соответствие кода правилам проекта»),
а не **как** («прочитай файл X, найди строку Y»). Поэтому ядро
ассистента — не «функция на каждую кнопку», а **сценарии**: они сами
решают, какие файлы прочитать, что искать по нескольким файлам и какой
результат записать.

Сценарии (минимум 2 по заданию, реализовано 5):

| Сценарий | Что делает автономно |
|---|---|
| `find_usages` | ищет места использования символа/API по коду и документации |
| `update_docs` | обновляет документацию по фактическим изменениям кода |
| `generate` | генерирует новый файл (README / ADR / changelog) |
| `check_invariants` | проверяет файлы на соответствие правилам проекта |
| `diff_report` | готовит diff / список изменений с сохранением или выводом |

### Что НЕ делаем (осознанно)

* **Не даём ассистенту `git push` / `commit`** — он готовит изменения
  на диске и отчёт; решение о коммите остаётся за человеком. Автономная
  запись в git-историю — необратимое действие, и без human-gate это
  небезопасно (та же логика, что у day15 plan-review).
* **Не индексируем весь репозиторий целиком** — корпус собирается
  **явным списком** (README, `docs/`, `studio/backend/*.py`,
  `openspec/`), чтобы в индекс не попадали `.venv`, `node_modules`,
  `data/kb/index.db` и прочий мусор.
* **Не трогаем `data/kb`** (загрузки пользователя) — корпус проекта
  живёт **отдельным индексом** (`data/kb/project.db`), чтобы
  пользовательские загрузки и документация проекта не смешивались и
  не ломали друг друга.
* **Не переписываем существующие роуты** — ассистент это новый
  префикс `/api/assistant/*` и новый модуль.

## What Changes

### Новый слой: корпус проекта (RAG по документации и коду)

* `ProjectCorpus` — сбор документов проекта по явным правилам:
  README.md, RELEASE.md, LINKS.md, `docs/**`, `openspec/**`,
  `studio/backend/**/*.py`, `studio/frontend/src/**`,
  `scripts/*.py` (расширяемо через аргумент).
* Индексация в **отдельный** SQLite-индекс (`data/kb/project.db`),
  переиспользуя `kb.py` (chunking, эмбеддеры, гибридный поиск) — новых
  пакетов не требуется.
* Каждый документ помечен источником (`docs` / `code` / `spec`), чтобы
  ответ мог сослаться на происхождение.

### Новый модуль `studio/backend/assistant.py`

* `TicketStore` — чтение CRM-данных (`data/crm/users.json`,
  `data/crm/tickets.json`): пользователи, тикеты, поиск по id/email,
  контекст пользователя для персонализации.
* `AssistantService` — единая точка входа, четыре режима:
  * `ask_project(question)` — RAG-ответ по документации и коду с
    цитатами и источниками (модуль А);
  * `review_diff(...)` — ревью PR: diff → сопоставление с
    документацией → структурированный отчёт (баги, архитектура,
    рекомендации) (модуль Б);
  * `support_answer(ticket_id, question)` — ответ поддержки с
    персонализацией по данным тикета и пользователя (модуль В);
  * `run_scenario(name, ...)` — автономные файловые сценарии
    (модуль Г), 5 штук.
* Разбор diff (unified), поиск использований символа, проверка
  инвариантов по правилам проекта — **офлайн, детерминированно, без
  сети** (LLM только там, где нужен текст: сводка, ответ, ADR).

### Роуты в `studio/backend/main.py`

* `GET /api/assistant/status` — состояние (индекс проекта, число
  документов, доступность LLM, CRM);
* `POST /api/assistant/index` — собрать/пересобрать индекс проекта;
* `POST /api/assistant/ask` — вопрос по проекту (RAG);
* `POST /api/assistant/review` — ревью diff (текст или git-ветка);
* `GET /api/assistant/tickets` — список тикетов из CRM;
* `POST /api/assistant/support` — ответ поддержки по тикету;
* `GET /api/assistant/scenarios` — список сценариев;
* `POST /api/assistant/scenario` — запустить сценарий (возвращает
  изменённые файлы и diff);
* `GET /api/assistant/git` — текущая ветка, изменённые файлы, diff.

### UI: вкладка «Ассистент»

* 4 секции по модулям: вопрос по проекту (с источниками), ревью diff
  (отчёт по severity), тикеты (персонализированный ответ), сценарии
  (запуск, список изменённых файлов, diff).

### Данные

* `data/crm/users.json`, `data/crm/tickets.json` — источник тикетов и
  пользователей (для сценариев поддержки), генератор
  `scripts/make_crm_data.py`.

### Скрипты и тесты

* `studio/backend/tests/test_assistant.py` — офлайн-тесты (TDD);
* `studio/backend/tests/test_assistant_api.py` — тесты роутов;
* `scripts/e2e_day31.py` — Part A офлайн (TestClient) + Part B live
  (реальный сервер + реальная Ollama + реальный git diff).
