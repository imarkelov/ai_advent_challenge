# Spec: dev-assistant

## Назначение

Единый AI-ассистент разработчика и поддержки: RAG-ответы по
документации и коду проекта, автоматическое ревью изменений,
обработка тикетов с учётом CRM-данных и автономная работа с файлами
проекта по высокоуровневым целям.

## Термины

* **Корпус проекта** (`ProjectCorpus`) — документы README, `docs/`,
  `openspec/`, код бэкенда и фронтенда, скрипты; отдельно от загрузок
  пользователя.
* **Индекс проекта** — SQLite-индекс `data/kb/project.db` (отдельный
  от `data/kb/index.db` дня 21).
* **Тикет** — обращение пользователя в CRM (`data/crm/tickets.json`).
* **Сценарий** (`scenario`) — автономная операция над файлами проекта,
  задаваемая целью, а не пошаговой инструкцией.
* **Находка** (`finding`) — результат детерминированной проверки при
  ревью: severity + сообщение + доказательство (файл, строка).

## Функциональные требования

### FR-1 Корпус и индекс проекта

* FR-1.1 Система SHALL собирать документы проекта по явным правилам:
  `README.md`, `RELEASE.md`, `LINKS.md`, `docs/**`, `openspec/**`,
  `studio/backend/**/*.py`, `studio/frontend/src/**`, `scripts/*.py`.
* FR-1.2 Система MUST исключать из корпуса `.venv`, `.venv-mlx`,
  `node_modules`, `.git`, `__pycache__`, `.pytest_cache`, `.idea`,
  `data/` и файлы размером более `MAX_FILE_BYTES`.
* FR-1.3 Индекс проекта MUST храниться отдельно от индекса дня 21 в
  `data/kb/project.db`; сборка индекса проекта MUST NOT изменять
  `data/kb/index.db`.
* FR-1.4 Каждый документ корпуса SHALL иметь источник (`docs` / `code`
  / `spec`) и относительный путь.
* FR-1.5 Пересборка индекса MUST быть идемпотентной (повторная сборка
  даёт то же число документов и чанков).

### FR-2 Вопросы по проекту (RAG)

* FR-2.1 `ask_project(question)` SHALL возвращать ответ и список
  источников с путём файла, секцией и фрагментом текста.
* FR-2.2 Если индекс не построен, система MUST вернуть ошибку с
  RU-текстом, а не пустой ответ.
* FR-2.3 Если релевантных чанков не найдено, система MUST NOT
  вызывать LLM, а SHALL ответить «не знаю» с явным признаком
  (`found: false`).
* FR-2.4 При доступной LLM ответ SHALL формироваться моделью на основе
  найденного контекста; при недоступной — SHALL возвращаться
  extractive-ответ из найденных фрагментов (деградация, не отказ).
* FR-2.5 В ответе SHALL быть указано, был ли использован LLM
  (`llm: true/false`).

### FR-3 Ревью изменений (PR Review)

* FR-3.1 Система SHALL принимать unified diff (текстом) либо имя
  git-ветки/`HEAD` для получения diff через git.
* FR-3.2 Система SHALL разбирать diff детерминированно: список
  файлов, добавленные/удалённые строки, номера строк в новой версии.
* FR-3.3 Система SHALL выполнять детерминированные проверки и
  возвращать находки со severity (`high`/`medium`/`low`), сообщением,
  файлом и номером строки:
  * `bare_except` — `except:` без типа;
  * `print_call` — `print(` в коде бэкенда;
  * `long_line` — строка длиннее `MAX_LINE_LEN`;
  * `secret` — похоже на ключ/токен/пароль в добавленной строке;
  * `todo` — `TODO`/`FIXME` без указания автора;
  * `missing_test` — изменён модуль `studio/backend/<m>.py` без
    изменения `tests/test_<m>.py`;
  * `missing_docs` — изменение кода без изменения документации.
* FR-3.4 Система SHALL сопоставлять изменённые файлы с документацией
  проекта через индекс (RAG) и указывать затронутые документы.
* FR-3.5 Отчёт SHALL содержать сводку: число файлов, добавленных и
  удалённых строк, находок по severity.
* FR-3.6 Отчёт SHALL формироваться **без LLM**; LLM (при наличии)
  добавляет только текстовые рекомендации, помеченные как таковые.
* FR-3.7 Некорректный/пустой diff MUST приводить к явной ошибке
  (400), а не к пустому отчёту.

### FR-4 Поддержка пользователей (CRM)

* FR-4.1 `TicketStore` SHALL читать `data/crm/tickets.json` и
  `data/crm/users.json`.
* FR-4.2 Система SHALL находить тикет по id и связывать его с
  пользователем; отсутствие данных MUST NOT приводить к исключению
  (ответ с `found: false`).
* FR-4.3 Ответ поддержки SHALL персонализироваться по данным тикета и
  пользователя (план, статус оплаты, роль, история обращений).
* FR-4.4 В ответе SHALL быть блок `context` с использованными полями
  CRM — персонализация наблюдаема, а не декларативна.
* FR-4.5 Система SHALL отдавать список тикетов с фильтрами по статусу
  и приоритету.
* FR-4.6 Для вопросов, покрытых базой знаний, ответ SHALL опираться
  на найденные фрагменты и содержать источники.

### FR-5 Автономные файловые сценарии

* FR-5.1 Система SHALL предоставлять минимум 5 сценариев:
  `find_usages`, `update_docs`, `generate`, `check_invariants`,
  `diff_report`.
* FR-5.2 Сценарий SHALL принимать цель/параметры, а не пошаговый
  список действий.
* FR-5.3 Любая запись MUST быть ограничена allow-list путей проекта
  (`README.md`, `docs/`, `openspec/`, `CHANGELOG.md`).
* FR-5.4 Попытка записи вне разрешённых путей (абсолютный путь, `..`,
  выход за пределы проекта) MUST приводить к `ScenarioError`.
* FR-5.5 Каждый сценарий SHALL возвращать отчёт: `changed_files`,
  `diff`, краткое описание выполненного.
* FR-5.6 Сценарий `find_usages` SHALL искать вхождения символа по
  коду и документации и группировать результат по файлам с номерами
  строк.
* FR-5.7 Сценарий `generate` для ADR SHALL нумеровать файл по уже
  существующим ADR (`docs/adr/NNNN-*.md`).
* FR-5.8 Сценарий `diff_report` SHALL уметь как сохранять отчёт в
  файл, так и возвращать его содержимое без записи.
* FR-5.9 Сценарии MUST NOT выполнять git-мутации (commit, push,
  checkout); допускается только чтение git.

### FR-6 Git-контекст

* FR-6.1 Система SHALL отдавать текущую ветку, список изменённых
  файлов и diff рабочего дерева.
* FR-6.2 Чтение git MUST NOT падать при отсутствии репозитория или
  git — SHALL возвращаться признак недоступности.

### FR-7 REST API

* FR-7.1 `GET /api/assistant/status` — состояние (индекс, документы,
  LLM, CRM, git).
* FR-7.2 `POST /api/assistant/index` — сборка индекса проекта.
* FR-7.3 `POST /api/assistant/ask` — вопрос по проекту.
* FR-7.4 `POST /api/assistant/review` — ревью diff.
* FR-7.5 `GET /api/assistant/tickets` — список тикетов.
* FR-7.6 `POST /api/assistant/support` — ответ по тикету.
* FR-7.7 `GET /api/assistant/scenarios` — список сценариев.
* FR-7.8 `POST /api/assistant/scenario` — запуск сценария.
* FR-7.9 `GET /api/assistant/git` — git-контекст.
* FR-7.10 Ошибки SHALL возвращаться с осмысленным HTTP-кодом
  (400 — некорректный вход, 404 — не найдено, 409 — индекс не
  построен) и RU-текстом.

### FR-8 UI

* FR-8.1 Вкладка «Ассистент» SHALL содержать секции: вопрос по
  проекту, ревью diff, тикеты, сценарии.
* FR-8.2 Секция вопроса SHALL показывать ответ и источники.
* FR-8.3 Секция ревью SHALL показывать отчёт с группировкой по
  severity и путями/строками.
* FR-8.4 Секция тикетов SHALL позволять выбрать тикет и получить
  персонализированный ответ с блоком контекста.
* FR-8.5 Секция сценариев SHALL позволять выбрать сценарий, задать
  параметры и увидеть изменённые файлы и diff.

## Нефункциональные требования

* NFR-1 Только stdlib + уже используемые зависимости (FastAPI,
  httpx); новых пакетов не требуется.
* NFR-2 Существующие роуты и поведение дней 11–30 не изменяются.
* NFR-3 Модуль импортируется без побочных эффектов: сеть и диск при
  импорте не трогаются.
* NFR-4 Ядро (разбор diff, проверки, поиск использований, проверка
  путей, CRM) работает **офлайн и детерминированно** — тесты без сети.
* NFR-5 Запись в файлы атомарна (временный файл + `os.replace`).
* NFR-6 Все сообщения об ошибках — на русском языке.
