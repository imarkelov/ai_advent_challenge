# Design: day30-local-llm-service

## Контекст

День 30 — превратить локальную LLM из «внутренностей Студии» в
**приватный сетевой сервис**. Опирается на дни 26 (Ollama как
провайдер), 28 (локальный RAG) и 29 (профили, `num_ctx` через нативный
API). Ничего из этого не ломается: шлюз — **новый слой**, старые пути
вызова остаются как есть.

## Схема

```
  ноутбук / телефон / планшет   (любое устройство в LAN)
        │  OpenAI-совместимый HTTP + Bearer <ключ клиента>
        ▼
  ┌──────────────────────────────────────────────┐
  │  Шлюз  (FastAPI Студии, слушает 0.0.0.0)     │
  │                                              │
  │  1. аутентификация  → ключ → клиент          │
  │  2. allow_models    → модель разрешена?      │
  │  3. rate limit      → RPM / TPM (окно)       │
  │  4. подсчёт входа   → токены промпта         │
  │  5. max_context     → влезает?               │
  │       ├─ да → как есть                       │
  │       └─ нет → LLM-сводка старых ходов       │
  │  6. прокси          → Ollama                 │
  │  7. учёт            → токены, запросы, отказ │
  └──────────────────────────────────────────────┘
        │  http://127.0.0.1:11434
        ▼
     Ollama (локальные модели, наружу не смотрит)
```

Ключевая идея: **Ollama остаётся закрытой на loopback**. Наружу
(в LAN) смотрит только шлюз — единственная точка, где есть
аутентификация, лимиты и учёт. Если открыть Ollama в LAN напрямую,
лимитов не будет ни у кого.

## Почему не жёсткий отказ при превышении контекста

Задание требует «ограничение по max context». Буквальная реализация —
400/413 при превышении. Но это ломает главный сценарий сервиса:
**длинный диалог с другого устройства**. Клиент (телефон) не умеет
сам сжимать историю; если сервис просто отказывает, пользователь
получает стену вместо ответа и должен вручную чистить историю.

Поэтому компрессия — часть контракта, а не обход лимита:

| Ситуация | Поведение |
|---|---|
| вход ≤ `max_context` | запрос уходит **бит-в-бит**, компрессии нет, накладных нет |
| вход > `max_context` | старые ходы → **LLM-сводка**; system + последние `keep_recent` ходов целиком |
| после компрессии всё ещё > лимита | 413 с точными числами (просили N, лимит M) |

Согласованный скоуп: **компрессия всегда через LLM-сводку** (не
жёсткая обрезка по токенам). Это дороже — плюс один вызов модели на
сжатие — но сохраняет смысл диалога, а не теряет его.

**Компрессия рекурсивна и идемпотентна.** Если после первой сводки всё
ещё не влезает, сжимается следующий блок старых ходов; уже
существующая сводка всегда остаётся в голове контекста и не
пересжимается повторно. Кап итераций — `MAX_COMPRESS_ROUNDS`.

**Сводка не теряет факты молча.** Правило промпта сводки: сохранять
цель, ограничения, принятые решения, имена и числа; отбрасывать
любезности. Сводка инжектится как отдельное `system`-сообщение с
пометкой, что это сжатая история — модель не путает её с текущим
запросом.

**Стоимость компрессии видна.** В ответе есть блок `gateway`:
`compressed: true`, `messages_before`/`after`, `tokens_before`/`after`,
`compress_rounds`. Клиент и UI видят, что произошло.

## Ограничения: что именно лимитируется

| Лимит | Где | Что делает |
|---|---|---|
| `rpm` | на клиента | запросов в минуту, **скользящее окно** 60 с |
| `tpm` | на клиента | токенов (вход+выход) в минуту, скользящее окно |
| `max_context` | на клиента | триггер компрессии, затем 413 |
| `max_output_tokens` | на клиента | жёсткий потолок ответа (перебивает запрос клиента) |
| `allow_models` | на клиента | пусто = все; иначе белый список |
| `enabled` | на клиента | выключение без удаления ключа |

Скользящее окно выбрано вместо «фиксированной минуты»: фиксированное
окно даёт двойной залп на стыке минут (типовой баг лимитеров).
Реализация — `deque` таймстемпов/весов на клиента, под `threading.Lock`
(FastAPI выполняет sync-хендлеры в пуле потоков).

**Что считается токеном.** Точной токенизации для произвольной модели
без загрузки её токенизатора нет, поэтому используется та же
эвристика, что в днях 8–29 (`estimate_tokens`): она уже принята в
проекте и даёт консистентные числа между учётом, лимитом и UI. Это
осознанный компромисс — задокументирован, а не скрыт.

## UX: ключи клиентов

* Ключ генерируется шлюзом (`sk-local-<32 hex>`), показывается
  **один раз** при создании, в конфиге хранится **SHA-256 хэш** —
  утечка `gateway.json` не даёт доступа.
* В UI и в `/api/gateway/clients` ключ всегда маскирован
  (`sk-local-…abcd`).
* Сравнение хэша — `hmac.compare_digest` (не `==`), чтобы не течь по
  времени.
* Дефолтный клиент создаётся из `.env` (`GATEWAY_CLIENT_KEY`), чтобы
  сервис был доступен сразу после запуска.

## Почему это безопасно в LAN (и где граница)

* Ollama слушает loopback и наружу не смотрит — единственный вход в
  LAN это шлюз;
* без ключа — 401; неизвестная модель — 404; неразрешённая — 403;
* лимиты не дают одному устройству занять GPU целиком;
* **граница:** трафик идёт по HTTP, ключ передаётся открытым текстом.
  Это допустимо **только внутри доверенной локальной сети**. Сервис
  намеренно не выставляется в интернет (нет TLS, нет защиты от
  публичного сканирования) — это записано и в UI, и в README.

## Регрессия

Шлюз — новый префикс путей (`/v1/*`, `/api/gateway/*`) и новый модуль.
Существующие роуты, агент, RAG и профили не изменяются. Единственная
точка касания `main.py` — регистрация роутов. Регрессия дней 11–29
гарантируется тем, что ни один существующий путь не редактируется.

## Находки живой проверки (что дала реальная Ollama)

Всё ниже найдено прогоном `scripts/e2e_day30.py` и
`scripts/demo_day30_service.py` на живой Ollama 0.34.4 (M3 Max, 48 ГБ),
а не выведено умозрительно.

### 1. Reasoning-модели ломают компрессию

`glm-4.7-flash:q4_K_M` (MoE + reasoning) на служебном вызове сводки:

* через OpenAI-совместимый `/v1/chat/completions` отдаёт
  `content: ""`, а весь текст уходит в поле `reasoning` — бюджет
  `max_tokens` потрачен на размышления;
* на большом контексте падает **HTTP 500** на нативном `/api/chat`
  при `num_predict: 2048`.

`qwen3-coder:30b` на том же входе отдаёт готовую сводку (743 символа)
сразу. Поэтому сводка идёт **цепочкой моделей** (`_summary_models`):
сначала модель, выбранная для диалога (уже прогрета в VRAM), затем
модели из `DEFAULT_SUMMARY_PREFERENCE` (`qwen3-coder:30b`, `gemma3:27b`),
затем остальные локальные (эмбеддеры исключены). Для каждой модели
пробуются **оба пути** вызова. Итог — первый непустой ответ; если всё
пусто, компрессия деградирует и шлюз честно отдаёт 413.

### 2. Пустой ответ модели — это наблюдаемое событие, а не «норма»

Та же модель на **обычном** запросе с малым `max_output_tokens`
возвращает пустой `content` и `finish_reason: length`: бюджет кончился
на рассуждениях. Клиент получал `choices[0].message.content == ""` без
объяснения. Теперь шлюз помечает такой ответ:

```json
"gateway": {
  "empty_response": true,
  "empty_reason": "Модель израсходовала бюджет ответа на рассуждения
                   (finish_reason=length). Увеличьте max_output_tokens
                   клиента «…» (сейчас 16) или выберите модель без
                   режима рассуждений.",
  "finish_reason": "length",
  "reasoning_chars": 783
}
```

### 3. Компрессия: хвост тоже нужно уметь сокращать

Первая версия цикла после раунда сводки останавливалась, если осталось
`keep_recent` сообщений, — **даже когда сам хвост был больше лимита**.
Живой прогон поймал это как пограничный случай: сводка дала 510 токенов
при лимите 500 → 413, хотя сократить хвост было можно.

Исправлено: после каждого раунда хвост сокращается, пока не влезет, но
**последнее сообщение пользователя не выбрасывается никогда**
(`last_user_index`). Если и это не помогает (одно огромное сообщение) —
честный 413, как и было задумано.

### 4. `lan_url` должен указывать на реальный порт

`GET /api/gateway/status` брал порт из константы `DEFAULT_GATEWAY_PORT`,
поэтому при запуске на нестандартном порту отдавал клиенту **неверный
адрес**. Теперь порт берётся из фактического запроса
(`request.url.port`), а `GATEWAY_HOST`/`GATEWAY_PORT` остались ручным
override.

### 5. Ловушка SPA-фолбэка (и почему e2e её избегает)

Фронтенд раздаётся catch-all-роутом `@app.get("/{full_path:path}")`.
Он принимает **только GET**, поэтому API-роуты (`POST`) имеют
приоритет — но любой запрос, ушедший как GET с телом, молча получает
HTML вместо JSON. Это ловушка для скриптов: `urllib` с явным
`method="GET"` и телом уходит именно так. В e2e и демо метод выводится из
наличия тела (`POST`, если тело есть). Сам `POST /v1/*` фолбэк не
перехватывает — проверено: анонимный `POST /v1/chat/completions`
возвращает 401, а не HTML.

### 6. Отдельная пре-существующая проблема запуска из корня

`uvicorn studio.backend.main:app` **из корня репозитория не работает**:
у пакета `studio/` нет `__init__.py`, `main.py` уходит в fallback-импорт
`from agent import ...` и подхватывает устаревший корневой `agent.py`
дня 7 (там нет `DEFAULT_CONTEXT_LIMIT`) → `ImportError`. Проблема не
связана с днём 30 и воспроизводится на HEAD. В e2e сервер поднимается
штатным флагом `--app-dir studio/backend` с приложением `main:app` —
это не меняет структуру репозитория и работает.
