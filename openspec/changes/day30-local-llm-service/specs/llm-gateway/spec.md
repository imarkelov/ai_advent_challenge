# Spec: llm-gateway

## Назначение

Локальная LLM как приватный сетевой сервис: OpenAI-совместимый шлюз
для доступа с любого устройства в локальной сети, с API-ключами
клиентов, ограничениями rate limit / max context и учётом
использования.

## Термины

* **Клиент** (`GatewayClient`) — устройство/пользователь, которому
  выдан ключ и набор лимитов.
* **Ключ** — `sk-local-<hex>`; в конфиге хранится только SHA-256 хэш.
* **Rate limit** — ограничение частоты (RPM/TPM) по скользящему окну.
* **Компрессия** — сжатие старых ходов диалога LLM-сводкой при упоре
  в `max_context`.
* **Использование** (`UsageStore`) — счётчики запросов, токенов и
  отказов по клиентам.

## Функциональные требования

### FR-1 Сетевой доступ

* FR-1.1 Шлюз принимает запросы на `POST /v1/chat/completions` в
  формате OpenAI (совместим с любым OpenAI-клиентом).
* FR-1.2 Эндпоинт `GET /v1/models` возвращает список доступных
  моделей в формате OpenAI (`{"object": "list", "data": [...]}`).
* FR-1.3 Сервис слушает `0.0.0.0`, чтобы быть доступным с других
  устройств в локальной сети; фактический LAN-адрес отдаётся
  `GET /api/gateway/status` (`lan_url`).
* FR-1.4 TLS не используется: сервис предназначен только для
  доверенной локальной сети. Это требование зафиксировано в
  документации и в UI.

### FR-2 Аутентификация

* FR-2.1 Запрос без заголовка `Authorization` → 401
  (`error.type = "invalid_request_error"`).
* FR-2.2 Неизвестный ключ → 401; выключенный клиент → 403.
* FR-2.3 Ключ сравнивается по SHA-256 хэшу через
  `hmac.compare_digest` (устойчивость к тайминг-атакам).
* FR-2.4 В ответах API и в UI ключ всегда маскирован; полный ключ
  возвращается **только** в ответе на создание клиента.
* FR-2.5 Модель вне `allow_models` клиента → 403; неизвестная модель
  → 404.

### FR-3 Rate limit

* FR-3.1 Ограничение запросов в минуту (`rpm`) на клиента;
  превышение → 429 с `Retry-After`.
* FR-3.2 Ограничение токенов в минуту (`tpm`) на клиента (вход +
  выход); превышение → 429.
* FR-3.3 Окно — **скользящее** (60 с), а не фиксированная минута:
  запросы на стыке минут не дают двойного залпа.
* FR-3.4 Значение `0` или `None` означает «без лимита» (для
  тестирования и доверенных клиентов).
* FR-3.5 Ограничитель потокобезопасен (FastAPI выполняет sync-
  хендлеры в пуле потоков).
* FR-3.6 Отказ по лимиту не расходует квоту и не портит счётчики
  использования.

### FR-4 Max context и компрессия

* FR-4.1 `max_context` — лимит входных токенов на запрос для клиента.
* FR-4.2 Если вход укладывается в лимит — запрос уходит **без
  изменений** (компрессии нет).
* FR-4.3 Если вход превышает лимит — старые ходы сжимаются
  **LLM-сводкой** (локальная модель), `system`-промпт и последние
  `keep_recent` сообщений сохраняются целиком.
* FR-4.4 Компрессия рекурсивна: если после сводки вход всё ещё
  превышает лимит, сжимается следующий блок; кап —
  `MAX_COMPRESS_ROUNDS`.
* FR-4.5 Существующая сводка всегда остаётся в контексте и не
  пересжимается повторно.
* FR-4.6 Если после всех раундов вход всё ещё превышает лимит → 413
  с точными числами (`tokens`, `limit`); молчаливой обрезки нет.
* FR-4.7 `max_output_tokens` клиента — жёсткий потолок ответа,
  перебивающий запрошенный клиентом `max_tokens`.
* FR-4.8 Результат компрессии виден в ответе: `gateway.compressed`,
  `messages_before/after`, `tokens_before/after`,
  `compress_rounds`; заголовок `x-gateway-compressed`.
* FR-4.9 Промпт сводки требует сохранять цель, ограничения, решения,
  имена и числа — сводка не теряет факты молча.
* FR-4.10 Падение LLM-сводки не роняет запрос: компрессия
  деградирует (сжатия нет) и это отражено в `gateway`.

### FR-5 Учёт использования

* FR-5.1 Считаются: запросы, входные/выходные токены, отказы — по
  каждому клиенту.
* FR-5.2 Счётчики персистентны (переживают рестарт процесса).
* FR-5.3 Ведётся кольцевой лог последних отклонённых запросов с
  причиной (401 / 403 / 404 / 413 / 429).
* FR-5.4 `GET /api/gateway/usage` отдаёт использование по клиентам;
  `GET /api/gateway/rejections` — лог отказов.

### FR-6 Управление клиентами

* FR-6.1 `GET /api/gateway/clients` — список (ключи маскированы).
* FR-6.2 `POST /api/gateway/clients` — создать/обновить клиента;
  валидация лимитов (400 с RU-текстом на некорректные значения).
* FR-6.3 `DELETE /api/gateway/clients/{name}` — удалить клиента.
* FR-6.4 Конфигурация клиентов сохраняется в `studio/data/gateway.json`
  и перечитывается без рестарта процесса.
* FR-6.5 При старте создаётся дефолтный клиент из `.env`
  (`GATEWAY_CLIENT_KEY`), если конфига ещё нет.

### FR-7 UI

* FR-7.1 Вкладка «Сервис» показывает LAN-адрес и готовый пример
  подключения (`curl` / Python).
* FR-7.2 Таблица клиентов: имя, маскированный ключ, RPM/TPM,
  max context, вкл/выкл, создание и удаление.
* FR-7.3 Живые счётчики использования по клиентам.
* FR-7.4 Лог отклонённых запросов с причиной.

## Нефункциональные требования

* NFR-1 Только stdlib + уже используемые зависимости (FastAPI,
  httpx); новых пакетов не требуется.
* NFR-2 Существующие роуты и поведение дней 11–29 не изменяются.
* NFR-3 Ошибки в формате OpenAI: `{"error": {"message", "type",
  "code"}}`.
* NFR-4 Модуль импортируется без побочных эффектов (сеть не
  трогается при импорте).
