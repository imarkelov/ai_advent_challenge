# Design: day35-cli-md-agents

## Контекст

Дни 30–34 дали `AssistantService` — четыре модуля (RAG по проекту,
ревью, поддержка с CRM, файловые сценарии) и 10 HTTP-роутов. Слой
описания агентов при этом остался **в коде**: системные промпты
`_ASK_SYSTEM` / `_SUPPORT_SYSTEM` / `_REVIEW_SYSTEM` — константы в
`assistant.py`, а «агента» как сущности в репозитории нет.

День 35 закрывает два разрыва сразу: даёт **терминальный вход**
(`studio/cli.py`) и выносит описания агентов в **`agents/*.md`**.

## Схема

```
  терминал / CI / пайп                     браузер (Студия)
        │                                        │
        │  python -m studio.cli review           │  POST /api/assistant/review
        │      --agent code-review               │
        ▼                                        ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  studio/cli.py  (тонкая обёртка: разбор argv → вызов → вывод)│
  └──────────────────────────────────────────────────────────────┘
        │                                        │
        └──────────────┬─────────────────────────┘
                       ▼
         ┌────────────────────────────────┐
         │  AssistantService              │  ← ОДИН источник правды
         │  ask_project / review_diff /   │     (дни 30–34)
         │  support_answer / run_scenario │
         └────────────────────────────────┘
                       │
                       │ читает системный промпт
                       ▼
         ┌────────────────────────────────┐
         │  agents/*.md                   │  ← определения агентов
         │  project-qa.{api,cli}.md       │     (frontmatter + тело)
         │  code-review.{api,cli}.md      │
         │  support.{api,cli}.md          │
         │  file-ops.{api,cli}.md         │
         └────────────────────────────────┘
                       ▲
                       │ AgentRegistry (кэш по mtime)
                       │ studio/backend/agents.py
```

## Решение 1: CLI — обёртка, а не второй ассистент

Соблазн — написать в CLI собственную логику: свой RAG, свой парсер diff,
свой обход CRM. Это дало бы **два поведения одного инструмента**:
терминал и веб начали бы расходиться в деталях (например, в ревью
появилось бы правило, которого нет в API), а багфиксы пришлось бы
делать дважды.

Поэтому CLI не содержит бизнес-логики вообще:

| Слой | Ответственность |
|---|---|
| `studio/cli.py` | разбор `argv`, типизация параметров, вызов сервиса, форматирование вывода, код возврата |
| `AssistantService` | вся логика: RAG, ревью, CRM, сценарии |
| `agents/*.md` | системный промпт и метаданные агента |

Проверяется тестом: CLI не импортирует `kb`, `mcp`, `gateway` и не
обращается к сети напрямую.

## Решение 2: почему агент — md-файл

Frontmatter-формат выбран потому, что определение агента — это
**документ**, а не код:

* **читается человеком** — видно, что инструктирует модель, без чтения
  Python;
* **диффится в ревью** — изменение промпта видно построчно, как обычный
  текст;
* **версионируется git** — история поведения агента доступна;
* **правится без кода** — сменить тон/ограничения можно правкой md;
* **не требует пакетов** — frontmatter `key: value` парсится stdlib-ом.

Формат файла:

```markdown
---
name: code-review
execution: cli
description: Ревью изменений: находки, severity, рекомендации
tools: [git, diff, corpus]
temperature: 0.1
---
Ты — код-ревьюер. ...
```

Обязательные поля: `name`, `execution`, `description`. Тело — системный
промпт (не пустой). Значения по умолчанию: `tools: []`,
`temperature: 0.2`.

**Валидация с RU-ошибками.** Битый frontmatter, отсутствие `---`,
неизвестное `execution` (не `api`/`cli`), пустое тело — `AgentError` с
указанием файла и причины. Молчаливое «агент не загрузился» недопустимо:
тогда CLI тихо работал бы дефолтным промптом, и правка md не давала бы
эффекта — худший вид бага.

## Решение 3: 4 агента × 2 исполнения = 8 файлов

Исполнения различаются **формой вывода и каналом**, а не смыслом:

| | `.api.md` (HTTP/Студия) | `.cli.md` (терминал) |
|---|---|---|
| Потребитель | браузер, JSON-клиент | человек в терминале, пайп, CI |
| Формат | структурированные поля, UI-блоки | markdown, короткие строки |
| Ссылки | на UI-элементы | на пути файлов и команды |
| Ограничения | без ANSI | без HTML, без «нажмите кнопку» |

Практическая разница видна на примере: в API-исполнении ревью-агент
может сослаться на панель источников, в CLI — обязан выдать
`файл:строка`, потому что панели в терминале нет.

**Разрешение выбора.** `AgentRegistry.get(name, execution="cli")`
берёт точное совпадение (`<name>.cli.md`); если файла нет — падает
обратно на `.api.md` и **помечает это** (`fallback: true`), чтобы CLI
мог предупредить. Молчаливая подмена исполнения сбивала бы с толку:
пользователь думал бы, что читает CLI-инструкции, а получал API-текст.

## Решение 4: типизация параметров сценариев

`run_scenario(name, **params)` принимает `dry_run: bool`. CLI получает
строки, и здесь кроется **опасный баг**: в Python непустая строка
истинна, поэтому `dry_run="false"` — это `True`. То есть
`scenario generate --param dry_run=false` **записал бы файлы**, хотя
пользователь просил dry-run.

Поэтому CLI типизирует значения явно:

| Ввод | Значение |
|---|---|
| `true`/`1`/`yes`/`on` | `True` |
| `false`/`0`/`no`/`off` | `False` |
| `none`/`null` | `None` |
| целое/дробное | `int`/`float` |
| остальное | строка |

Отдельный тест фиксирует, что `dry_run=false` **не пишет файлы**.

## Решение 5: вывод и код возврата

* по умолчанию — markdown в stdout (читается человеком и рендерится в
  GitHub/терминале);
* `--json` — машинный вывод для скриптов;
* `--out FILE` — запись отчёта в файл (для `review`/`scenario`);
* код возврата: `0` — успех, `1` — ошибка (валидация, отсутствие
  индекса, git, битый md). Пригодно для `&&`, `||` и CI;
* ошибки — в stderr с RU-текстом, без traceback (traceback только при
  `--debug`).

## Регрессия

Новые файлы: `agents/*.md` (8), `studio/backend/agents.py`,
`studio/cli.py`, два файла тестов, `scripts/e2e_day32.py`. Существующие
модули **не редактируются** — CLI переиспользует `AssistantService`
как есть. Поэтому регрессия дней 11–34 гарантируется структурно;
полный прогон тестов это подтверждает.
