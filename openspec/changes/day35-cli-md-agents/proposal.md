# Proposal: day35-cli-md-agents

## Why

Дни 30–34 дали ассистента, но **только через веб-Студию и HTTP**.
Разработчик, который живёт в терминале, вынужден поднимать сервер,
открывать браузер и кликать — чтобы задать вопрос по коду или посмотреть
ревью. Это разрыв: инструмент есть, а привычного входа в него нет.

Второй разрыв — **агенты неявны**. Четыре модуля ассистента (вопросы по
проекту, ревью, поддержка, файловые операции) реализованы как методы
Python, а их «характер» — системные промпты `_ASK_SYSTEM`,
`_SUPPORT_SYSTEM`, `_REVIEW_SYSTEM` — зашит в код. Из-за этого:

* нельзя посмотреть, **что именно** инструктирует модель, не читая
  Python;
* нельзя поправить поведение агента без правки кода и перезапуска;
* нельзя добавить нового агента, не написав метод;
* нет единого места, где видно набор агентов и их инструменты.

Это ровно тот случай, когда **Markdown — лучший формат для определения
агента**: он читается человеком, версионируется в git, диффится в
ревью и не требует кода для правки промпта.

### Ключевое решение: агент — это md-файл, а не метод

Определения агентов выносятся в `agents/*.md` с YAML-frontmatter:

```markdown
---
name: code-review
description: Ревью изменений — находки, severity, рекомендации
tools: [git, diff, corpus]
temperature: 0.1
---
Ты — код-ревьюер. По приведённым находкам сформулируй рекомендации...
```

**Восемь файлов: 4 агента × 2 исполнения** (как просили — «в обоих
исполнениях»):

| Агент | API-исполнение | CLI-исполнение |
|---|---|---|
| `project-qa` | `agents/project-qa.api.md` | `agents/project-qa.cli.md` |
| `code-review` | `agents/code-review.api.md` | `agents/code-review.cli.md` |
| `support` | `agents/support.api.md` | `agents/support.cli.md` |
| `file-ops` | `agents/file-ops.api.md` | `agents/file-ops.cli.md` |

Различие исполнений — в **форме вывода и канале**, а не в смысле:

* `.api.md` — исполнитель HTTP/Студия: ответ идёт в JSON, структура
  полей фиксирована, есть UI-блоки (`context.applied`);
* `.cli.md` — исполнитель терминал: ответ идёт в stdout/markdown-файл,
  нужны ANSI-дружелюбность, короткие строки, код возврата, отсутствие
  HTML и «нажмите кнопку».

Это не дублирование: у двух исполнений **разные потребители** — браузер
и терминал/пайп (`assistant review | less`, `> report.md`, CI).

### Что НЕ делаем (осознанно)

* **Не переписываем модули ассистента.** CLI — **тонкая обёртка** над
  `AssistantService`: он не дублирует логику RAG, ревью, CRM и
  сценариев. Один источник правды — `assistant.py`.
* **Не ломаем HTTP-путь.** Роуты `/api/assistant/*` продолжают работать
  как есть; md-агенты — дополнительный слой описания, а не замена.
* **Не выдумываем свой формат.** Frontmatter — обычный YAML-подобный
  блок `key: value`, парсится stdlib-кодом (PyYAML в зависимостях нет,
  а NFR-1 запрещает новые пакеты).
* **Не даём CLI git-мутаций** — как и в API: читаем, пишем файлы,
  коммит за человеком.

## What Changes

### Новый каталог `agents/`

* 8 md-файлов: 4 агента × 2 исполнения (`.api.md` / `.cli.md`),
  каждый с frontmatter (`name`, `execution`, `description`, `tools`,
  `temperature`) и телом промпта.
* Frontmatter — источник правды для CLI (`agents list`, `--agent`).

### Новый модуль `studio/backend/agents.py`

* `AgentSpec` (dataclass): `name`, `execution`, `description`, `tools`,
  `temperature`, `system_prompt`, `path`.
* `parse_agent_md(text)` — разбор frontmatter + тела (stdlib, без YAML-
  пакета), с валидацией обязательных полей и понятными ошибками.
* `AgentRegistry`: загрузка `agents/*.md`, `list()`, `get(name,
  execution)`, кэш по mtime (правка md подхватывается без рестарта).
* Разрешение конфликта: `get(name, execution="cli")` берёт
  `<name>.cli.md`, при отсутствии — падает обратно на `.api.md`
  (деградация с явным признаком, а не молчаливая подмена).

### Новый модуль `studio/cli.py`

* Один исполняемый CLI с подкомандами:
  * `agents list` / `agents show <name>` — каталог агентов из md;
  * `ask "вопрос" --agent project-qa` — вопрос по проекту (RAG);
  * `review [--diff FILE|--base BRANCH] [--out FILE]` — ревью;
  * `support <TICKET_ID> [--question Q]` — ответ по тикету;
  * `tickets [--status S] [--priority P]` — список тикетов;
  * `scenario <name> [--param k=v ...]` — запуск сценария;
  * `index [--strategy S]` — сборка индекса проекта;
  * `status` / `git` — состояние и git-контекст.
* Вывод: человекочитаемый markdown в stdout; `--json` для скриптов;
  `--out FILE` для записи отчёта в файл.
* Код возврата: 0 — успех, 1 — ошибка (пригодно для CI и пайпов).
* Параметры сценариев типизируются: `dry_run=false` — это `False`, а не
  непустая строка (иначе `"false"` — истина в Python, и `--param
  dry_run=false` **записал бы файлы** вместо dry-run).

### Тесты и e2e

* `studio/backend/tests/test_agents.py` — парсер, реестр, деградация;
* `studio/backend/tests/test_cli.py` — подкоманды через `main(argv)`;
* `scripts/e2e_day32.py` — Part A офлайн (CLI как **реальный
  подпроцесс**, а не вызов функции) + Part B live (реальная Ollama).
