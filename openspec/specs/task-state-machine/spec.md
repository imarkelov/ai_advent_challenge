# task-state-machine Specification

## Purpose

Состояние задачи как конечный автомат (день 13): задача per-диалог —
пайплайн stage-агентов (Планировщик → Исполнитель → Валидатор →
Оркестратор) под управлением детерминированного оркестратора; вход —
вкладка «Задача» в панели «Контекст». Состояние формализовано per-диалог
(стадия, пауза, описание, выводы стадий), пауза — на границе стадии с
инструкцией, продолжение — с сохранённого состояния, без повторных
объяснений.

## Requirements

### Requirement: Состояние задачи per-диалог

Система SHALL хранить состояние задачи в записи каждого диалога:
`task_id` (уникальный на каждую задачу; новый создаётся на каждый
запуск), стадия `planning` | `execution` | `validation` | `done` |
`paused` | `failed` (пауза и ошибка — значения стадии, не отдельные
флаги), позицию в пайплайне `current_step`/`total_steps`, ожидаемое
действие `expected_action` (`agent_response` — выполняется LLM-вызов;
`resume_wait` — пауза, ожидание продолжения; `human_input` — пауза,
ожидается инструкция), план stage-агентов `plan` (4 записи: агент,
статус `pending`|`in_progress`|`completed`, output, отметка времени
спавна), декомпозицию задачи `work_steps` (шаги: имя, статус
`pending`|`in_progress`|`completed`, output), `context_snapshot`
(описание, work-шаги с выводами, instruction — данные для продолжения
без повторных объяснений), описание задачи, счётчик повторов и текст
ошибки. Активная задача в диалоге SHALL быть одна; завершённая (`done`
/ `failed`) задача не блокирует создание новой. Задача MUST
принадлежать диалогу: переключение диалога переключает её состояние.
Состояние MUST переживать перезапуск сервера. Для диалога, созданного
до внедрения задачи, задача SHALL считаться неактивной (поле
отсутствует). Задача одного диалога MUST NOT влиять на другие
диалоги. Обычный чат (профиль дня 12, слои памяти дня 11) MUST
остаться без изменений.

#### Scenario: Состояние переживает перезапуск

- **WHEN** задача диалога на стадии `paused` (work-шаги с выводами сохранены) и сервер перезапущен
- **THEN** состояние задачи этого диалога восстанавливается: та же стадия, те же `work_steps` с выводами, и продолжение работает без повторного планирования и повторных объяснений

#### Scenario: Задача переключается вместе с диалогом

- **WHEN** в диалогах A и B ведутся разные задачи и пользователь переключается с A на B
- **THEN** UI показывает состояние задачи диалога B; пайплайн A заморожен в своём состоянии

#### Scenario: Старый диалог без поля задачи

- **WHEN** загружен `dialogues.json` с диалогом, у которого нет поля задачи
- **THEN** задача этого диалога считается неактивной и данные диалога не повреждаются

#### Scenario: Новая задача после завершения

- **WHEN** задача диалога на стадии `done` (или `failed`) и пользователь отправляет новый запрос в режиме «задача»
- **THEN** создаётся новая задача с новым `task_id` на стадии `planning`; карточка старой задачи остаётся в истории диалога

### Requirement: Stage-агенты и FSM-переходы

Пайплайн задачи SHALL состоять из стадий-состояний конечного автомата
`planning` → `execution` → `validation` → `done`. Переход в `paused`
возможен с любой активной стадии (на границе LLM-вызова); переход в
`failed` — с любой стадии при ошибке LLM-вызова; возврат из `failed`
— действием «повтор» (повтор упавшей стадии/шага). Каждую стадию SHALL
исполнять отдельный stage-агент: тот же LLM из конфига со своим
system-промптом. Планировщик (planning) по описанию задачи
составляет план work-шагов (структурированный ответ, best-effort
парсинг; сбой парсинга — план из 1 шага «выполнить запрос»).
Исполнитель (execution) выполняет work-шаги по одному (см.
Requirement «Пошаговое исполнение задачи»). Валидатор (validation)
сверяет работу с планом и выдаёт вердикт; на `done` Оркестратор-синтез
собирает outputs всех стадий в единый финальный ответ. Переходы между
стадиями SHALL контролировать детерминированный оркестратор бэкенда;
LLM MUST NOT управлять состоянием FSM. В system-промпт каждого
stage-агента SHALL инъектироваться только данные состояния задачи
(`context_snapshot`: описание, work-шаги и их outputs, ожидаемое
действие и (если задана) instruction); история сообщений чата MUST NOT
использоваться как источник промпта (чат — лишь представление процесса
для пользователя). Ошибка LLM-вызова стадии MUST NOT ломать диалог:
задача сохраняется на стадии `failed` с текстом ошибки, повтор —
действием «повтор».

#### Scenario: Полный прогон стадии за стадией

- **WHEN** запущен пайплайн задачи
- **THEN** вызовы LLM идут в порядке planning → execution (по work-шагам) → validation → синтез, system-промпт каждого stage-агента содержит описание задачи и outputs предыдущих стадий/шагов, финальный ответ — синтез Оркестратора

#### Scenario: История чата не входит в task-промпты

- **WHEN** задача выполняется в диалоге с длинной историей сообщений
- **THEN** system-промпты stage-агентов содержат только `context_snapshot` задачи (описание, work-шаги, их outputs, instruction); сообщения чата в task-промпты не входят

#### Scenario: Структурированный план Планировщика

- **WHEN** Планировщик возвращает структурированный список work-шагов
- **THEN** `work_steps` сохранены в состоянии задачи и видны в карточке процесса; при сбое парсинга плана задача продолжается с планом из 1 шага без ошибки пайплайна

#### Scenario: Ошибка стадии не ломает диалог

- **WHEN** LLM-вызов стадии завершился ошибкой API
- **THEN** задача сохранена на стадии `failed` с текстом ошибки, чат-история диалога не повреждена, повтор стадии/шага возможен действием «повтор»

### Requirement: Валидация и повтор выполнения

Валидатор SHALL выдавать вердикт `pass` | `fail` отдельной
машиночитаемой меткой в своём ответе (best-effort парсинг:
отсутствие/сбой метки интерпретируется как `pass`). При вердикте
`fail` система SHALL повторить стадию `execution` один раз:
Исполнитель повторяет work-шаги, его промпт содержит план, предыдущие
выводы шагов и замечания Валидатора как фидбэк. Повторный `fail` MUST
NOT приводить к бесконечному циклу: задача завершается на `done` с
сохранённым вердиктом, который попадает в синтез финального ответа.

#### Scenario: Первый fail → повтор execution

- **WHEN** Валидатор вернул `fail` с замечаниями
- **THEN** Исполнитель вызывается повторно по work-шагам, его промпт содержит план, первую работу по шагам и замечания Валидатора

#### Scenario: Второй fail → завершение с пометкой

- **WHEN** повторная валидация снова вернула `fail`
- **THEN** цикл не продолжается, задача переходит в `done`, вердикт `fail` сохранён и учтён в финальном ответе

#### Scenario: Метка вердикта отсутствует или битая

- **WHEN** ответ Валидатора не содержит распознаваемой метки вердикта
- **THEN** задача переходит в `done` как при `pass`, без ошибки пайплайна

### Requirement: Пауза и продолжение на любом этапе

Пользователь SHALL иметь возможность остановить задачу на любом этапе
кнопкой Пауза в карточке процесса и возобновить работу кнопкой
Продолжить. Пауза SHALL вступить в силу на границе LLM-вызовов
(граница стадии или граница work-шага): текущий LLM-вызов
доигрывается, следующий не начинается, стадия становится `paused`,
`expected_action` — `resume_wait`, `context_snapshot` зафиксирован.
При возобновлении пайплайн SHALL продолжить с первой невыполненной
стадией/work-шагом, получив всё необходимое из сохранённого состояния —
пользователь MUST NOT объяснять контекс заново. Обычные сообщения чата
во время активной непаузанной незавершённой задачи не выполняются:
`POST /api/chat` отвечает 200 с SSE-событием `error` («Задача
выполняется…»), сообщение пользователя не сохраняется; на паузе чат
работает как обычно (в режиме «задача» ввод = instruction).

#### Scenario: Пауза на стадии execution

- **WHEN** задача исполняет work-шаг 2 из 3 (стадия `execution`) и пользователь нажал Пауза
- **THEN** текущий LLM-вызов шага завершается и его output сохранён, стадия `paused`, следующий work-шаг не вызывается

#### Scenario: Продолжение без повторных объяснений

- **WHEN** задача на паузе после завершённого work-шага и пользователь нажал Продолжить
- **THEN** следующий work-шаг/стадия получает в system-промпте описание задачи, план, выводы завершённых шагов и instruction — без новых сообщений пользователя с контекстом

#### Scenario: Чат заблокирован во время задачи

- **WHEN** задача активна и не на паузе и клиент шлёт `POST /api/chat`
- **THEN** ответ 200 с SSE-событием `error` («Задача выполняется…»), сообщение не сохраняется; на паузе чат работает как обычно

### Requirement: Instruction на паузе

Пока задача на паузе пользователь SHALL иметь возможность дать
instruction (правку/уточнение): в режиме «задача» поле ввода чата
принимает её без LLM-вызова (плейсхолдер «Инструкция для
агентов…»). Instruction SHALL сохраняться в состоянии задачи и SHALL
быть инъектирована в system-промпт следующего выполняемого
шага/стадии при возобновлении, после чего очищена. Instruction для
непаузанной или неактивной задачи — ошибка 400.

#### Scenario: Instruction влияет на следующую стадию

- **WHEN** задача на паузе после первого work-шага, пользователь ввёл instruction «шаг 3 сделать иначе» в режиме «задача» и возобновил задачу
- **THEN** system-промпт следующей выполняемой стадии/work-шага содержит план и instruction, и instruction очищается из состояния после применения

#### Scenario: Instruction вне паузы отклоняется

- **WHEN** `POST /api/task/instruction` при непаузанной (или отсутствующей) задаче
- **THEN** 400 с RU-сообщением, состояние задачи не меняется

### Requirement: SSE-протокол пайплайна

Пайплайн задачи SHALL выполняться в отдельном SSE-эндпоинте
`POST /api/task/run` и стримовать события: спавн stage-агента
(`agent_spawned` со стадией, именем агента и временем), смену статуса
work-шага (`step_updated`: имя/индекс шага, статус, output при
завершении), поток вывода текущего work-шага (`step_delta` с
фрагментом текста), завершение стадии (`stage_done` с output и
вердиктом для validation), паузу (`task_paused`), снятие паузы
(`task_resumed`), завершение задачи (`task_done` с финальным ответом
Оркестратора), сбой (`task_failed` с текстом ошибки) и ошибку
(`error`). Outputs стадий и work-шагов SHALL сохраняться в истории
сообщений диалога с маркерами `task_id`/стадии/шага (для
восстановления карточки после перезагрузки); финальный ответ — как
обычное assistant-сообщение. Старый протокол `POST /api/chat`
(delta/done/error) MUST остаться без изменений.

#### Scenario: Стрим полного прогона

- **WHEN** клиент запустил `POST /api/task/run` для готовой к запуску задачи
- **THEN** последовательность событий: `agent_spawned`(planning) → `stage_done`(planning) → `agent_spawned`(execution) → `step_updated`/`step_delta` по каждому work-шагу → `stage_done`(execution) → `agent_spawned`(validation) → `stage_done`(validation) → `stage_done`(done) → `task_done`; история диалога содержит сообщения с маркерами и финальный ответ

#### Scenario: Стрим останавливается на паузе

- **WHEN** во время пайплайна задан стоп и текущий LLM-вызов завершён
- **THEN** стрим завершается событием `task_paused` на границе (стадия/шаг), дальнейшие стадии/шаги не выполняются

#### Scenario: Стрим при сбое LLM-вызова

- **WHEN** LLM-вызов стадии/work-шага завершился ошибкой API
- **THEN** стрим завершается событием `task_failed`, задача сохранена на стадии `failed`, повтор возможен через `run` (повтор упавшей стадии/шага)

### Requirement: REST API задачи

Система SHALL предоставлять (все тела с `dialogue_id`; 404 — диалог не
найден, 400 — RU-сообщение):
- `POST /api/task/start` — `{"dialogue_id", "description"}`: создать
  задачу (стадия `planning`, новый `task_id`); при активной
  (незавершённой, включая `paused`) задаче — 400; при последней задаче
  на `done`/`failed` — создаётся новая задача;
- `POST /api/task/run` — SSE-пайплайн: выполнять с текущего состояния
  до `done`/паузы/`failed`; при `failed` — повтор с упавшей
  стадии/шага; 400 — задача неактивна или на `done`;
- `POST /api/task/pause` — установить паузу (вступает на границе
  LLM-вызова); 400 — нет активной задачи или задача на `done`/`failed`;
- `POST /api/task/resume` — снять паузу (стадия возвращается к активной
  по `plan`/`work_steps`); 400 — нет паузы;
- `POST /api/task/instruction` — `{"dialogue_id", "text"}`, только на
  паузе;
- `POST /api/task/reset` — завершить текущую задачу и сбросить
  состояние (готовность к новой задаче);
- `GET /api/task?dialogue_id=` — текущее состояние задачи (или
  «неактивна»).

Состояние задачи SHALL включаться в ответы выдачи диалогов
(`GET /api/dialogues`, `GET /api/dialogues/{id}`).

#### Scenario: Запуск задачи

- **WHEN** `POST /api/task/start` с описанием для диалога без задачи
- **THEN** 200: задача активна, стадия `planning`, создан `task_id`; последующий `POST /api/task/run` начинает пайплайн

#### Scenario: Двойной start отклоняется

- **WHEN** `POST /api/task/start` при активной (незавершённой, включая `paused`) задаче
- **THEN** 400 с RU-сообщением, текущая задача не сбрасывается

#### Scenario: Start после завершения = новая задача

- **WHEN** `POST /api/task/start` при последней задаче на `done` или `failed`
- **THEN** 200: создана новая задача с новым `task_id` на стадии `planning`; данные старой задачи сохранены в истории сообщений

#### Scenario: Run на failed = повтор

- **WHEN** `POST /api/task/run` при задаче на стадии `failed`
- **THEN** пайплайн продолжается с упавшей стадии/work-шага; при успехе задача движется дальше по FSM

#### Scenario: Reset готовит к новой задаче

- **WHEN** `POST /api/task/reset` для задачи (любая стадия)
- **THEN** состояние задачи очищено; следующий `start` создаёт новую задачу со стадией `planning` и новым `task_id`

#### Scenario: Состояние в выдаче диалогов

- **WHEN** клиент запрашивает диалог (GET)
- **THEN** ответ содержит состояние задачи (`task_id`, стадия, `plan`, `work_steps`, `expected_action`, описание, вердикт) либо отметку об отсутствии задачи

### Requirement: Проверка (тесты и e2e)

Репозиторий SHALL содержать тесты, доказывающие: (1) новое состояние —
`task_id`, unified stage (включая `paused`/`failed`), `plan`/`work_steps`
со статусами, `expected_action`, новая задача после `done`/`failed`;
(2) FSM-цикл — полный прогон planning → execution (по work-шагам) →
validation → done через mock-LLM, события `agent_spawned`/`step_updated`/
`step_delta`/`stage_done`/`task_done`, task-промпты собираются из
`snapshot` (история чата не входит), синтез финального ответа;
(3) валидация — fail → повтор execution по work-шагам с фидбэком,
второй fail → done с пометкой, битая/отсутствующая метка → pass;
(4) пауза/продолжение — пауза на границе work-шага, возобновление с
сохранённого состояния, instruction в режиме «задача» попадает в
следующий промпт и отклоняется вне паузы; `failed` → повтор через
run; (5) API — `start` при активной → 400, `start` после
`done`/`failed` → новая задача, `run` на `done` → 400, `run` на
`failed` → повтор, 400/404 по остальным эндпоинтам, гард
`/api/chat`; (6) UI — карточка процесса (спавн, work-шаги, живой
вывод, пауза/продолжение, сворачивание при `done`, восстановление из
маркеров), тумблер режимов (чат не создаёт задачу, задача запускается
запросом, блокировка тумблера во время работы), отсутствие вкладки
«Задача» (Vitest/Testing Library). `scripts/e2e_studio.py` SHALL быть
расширен: детерминированное ядро (start → run до паузы на границе
шага → instruction → resume → done → reset) + live best-effort полный
пайплайн (события спавна/шагов, финальный синтез, карточка
восстанавливается после перечитывания диалога; в режиме чата задача не
создаётся); exit 0 = PASS/SKIP, 1 = FAIL.

#### Scenario: Офлайн-прогон FSM

- **WHEN** прогоняется офлайн-тест пайплайна с mock-LLM
- **THEN** все стадии и work-шаги выполнены в порядке, task-промпты содержат предыдущие outputs (из состояния, не из чата), задача в `done`, финальный ответ — синтез

#### Scenario: E2E прогон задачи

- **WHEN** запущен `python scripts/e2e_studio.py` (GPustack доступен)
- **THEN** пройден поток: start → SSE-пауза на границе work-шага → instruction → resume → task_done → reset; события спавна и step-события присутствуют; exit 0

### Requirement: Пошаговое исполнение задачи

Исполнитель (стадия `execution`) SHALL выполнять work-шаги плана
Пошагово: на каждый work-шаг — отдельный LLM-вызов, system-промпт
которого содержит описание задачи, план, выводы завершённых
work-шагов и (если задана) instruction. Статусы work-шагов в состоянии
задачи SHALL меняться `pending` → `in_progress` → `completed` с
сохранением вывода каждого шага. Поток вывода текущего work-шага SHALL
транслироваться клиенту в реальном времени (событие `step_delta`).
Стоимость задачи SHALL составлять 1 (планирование) + N (work-шаги) +
1 (валидация) + 1 (синтез) LLM-вызовов, с ретраем валидации — до 2N+3.

#### Scenario: Пошаговый прогон execution

- **WHEN** задача с планом из 3 work-шагов на стадии `execution`
- **THEN** Исполнитель вызывается 3 раза (по одному на шаг), по каждому шагу приходят события смен статуса, промпт каждого следующего шага содержит выводы предыдущих

#### Scenario: Живой вывод текущего шага

- **WHEN** work-шаг в статусе `in_progress`
- **THEN** клиент получает события `step_delta` с фрагментами вывода шага, и карточка процесса показывает текст текущего шага в реальном времени

### Requirement: UI: карточка процесса и режимы

В чате SHALL быть тумблер режимов «чат»/«задача» (сегмент-контрол у
поля ввода; состояние глобальное, персистентно хранится; по
умолчанию — «чат»): в режиме «чат» сообщение поля ввода даёт обычный
ответ (`POST /api/chat`), в режиме «задача» — запускает задачу
(или, при паузе, передаёт instruction; плейсхолдер ввода меняется
соответственно). Тумблер SHALL быть заблокирован, пока активна
непаузанная незавершённая задача.

После сообщения-запроса в потоке сообщений SHALL рендериться карточка
процесса: заголовок (описание задачи, статус-бейдж, кнопка действия —
Пауза во время выполнения, Продолжить на паузе, Повтор при `failed`,
отметка «Готово»/«Ошибка» в терминальных стадиях), прогресс-бар
(`current_step`/`total_steps` + подпись «Этап N/4: <label>») и секции
stage-агентов (`plan`) со сворачиванием/разворачиванием: иконка, имя
агента, бейдж статуса, отметка «спавн X с назад», тело секции
(Планировщик — сводка плана; Исполнитель — чек-лист work-шагов
[✓]/[⏳]/[ ] + живой бокс вывода; Валидатор — вердикт и вывод;
Оркестратор — финальный ответ). Спавн агента SHALL быть виден
(появление/разворачивание секции по `agent_spawned`). Секция активного
агента SHALL разворачиваться автоматически, завершённые — сворачиваться;
на `done` все секции свёрнуты (сводка), на `failed` секция упавшего
агента развёрнута с текстом ошибки. На паузе карточка заморожена
(живой бокс скрыт). После перезагрузки карточка SHALL восстанавливаться
из маркеров сообщений диалога.

#### Scenario: Спавн агента виден в диалоге

- **WHEN** оркестратор запускает stage-агента (событие `agent_spawned`)
- **THEN** в карточке процесса появляется/разворачивается секция агента с бейджем «В процессе» и отметкой времени спавна

#### Scenario: Прогресс по work-шагам в карточке

- **WHEN** Исполнитель выполняет work-шаги плана
- **THEN** чек-лист карточки показывает завершённые шаги [✓] с выводами, текущий [⏳] с живым выводом, ожидающие [ ]

#### Scenario: Сворачивание при завершении

- **WHEN** задача достигла `done`
- **THEN** все секции карточки свёрнуты, бейдж «Готово», финальный ответ виден как обычное assistant-сообщение под карточкой

#### Scenario: Пауза и продолжение из карточки

- **WHEN** пользователь нажал Пауза в карточке, а затем Продолжить
- **THEN** карточка заморожена на паузе (кнопка Продолжить), после продолжения пайплайн resumes с сохранённого состояния и карточка возобновляет живой вывод

#### Scenario: Восстановление карточки после перезагрузки

- **WHEN** страница перезагружена при существующей задаче (любая стадия)
- **THEN** карточка процесса восстановлена из маркеров сообщений: стадии с выводами, статусы work-шагов, текущая стадия; для завершённой задачи — свёрнутая сводка

#### Scenario: Тумблер режимов

- **WHEN** пользователь в режиме «чат» отправляет сообщение
- **THEN** обычный ответ, задача не создаётся; в режиме «задача» то же сообщение создаёт задачу и запускает пайплайн; при активной непаузанной задаче тумблер заблокирован
